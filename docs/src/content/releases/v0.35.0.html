v0.35.0 https://docs.peppy.bot/releases/v0-35-0/ 2026-10-25T00:00:00Z Actions and services gain typed failure kinds, commands cancel on Ctrl+C, and new commands call running instances. <article> <header> <h1>v0.35.0</h1> <p><em>Actions and services gain typed failure kinds, commands cancel on Ctrl+C, and new commands call running instances.</em></p> <p><small> Released on October 25, 2026 </small></p> </header> <h3>Breaking changes</h3> <ul> <li>A goal result and a service response are always a success: end a goal with <code>complete</code> (the result only), <code>fail(kind, message)</code> or <code>complete_cancelled(reason, …)</code>, and update any code that passed a success or error argument.</li> <li>Refuse a goal with <code>GoalDecision::refuse(kind, message)</code> in place of <code>reject(reason)</code>.</li> <li><code>fire_goal</code> and the test harness <code>send_goal</code> take a feedback bound such as <code>DEFAULT_FEEDBACK_BOUND</code> instead of the feedback QoS profile; the handle keeps every message up to that bound and cancels the goal when a consumer overflows it.</li> <li>A failed service call surfaces as <code>ServiceFailed</code> (the service's <code>Failure</code> in Python) with a failure kind and message, replacing <code>ServiceError</code> and <code>RuntimeError</code>; a service handler returns its response or that <code>Failure</code>.</li> <li>In tests, answer a service with <code>respond_failure(kind, message)</code> and refuse a goal with <code>pending.refuse(kind, message)</code>, in place of <code>respond_error</code> and <code>reject</code>.</li> </ul> <h3>Failure kinds</h3> <ul> <li>A contract declares its own failure kinds in a <code>failure_kinds</code> block that each member lists, so every generated action and service exposes a typed <code>FailureKind</code> enum and <code>Failure</code> the provider and client must use.</li> <li>The daemon refuses work that collides with other work holding a machine's stack (a stack change, node command, second repository refresh or benchmark, or a reservation) with the failure kind <code>busy</code>, retryable once that work ends.</li> <li><code>peppy repo add</code>, <code>remove</code> and <code>exclude</code> name the failure kind of a refusal, such as <code>precondition_failed</code> for an id already in use.</li> </ul> <h3>Cancelling commands</h3> <ul> <li><code>peppy stack launch</code>, <code>build</code>, <code>join</code>, <code>remove</code> and <code>benchmark</code>, <code>peppy node add</code>, <code>build</code> and <code>run</code>, and <code>peppy repo refresh</code> cancel their work on the first Ctrl+C, follow the goal to its end, and print its failure kind and message.</li> <li>Each of these commands exits with a status for the goal's outcome: 0 completed, 3 refused, 4 failed, 5 cancelled, and 130 after a second Ctrl+C.</li> <li>A goal ends when the process that sent it is gone; a provider sets <code>set_sender_grace</code> so a client that stops and restarts keeps its goals running.</li> <li>A worker reads why its goal was cancelled through <code>cancel_cause</code> (its caller, or its sender gone) and reports the reason through <code>complete_cancelled</code>.</li> </ul> <h3>Calling running instances</h3> <ul> <li><code>peppy node call &lt;instance&gt; &lt;member&gt;</code> calls one service or action of a running instance from the command line, taking its message through <code>--args</code>, <code>--set</code> and <code>--file</code>, and prints how the call ended.</li> <li><code>peppy node echo &lt;instance&gt; &lt;topic&gt;</code> prints a topic's messages until Ctrl+C, and <code>peppy node describe &lt;instance&gt;</code> shows a running instance's interfaces and their message formats.</li> </ul> <h3>MCP exposures</h3> <ul> <li>An MCP tool that refuses or fails a call reports a failure kind and message in its tool error and call record, and the <code>stack_copies</code> <code>join</code> and <code>remove</code> tools return an empty result on success.</li> <li>A goal that runs inside an MCP call is cancelled when the call closes or the client disconnects, while a goal run as a task keeps running until the client cancels the task.</li> </ul> <h3>Node documents</h3> <ul> <li>A node uses one content for each document it names; <code>peppy node sync</code> and <code>peppy node add</code> refuse a manifest that references one contract or pairing at two different sha256 values.</li> </ul> </article>
