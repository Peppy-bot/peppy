`peppy platform` connects this machine to the Peppy platform in two independent
steps. **Signing in** (`login`) gives the CLI a session for the platform API.
**Enrolling** (`enroll`) joins this machine to a project's cloud messaging
router: the CLI mints a private key and a certificate signing request, the
platform signs it, and the daemon dials the project's router with that
certificate from then on. The session is yours; the enrollment is the
machine's. Logging out does not unenroll, and the daemon never needs a session
to stay connected.

Peppy is a public OAuth client of the platform's identity provider (Zitadel):
the CLI obtains a bearer token through the browser and sends it to the backend,
which validates it. The CLI never sees your Google/passkey credentials. Those
stay in the browser.

## Commands

| Command | What it does |
|---------|--------------|
| `peppy platform login [--api-url <url>] [--no-browser]` | Signs in via the OAuth 2.0 Device Authorization Grant and caches the tokens. |
| `peppy platform logout` | Revokes the session's tokens at the identity provider and deletes them locally. The enrollment stays. |
| `peppy platform whoami [--json]` | Shows the signed-in identity, backend, and token validity. |
| `peppy platform workspaces [--json]` | Lists the workspaces you belong to. |
| `peppy platform projects [--workspace <id\|name>] [--json]` | Lists the projects of a workspace. |
| `peppy platform enroll [--workspace <id\|name>] [--project <id\|name>] [--name <peer>] [--replace] [--yes]` | Enrolls this machine as a peer of a project's cloud router and restarts the daemon under the new identity. |
| `peppy platform unenroll [--local-only] [--yes]` | Removes this machine's peer from the platform, deletes the local enrollment, and restarts the daemon standalone. |
| `peppy platform status [--json]` | Shows the enrollment, whether the daemon runs under it with a verified link, and what the platform reports about the router and this peer. |
| `peppy platform peers [--workspace <id\|name>] [--project <id\|name>] [--json]` | Lists the peers of a project's cloud router, this machine's project by default. |

`--api-url` overrides the backend on any command. `--yes` (`-y`) skips the
daemon-restart confirmation prompt described under [Enrolling](#enrolling).

## Signing in

```sh
peppy platform login
```

On a terminal this prints a verification URL and a user code, then opens your
browser at that URL (with the code pre-filled). Approve the request in the
browser and the CLI stores the tokens. Subsequent commands reuse them: you sign
in once and stay signed in until the refresh token expires; expired access
tokens are refreshed automatically.

Over SSH or anywhere without a browser, use `--no-browser`: the CLI prints the
URL and code and waits for you to approve them on another device.

```sh
peppy platform login --no-browser
```

### How it works

1. The CLI fetches the public `GET {api_url}/cli/auth-config`, which returns the
   `issuer`, the `client_id`, and the exact `scopes` to request.
2. It runs OIDC discovery against the `issuer`
   (`{issuer}/.well-known/openid-configuration`) to find the device, token and
   revocation endpoints.
3. It starts the device flow, opens the browser, and polls until you approve.
4. It caches the tokens (and the `issuer`/`client_id`, so refresh works offline)
   under `~/.peppy/conf/credentials.json5`.

Every later call to the platform API sends the cached access token as a bearer.
When it is about to expire, or the backend answers `401`, the CLI exchanges the
refresh token for a new one and persists the rotation.

## Enrolling

```sh
peppy platform enroll
```

Enrollment joins this machine to one project's cloud router. With one workspace
and one project on the account, the command needs no flags; otherwise name
them with `--workspace` and `--project` (an id or the exact name). The peer's
name defaults to this machine's core-node name; `--name` overrides it.

What happens:

1. The CLI resolves the workspace and project.
2. It mints a P-256 key pair and a certificate signing request whose only
   subject is the peer name. The private key never leaves the machine.
3. It posts the request to the project's `router/peers` endpoint. The platform
   signs it and answers with the certificate, the project CA, the routing
   namespace (the project id), and the zenoh identity the daemon's router must
   run under.
4. It writes the enrollment bundle under `~/.peppy/conf/peer/`:
   `enrollment.json5` (the record), `peer.key` (the private key, owner-only),
   `peer.crt` (the certificate followed by its issuing chain), `ca.crt` (the
   project CA), and `zenohd.platform.json5` (the peer config the platform
   rendered, kept for inspection).
5. Under `zenoh.managed`, it pokes the running daemon over its control socket.
   The daemon's router identity and session namespace cannot change while
   live, so the daemon restarts its generation under the new identity and the
   CLI waits for it to come back. A second poke then verifies the mutual-TLS
   link to the cloud router with a real handshake; a link that does not
   validate is reported with its reason, and the enrollment is kept.

The restart wipes the running node stack. When a daemon is running with user
nodes on a terminal, the command asks for confirmation first; `--yes` skips
the prompt, and a script (no TTY) is never prompted.

With no daemon running, the enrollment is written and the daemon joins the
router when it starts. Under `zenoh.external` the daemon is left alone and the
command prints where the material is for the operator's router to use.

### The certificate

The peer certificate is valid for 90 days. `peppy platform status` shows its
expiry and warns from 14 days out. To mint a new one, run:

```sh
peppy platform enroll --replace
```

This enrolls anew (a new peer and a new zenoh identity), restarts the daemon
under it, and removes the previous peer from the platform.

### Namespace

An enrolled daemon opens its own session, and every node it spawns, under the
project's routing namespace. Two machines enrolled in the same project share a
namespace and address each other across the cloud router, which is the
foundation for running one stack across both; see
[Federation](/advanced_guides/federation/). An unenrolled daemon runs under
`local`. The namespace is routing context only. It is not proof of project
membership, a tenant-isolation boundary, or an authorization policy: isolation
comes from each project having its own router and its own certificate
authority.

### Checking the link

```sh
peppy platform status
```

The report has three parts: the enrollment on disk (project, peer, router,
certificate expiry, files), the daemon (running, under the enrolled identity,
and whether a fresh handshake to the cloud router validates), and, when you
are signed in, the platform's view (the router's phase and this peer's
connection status). `peppy platform peers` lists every peer of the project as
the platform sees them, marking this machine.

## Unenrolling

```sh
peppy platform unenroll
```

This removes the peer on the platform (the platform drops it at the router's
next restart), deletes `~/.peppy/conf/peer/`, and pokes the daemon, which
restarts standalone under `local`. Removing the peer needs a session; a machine
that cannot sign in can delete only its local enrollment with `--local-only`
and have the peer removed from the web app. The same restart prompt and
`--yes` bypass apply as for `enroll`.

## Federation outside the Peppy platform

You do not need the Peppy platform to run nodes across several machines. Point
every machine at a Zenoh router you run yourself with
[`zenoh.external`](/advanced_guides/daemon_config/#zenohexternal-use-an-operator-run-router)
in `~/.peppy/conf/peppy_config.json5`:

```json5
zenoh: {
  external: {
    endpoint: "tcp/router.internal:7448",
  },
},
```

`endpoint` is a dial address, so start the router first (for example
`zenohd -l tcp/0.0.0.0:7448`) and make sure every machine, and every node
environment on it, can reach that host and port. Peppy dials this router, adopts
it, and never starts, restarts, reconfigures, or federates it: its lifecycle is
yours. No sign-in, no backend, and no cloud router is involved.

Every session carries a namespace under `zenoh.external` exactly as it does
under `zenoh.managed`: `local` when the machine is not enrolled, the project
namespace when it is. A shared router forwards traffic between namespaces
without matching it, so an enrolled machine and an unenrolled one discover
nothing from each other even though both are connected to your router. Keep
every machine on the same namespace; without the platform that is `local`, so
unenroll each machine (`peppy platform unenroll --local-only` when it has no
session) and restart its daemon. External mode has no federation control
socket, so `enroll` and `unenroll` never restart the daemon: a namespace change
reaches sessions only when you restart it by hand (`peppy service stop`, then
start it again).

## Backend

By default the CLI talks to the prod backend, `https://api.peppy.bot`. That URL
is stored in the `resource_servers` block of
`~/.peppy/conf/peppy_config.json5` (see [Daemon configuration](/advanced_guides/daemon_config/)),
seeded on first run and editable in place. To point at a different backend
without editing the file, use `--api-url` or `PEPPY_API_URL`.
The URL is resolved in precedence order: `--api-url`, then `PEPPY_API_URL`, then
`resource_servers.api`. In release builds, plain `http` is allowed only for
local backends (loopback / `*.localhost`); anything else must be `https`. Debug
builds accept remote plain `http` with a warning.

## Credential storage

Tokens live at `~/.peppy/conf/credentials.json5`, written owner-only (`0600`).
The enrollment lives beside it under `~/.peppy/conf/peer/`, with the private
key and the record owner-only. The root honors `PEPPY_HOME`.

Tokens are never printed and `Authorization` headers are redacted in verbose
output.

## Signing out

```sh
peppy platform logout
```

This revokes the refresh token and then the access token at the identity
provider, then deletes the local session. The backend checks every bearer with
the identity provider, so a revoked token stops working at once. It revokes
only the tokens this machine holds; a session on another device keeps working.

Signing out leaves the enrollment in place: the daemon keeps its certificate
and its link to the project router, and only the CLI's platform calls need a
new `peppy platform login`.

## Environment variables

| Variable | Purpose |
|----------|---------|
| `PEPPY_API_URL` | Override the backend base URL. |
| `PEPPY_HOME` | Override the `~/.peppy` data root (also moves the credentials file and the enrollment). |
| `NO_COLOR` | Disable colored output. |

## Running one stack across your project's machines

Once two machines are enrolled in the same project they share a namespace and
can address each other through the project's cloud router, which is the
foundation for running a single Peppy stack across both. See
[Federation](/advanced_guides/federation/).
