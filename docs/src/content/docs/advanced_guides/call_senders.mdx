Every call to a Peppy daemon (raw services, raw actions, and daemon interfaces like `robot_leases:v1` and `robot_membership:v1`) is cryptographically signed. The daemon enforces [daemon scopes](/advanced_guides/fleet/#scopes-and-raw-calls), raw-call restrictions, and CLI privileges against the **verified signature**, never trusting an unverified sender ID. A node cannot impersonate `peppy-cli` or another lease holder.

## Keys

Each caller signs daemon requests with an Ed25519 key pair:

| Caller | Key lifecycle |
| --- | --- |
| **Node instance** | Fresh ephemeral key pair per start, written to a per-start key file named in the instance's runtime config and deleted when that process exits (restarts get a new key). |
| **CLI (`peppy`)** | Persistent key pair at `<data_root>/credentials/command_line.key`, created on first daemon boot. |
| **Daemon** | Fresh in-memory key pair per daemon boot. |

`credentials/` and its key files are owner-only (`0700` / `0600`).

Signing happens automatically inside `peppylib` (Rust and Python), generated code, the codec API, built-in MCP servers, and the `peppy` CLI. Topics, node-to-node calls, and daemon-to-node calls are **not** signed.

Each signature rides in the Zenoh query attachment and covers: session namespace, key expression (sender + receiver), call kind, payload, timestamp, and a one-time nonce.

## What the daemon refuses

The daemon verifies the signature before handling any call (except service liveness probes) and returns `rejected` if:

- The call is unsigned (for example, a node built with an older Peppy version: rebuild it).
- The signature does not match the claimed sender's key (spoofing `peppy-cli` or another instance).
- The claimed sender has no active key registered on the daemon (stopped process).
- The timestamp differs from the daemon's wall clock by more than **30 seconds**.
- The nonce was already seen within the last 30 seconds (replay).
- A cross-machine call lacks a valid machine certificate chain (see [Machines of a federation](#machines-of-a-federation)).

For action goals on the daemon, only the **original goal sender** may cancel a goal, preventing another process that observes a `goal_id` on the wire from cancelling someone else's `lease` goal.

## Limits

- **Same-user process nodes**: Native (non-container) nodes run as the same Unix user as the daemon and CLI, so OS permissions alone do not stop a native node from reading other local key files. [Container nodes](/advanced_guides/containers/#what-a-container-node-sees-of-the-data-root) cannot see the Peppy data root and only see their own key file.
- **Replies are unsigned**: Daemon responses are not signed; an attacker on the network could spoof replies.
- **Leases stay cooperative**: Robot driver nodes do not verify leases themselves; signatures enforce who may talk to the daemon, not who may talk directly to a robot node.

## Machines of a federation

Across machines in a [federation](/advanced_guides/federation/), each daemon proves its identity with an X.509 **machine certificate**:

- **Platform-enrolled machines**: automatically use `conf/peer/peer.crt` + `chain.crt` + `peer.key`, verified against the project CA (`ca.crt`).
- **Self-managed federations** (operator-run router): configure [`machine_certificate`](/advanced_guides/daemon_config/#machine_certificate-the-certificate-of-the-machine) with a certificate whose Common Name matches the core node name.

**How the trust chain works:**

1. At boot, each daemon signs a **boot statement** (namespace, core node, boot ID, ephemeral boot public key) using its machine certificate key.
2. Using that boot key, the daemon signs an **endorsement** for its CLI key and for every instance key it starts.
3. Cross-machine calls attach the certificate chain, boot statement, and endorsement. The receiving daemon validates the chain against its CA and checks that the namespace, core node, and instance ID match the call.

Important rules:
- Daemons without a machine certificate reject all cross-machine calls (and their calls are rejected by peers).
- A launch coordinator only accepts a remote instance's call as that instance if the launch actually placed it on that machine.
- Platform certificates identify a project peer rather than a specific core node name, and removed peers stay trusted until their certificate expires.
- Federated machines must keep their wall clocks synchronized within **30 seconds**.
