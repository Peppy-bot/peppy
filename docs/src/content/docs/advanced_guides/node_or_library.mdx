Code shared across multiple parts of a robot has two possible homes:

- A [**node**](/reference/concepts/#node) is an independent OS process managed by the Peppy daemon. Other nodes talk to it over [topics](/advanced_guides/topics/), [services](/advanced_guides/services/), and [actions](/advanced_guides/actions/).
- A **shared library** is a normal Rust crate or Python package compiled or imported directly into each node that calls it.

Use this page to decide which one fits. Once you decide on a node, see [Choosing a communication pattern](/advanced_guides/communication_patterns/).

The decision comes down to two questions:

1. **Does the code need its own lifecycle?** Nodes start, stop, crash, and restart independently, and Peppy monitors them. Libraries share the lifecycle and process of their caller.
2. **Can each call afford messaging overhead?** Calling a node serializes a message over the transport layer. Calling a library is a direct in-process function call.

## Side by side

| | Node | Shared library |
|---|---|---|
| Execution | Dedicated OS process per instance | Runs inside each calling node's process |
| Interface | Declared in `peppy.json5` (topics, services, actions) | Language-native functions and types |
| Callers | Rust or Python nodes on any machine, `peppy node call`, and [MCP](/advanced_guides/mcp/) | Nodes in the same programming language |
| Data passed | Declared [message formats](/reference/message_format/) (copied on the wire) | Any language type, by value or reference |
| Call cost | Serialization + messaging hop + deserialization | Function call |
| Fault isolation | Isolated; governed by its own [restart policy](/guides/launch_files/#restart-policy) | Crashes the calling node |
| Observability | Status, health, restarts, run log, OpenTelemetry export | None separately (part of caller's log) |
| State | Single shared state across consumers | Separate copy per calling node |
| Versioning | One resolved version per launch | Independent version pinned per node |
| Distribution | Peppy [repository](/advanced_guides/repositories/) | Language package manager (`cargo`, `uv`, etc.) |

## Make it a node

Choose a **node** when any of these apply:

- **Standalone robot subsystem**: Camera drivers, arm controllers, and motion planners have clear inputs/outputs and can run independently. Declaring them in `peppy.json5` makes them inspectable (`peppy node describe`) and callable (`peppy node call`) with zero extra code.
- **Reusable across stacks**: Launchers configure instances with [parameters](/guides/parameters/) and bindings, and teams pull them by `name:tag` from a [repository](/advanced_guides/repositories/) ([Sharing nodes](/guides/sharing_nodes/)).
- **Needs recording, monitoring, or benchmarking**: Recorders and dashboards can only tap data sent over Peppy interfaces ([contracts](/advanced_guides/contract_implementation/), [observers](/advanced_guides/pairing/#observers-watching-a-pairing-without-joining-it), [`peppy stack benchmark`](/advanced_guides/stack_benchmark/)). In-process library return values are invisible to other nodes.
- **Cross-language callers**: Rust and Python nodes exchange messages seamlessly via generated `peppygen` bindings without writing FFI bridges.
- **Multi-robot or swappable**: One generic node can serve multiple robots via parameters and [contracts](/advanced_guides/contract_implementation/).
- **Needs fault isolation or automatic restarts**: Each instance has its own [restart policy](/guides/launch_files/#restart-policy) (exponential backoff 1 s to 60 s) and health checks (3 missed checks = `unhealthy`, 60 s silent = kill and restart under `on_failure`/`always`; see [Instance health and lifecycle](/guides/node_stack/#instance-health-and-lifecycle)). Consumers reconnect automatically.
- **Needs per-component observability**: Appears in [`peppy stack list`](/guides/node_stack/#checking-node-status), gets its own run log, and tags [OpenTelemetry](/advanced_guides/opentelemetry/#filtering-by-node-and-by-machine) logs with `service.name` (node) and `service.namespace` (machine).
- **Needs its own runtime environment or host**: Can run inside a [container](/advanced_guides/containers/) with isolated system dependencies or be placed on a GPU host via [federation](/advanced_guides/federation/).
- **Owns an exclusive resource**: Hardware buses, shared maps, or GPU-resident models belong in one owning node that serves multiple consumers.

## Make it a shared library

Choose a **shared library** when any of these apply:

- **Inside a tight control loop**: High-frequency loops (such as 1 kHz inverse kinematics) cannot afford messaging latency. Measure actual messaging overhead on your hardware with [`peppy stack benchmark`](/advanced_guides/stack_benchmark/) to check.
- **Zero transport failure tolerance**: Critical checks (such as motor safety limits) must run synchronously in-process without risk of timeouts or dropped links.
- **Pure computation with no lifecycle**: Math utilities, parsers, wire protocols, and robot kinematics definitions have no independent state or streams.
- **Rich in-memory types**: Functions passing references into large maps, closures, or generics do not fit serialized [message formats](/reference/message_format/).

Tradeoffs of a library: it crashes with its caller, is invisible to Peppy monitoring, is single-language (unless you maintain FFI bindings), and each node links its own state and pinned version.

## A node built on a library

You can combine both: put pure logic in a transport-free shared library, then wrap it in a thin node that handles `peppy.json5` interfaces and parameters.

- High-frequency nodes link the library directly, while slower consumers call the wrapper node.
- Hardware drivers and simulated twins share the same library and implement the same [contract](/advanced_guides/contract_implementation/).
- Unit tests test the library directly with `cargo test` or `pytest`, while the [test harness](/advanced_guides/testing/) tests the node wrapper.

The Peppy hubs follow this pattern: [`public-peppy-libs`](https://github.com/Peppy-bot/public-peppy-libs) holds transport-free kinematics, collision geometry, and motion planning libraries, while [`nodes-hub`](https://github.com/Peppy-bot/nodes-hub) wraps them into arm nodes and `motion_planner`.

## How a node takes a shared library

Nodes pull libraries through their native package manager (`cargo` or `uv`):

- **Inside the node directory**: Use a local path dependency (for private code used only by that node).
- **Shared across nodes**: Pull from a Git repository or package registry. Because [`peppy node add`](/guides/node_stack/#adding-hello_world-to-the-stack) snapshots only the node directory and never follows symlinks, relative paths outside the node directory (`../shared`) will fail to build.

Pin an exact Git commit (`rev`), not a branch, so builds stay reproducible across machines:

<Tabs>
  <TabItem label="Python">
    ```toml title="pyproject.toml"
    [project]
    dependencies = ["arm_kinematics"]

    [tool.uv.sources.arm_kinematics]
    git = "https://github.com/acme/robot-libs"
    subdirectory = "arm_kinematics"
    rev = "<commit>"
    ```
  </TabItem>
  <TabItem label="Rust">
    ```toml title="Cargo.toml"
    [dependencies]
    arm_kinematics = { git = "https://github.com/acme/robot-libs", rev = "<commit>" }
    ```
  </TabItem>
</Tabs>

When two communicating nodes must agree on shared calculations (such as unit conversions), pin them to the same commit.

## Worked example: one arm

- **Motor protocol (library)**: Called every control tick inside the driver; no shared state.
- **Arm driver (node)**: Owns the motor bus, restarts independently, publishes joint states to controllers, dashboards, and recorders.
- **Kinematics (library)**: Called in the 1 kHz controller loop and inside the motion planner.
- **Motion planner (node)**: Takes ~1 s per request (messaging cost is negligible), works with any robot implementing its contracts, and can run on a remote compute machine.
- **Robot description (library)**: Joint limits and meshes pinned at one commit so driver, simulator, and planner agree.
- **Recorder (node)**: Taps driver and camera outputs without modifying either node.

**Rule of thumb:** Code with its own lifecycle or external consumers is a **node**; code that only computes for its caller is a **library**.
