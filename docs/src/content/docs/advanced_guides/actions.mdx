Actions are for **long-running tasks** that need feedback during execution and support cancellation.
A client sends a goal to an action node, which can provide periodic feedback while working and delivers a final result upon completion.

Use actions for tasks like navigation, arm movement, or any operation that runs over time and benefits from progress updates. (For a *continuous* bidirectional exchange with no defined end, an inner control loop rather than a discrete job, use a [pairing](/advanced_guides/pairing/#pairing-vs-actions) instead.) For the full map of mechanisms, see [Choosing a communication pattern](/advanced_guides/communication_patterns/).

A node can drive **multiple goals concurrently** for the same action. Each accepted goal yields its own `GoalContext` (owning that goal's feedback stream, cancel signal, and result), so one server can route by a discriminator in the request (e.g. `arm_id`) and drive several independent resources in parallel. The framework routes each client's cancel and result requests to the right goal by `goal_id`; deciding whether to accept a second concurrent goal is up to your goal handler.

## Action lifecycle

An action consists of four communication channels built on top of services and topics:

1. **Goal** (service): the client sends a goal request; the server accepts or refuses it.
2. **Feedback** (topic): the server publishes progress updates while working on the goal.
3. **Cancel** (service): the client asks a live goal to stop, at any time; delivery is a signal the worker may honor or ignore.
4. **Result** (service): the client requests how the goal ended once the server finishes.

```
Client                              Server
  │                                    │
  │──── fire_goal (request) ──────────>│
  │<─── goal ack (+ GoalResponse) ─────│
  │                                    │
  │<─── feedback ──────────────────────│  (repeated)
  │<─── feedback ──────────────────────│
  │                                    │
  │──── get_result (request) ─────────>│
  │<─── ResultResponse ────────────────│
```

### How a goal ends

The server answers each goal with its acceptance or its refusal. An accepted goal then ends with one terminal status:

| Status | What ends the goal | What the client gets |
| --- | --- | --- |
| `completed` | The worker calls `complete` | The result. The goal is a success. |
| `failed` | The worker calls `fail` | A failure kind and a message, and no result |
| `cancelled` | The worker calls `complete_cancelled` | The reason of the cancel and a result |
| `abandoned` | The worker drops the goal without an end, or the producer is gone | Nothing |
| `expired` | The goal ended, and the producer no longer keeps its result | Nothing |

A refusal and a failed goal give a **failure kind** and a message for a person. The kind says why, so that the client can try again, plan again or call a person. A member gives a kind from a closed set: the kinds of peppy, and the kinds that the contract of the member declares in its [`failure_kinds` block](/advanced_guides/contract_implementation/#failure-kinds). A native action, which no contract declares, gives the kinds of peppy only:

| `failure_kind` | Meaning |
| --- | --- |
| `attempt_failed` | The attempt gave no result |
| `timeout` | The bound of the provider passed |
| `precondition_failed` | A precondition failed |
| `resource_unavailable` | A robot, limb or host is gone |
| `rejected` | The provider refused the goal, and no other kind says why |

The peppy daemon gives one kind of its own beside these, as a contract does: `busy`, other work runs on the daemon (a stack change, a node goal, a repository refresh or a benchmark), and the same request can succeed once that work ends (see [How a stack command ends](/guides/launch_files/#how-a-stack-command-ends)).

The generated code of each action declares these kinds as a `FailureKind` enum and a `Failure` type (`kind`, `message`). The generated provider can give no other kind: in Rust a kind that the member does not declare is not a variant of the enum, so the node does not compile; in Python `Failure` raises `ValueError` for it before anything reaches the wire. The generated client parses each failure from the wire into the same type: a kind that the member does not declare is an error, never a failure of an unknown kind. The error of an undeclared kind keeps the message of the failure in its text. In Python, `Failure` also raises `TypeError` for a message that is not a `str`: give the text of an exception `error` with `Failure(kind, str(error))`.

So no result reports a refusal or a failure in a field of its own, such as `success: false` and an error text. A field that gives the answer of a check, such as whether a pose is reachable, is data and stays in the result.

## Exposing an action

A node that handles action goals declares its actions under `interfaces.actions.exposes` in its `peppy.json5`.
Each action can define a `goal_service`, a `feedback_topic`, and a `result_service`:

The `goal_service` payloads and the `result_service` response are all optional: any of `goal_service.request_message_format`, `goal_service.response_message_format`, and `result_service.response_message_format` is omitted when the corresponding payload carries no fields. For example, a `calibrate` action can omit `goal_service.request_message_format` because it has no goal parameters, and a `result_service` that only signals completion can omit its `response_message_format` too. The `result_service` block itself is also optional: the goals of an action without it end with `complete`, `fail` or `complete_cancelled` all the same, with an empty result.

The `result_service` never carries a user-defined request. A `get_result` call is correlated to its goal by the `goal_id` the framework assigns at `fire_goal`, so the only payload you declare on the result side is `response_message_format`, which the producer supplies through `complete` or `complete_cancelled`. Declaring a `result_service.request_message_format` is rejected when the config is parsed, since no generated API, wire message, or producer handler could ever read it.

The `feedback_topic` block is optional: actions that don't stream progress can omit it entirely. When you do declare `feedback_topic`, however, its `message_format` is required and cannot be empty: every feedback message must carry a non-empty payload, since empty payloads are reserved as the framework's per-goal end-of-stream signal (see [Receiving feedback](#receiving-feedback)). A `feedback_topic` declared without a `message_format`, or with an empty one, is rejected when the config is parsed, identically for Rust and Python nodes.

Feedback is live only: `feedback_topic` takes no `retention`. The server always publishes feedback with the `reliable` profile's settings; a `qos_profile` key on `feedback_topic` is not read by the generated code. The client sets how many unread feedback messages its handle keeps with the feedback bound of `fire_goal` (see [Receiving feedback](#receiving-feedback)).

### Handling goals

After running `peppy node sync`, the code generator creates a module for each exposed action under `peppygen::exposed_actions`.
Use `ActionHandle::expose` to set up the action, then loop accepting goals. `handle_goal_next_request` returns the next *accepted* goal as a `GoalContext`; refused goals are answered and skipped for you, so the accept loop ends only when the goal stream closes (the node is shutting down). Spawn a worker per context so goals run concurrently; each context owns that goal's feedback, cancel signal, and result, so nothing crosses between goals:

<Tabs>
  <TabItem label="Python">
```python
import asyncio

from peppygen import NodeBuilder
from peppygen.exposed_actions import move_arm


# Drive one accepted goal concurrently with any others already running. The
# context owns this goal's feedback, cancel signal, and result.
async def drive(ctx):
    # Feedback goes through this goal's context, not a shared slot.
    await ctx.publish_feedback([7, 31, 43])
    # Deliver the result for this specific goal; the client's
    # get_result(handle) is routed back here by goal_id.
    await ctx.complete(True, None, [98, 4, 26])


async def run_action(node_runner):
    action = await move_arm.ActionHandle.expose(node_runner)

    # The decider sets the concurrency policy: e.g. refuse a goal for a busy
    # arm_id. Refused goals are answered and skipped internally.
    def decide(request):
        print(
            f"goal from {request.instance_id}: arm_id={request.data.arm_id} "
            f"desired={request.data.desired_position}",
            flush=True,
        )
        return move_arm.GoalDecision.accept()

    while True:
        ctx = await action.handle_goal_next_request(decide)
        if ctx is None:
            break  # goal stream closed (node shutting down)
        asyncio.create_task(drive(ctx))


async def setup(parameters, node_runner):
    # Spawn the accept loop so setup returns and the node starts serving.
    return [asyncio.create_task(run_action(node_runner))]


def main():
    NodeBuilder().run(setup)


if __name__ == "__main__":
    main()
```
  </TabItem>
  <TabItem label="Rust">
```rust
use peppygen::exposed_actions::move_arm;
use peppygen::{NodeBuilder, Parameters, Result};

fn main() -> Result<()> {
    NodeBuilder::new().run(|_args: Parameters, node_runner| async move {
        let mut action = move_arm::ActionHandle::expose(&node_runner).await?;

        // Spawn the accept loop so this setup closure returns and the node
        // starts serving. The loop runs for the life of the node.
        tokio::spawn(async move {
            // Each call returns the next accepted goal; refused goals are
            // answered and skipped, so the loop ends only when the stream
            // closes (None) or errors.
            while let Ok(Some(ctx)) = action
                .handle_goal_next_request(|request| -> Result<move_arm::GoalDecision> {
                    println!(
                        "goal from {}: arm_id={} desired={:?}",
                        request.instance_id, request.data.arm_id, request.data.desired_position
                    );
                    // The decider sets the concurrency policy: e.g. refuse a
                    // goal for a busy `arm_id`.
                    Ok(move_arm::GoalDecision::accept())
                })
                .await
            {
                // Drive this goal concurrently with any others already running.
                tokio::spawn(async move {
                    // Feedback goes through this goal's context, not a shared slot.
                    ctx.publish_feedback([7, 31, 43]).await.ok();
                    // Deliver the result for this specific goal; the client's
                    // get_result(handle) is routed back here by goal_id.
                    ctx.complete(true, None, [98, 4, 26]).await.ok();
                });
            }
        });

        Ok(())
    })
}
```
  </TabItem>
</Tabs>

`GoalDecision` controls admission. The decision and the failure of a refusal travel in a framework-owned envelope wrapped around the goal reply, so they never appear in your schema: `GoalResponse` contains exactly the fields declared in `goal_service.response_message_format`, and the framework never adds an `accepted` or error field to it.

- `GoalDecision::accept()` (`GoalDecision.accept()` in Python) admits the goal, replies to the client, and yields a `GoalContext`. When the action declares a `response_message_format`, the constructor takes the declared response instead: `GoalDecision::accept(response)`.
- `GoalDecision::refuse(kind, message)` (`GoalDecision.refuse(kind, message)` in Python) refuses it with a [failure kind](#how-a-goal-ends) of the action and a message: the client sees `accepted == false` and the failure on its handle, no context is created, and the accept loop transparently moves on to the next goal. A refusal carries no goal response. This is where you enforce per-resource concurrency limits.

In Python, the constructor `GoalDecision(response, refusal)` takes an accept with the declared response, or a refusal with no response, and raises `ValueError` for any other pair. The server builds the decision of the decider again as a decision of its own action before it answers the goal, so a decider shared between two actions can give the decisions of either. A decider that raises, or that gives a decision that the serving action cannot send (a refusal with a kind that the action does not declare, an accept without the declared response), refuses the goal with the kind `attempt_failed` and the text of the error. Nothing of that decision reaches the wire, the client gets an answer, and the server keeps serving the next goal. In Rust, a decider that returns `Err` does the same: the goal is refused with `attempt_failed` and the text `the goal decider failed: <error>`, and `handle_goal_next_request` keeps polling.

A goal whose request bytes do not decode into the declared `request_message_format` (a field missing, a fixed-length array of the wrong length) never reaches your decider: the generated server refuses it with the kind `rejected` and the decode error as the message, and keeps serving the next goal. The client sent something this server's shape does not admit, which is the client's problem to learn about, not a reason to stop serving.

The `GoalRequest` passed to the decider contains:
- `instance_id`: the client instance that sent the goal. The producer is binding-agnostic; it doesn't know which slot on the client this goal is heading to.
- `core_node`: the core node of the caller.
- `data`: the deserialized goal parameters (only present when `request_message_format` is defined).

The `GoalContext` (`ctx`) is the only handle you need to drive the goal:
- `ctx.request()`: the decoded `GoalRequest`.
- `ctx.goal_id()`: this goal's correlation id.
- `ctx.sender()` (Rust): the process that sent the goal (see [Goals that end with their sender](#goals-that-end-with-their-sender)).
- `ctx.publish_feedback(...)`: publish a feedback message on this goal's stream.
- `ctx.cancel_signal()` / `ctx.is_cancelled()` / `ctx.cancel_cause()`: observe cancellation and why it came (see below). In Python, `ctx.cancel_reason()` gives the reason of that cause in words.
- `ctx.complete(...)`: end the goal with its result, a success.
- `ctx.fail(kind, message)`: end the goal failed, with a failure kind of the action, a message, and no result.
- `ctx.complete_cancelled(reason, ...)`: end the goal cancelled, for `reason`, with its result.

The first of `complete`, `fail` and `complete_cancelled` ends the goal; later calls do nothing.

A producer exposes its action once and serves any client that fires a goal at it. Starting the producer before or after the client is equally valid.

To enforce a concurrency limit (say, one in-flight goal per arm), refuse a goal whose arm is already busy, and release the arm when the goal finishes. The decider and the per-goal workers share the busy set:

<Tabs>
  <TabItem label="Python">
```python
# Arms currently driving a goal. Shared by the decider and the workers;
# asyncio is single-threaded, so a plain set is safe here.
busy: set[int] = set()


async def drive(ctx):
    arm_id = ctx.request().data.arm_id
    await ctx.complete(True, None, [98, 4, 26])
    # Release the arm so future goals for it are accepted again.
    busy.discard(arm_id)


def decide(request):
    arm_id = request.data.arm_id
    if arm_id in busy:
        # The failure rides back to the client in the goal ack.
        return move_arm.GoalDecision.refuse(
            move_arm.FailureKind.REJECTED, f"arm {arm_id} is already moving"
        )
    busy.add(arm_id)
    return move_arm.GoalDecision.accept()


while True:
    ctx = await action.handle_goal_next_request(decide)
    if ctx is None:
        break
    asyncio.create_task(drive(ctx))
```
  </TabItem>
  <TabItem label="Rust">
```rust
use std::collections::HashSet;
use std::sync::{Arc, Mutex};

// Arms currently driving a goal. Shared by the decider and the workers.
let busy: Arc<Mutex<HashSet<u16>>> = Arc::new(Mutex::new(HashSet::new()));

while let Ok(Some(ctx)) = action
    .handle_goal_next_request({
        let busy = Arc::clone(&busy);
        move |request| -> Result<move_arm::GoalDecision> {
            // `HashSet::insert` returns false when the arm is already busy.
            if busy.lock().unwrap().insert(request.data.arm_id) {
                Ok(move_arm::GoalDecision::accept())
            } else {
                // The failure rides back to the client in the goal ack.
                Ok(move_arm::GoalDecision::refuse(
                    move_arm::FailureKind::Rejected,
                    format!("arm {} is already moving", request.data.arm_id),
                ))
            }
        }
    })
    .await
{
    let busy = Arc::clone(&busy);
    tokio::spawn(async move {
        let arm_id = ctx.request().data.arm_id;
        ctx.complete(true, None, [98, 4, 26]).await.ok();
        // Release the arm so future goals for it are accepted again.
        busy.lock().unwrap().remove(&arm_id);
    });
}
```

### Failing a goal

A worker that cannot reach the end of its goal ends it with `fail`: a failure kind of the action and a message. A failed goal gives no result, so the client never reads a result that only reports the failure:

<Tabs>
  <TabItem label="Python">
```python
async def drive(ctx):
    plan = await plan_motion(ctx.request().data.desired_position)
    if plan is None:
        await ctx.fail(move_arm.FailureKind.ATTEMPT_FAILED, "no plan to the target")
        return
    await ctx.complete(True, None, plan.final_position)
```
  </TabItem>
  <TabItem label="Rust">
```rust
tokio::spawn(async move {
    let Some(plan) = plan_motion(ctx.request().data.desired_position).await else {
        ctx.fail(move_arm::FailureKind::AttemptFailed, "no plan to the target")
            .await
            .ok();
        return;
    };
    ctx.complete(true, None, plan.final_position).await.ok();
});
```
  </TabItem>
</Tabs>

A contract can declare kinds of its own, such as `unreachable` for "No plan to the target". The action of a node that implements the contract then gives them too: `FailureKind::Unreachable` in Rust, `FailureKind.UNREACHABLE` in Python.

### Handling cancellation

A worker reacts to a cancel for **its** goal via `ctx.cancel_signal()`, which resolves when the goal receives its cancel signal: a cancel request of its caller arrives for that `goal_id`, or [its sender is gone](#goals-that-end-with-their-sender). `ctx.cancel_cause()` tells which: `CancelCause::Caller` or `CancelCause::SenderGone` in Rust (`CancelCause::reason()` gives a reason in words), `"caller"` or `"sender_gone"` in Python (`ctx.cancel_reason()` gives a reason in words). Pair the signal with the goal's work and end the goal with `complete_cancelled`, its reason and its result:

<Tabs>
  <TabItem label="Python">
```python
async def drive(ctx):
    cancel_task = asyncio.ensure_future(ctx.cancel_signal())
    work_task = asyncio.ensure_future(run_arm(ctx.request().data.arm_id))
    done, pending = await asyncio.wait(
        [cancel_task, work_task], return_when=asyncio.FIRST_COMPLETED
    )
    for task in pending:
        task.cancel()

    if cancel_task in done:
        # This goal received its cancel signal; wind down and report it.
        await ctx.complete_cancelled(
            ctx.cancel_reason(), False, None, last_known_position
        )
    else:
        outcome = work_task.result()
        for position in outcome.steps:
            await ctx.publish_feedback(position)
        await ctx.complete(True, None, outcome.final_position)
```
  </TabItem>
  <TabItem label="Rust">
```rust
tokio::spawn(async move {
    tokio::select! {
        outcome = run_arm(ctx.request().data.arm_id) => {
            for position in outcome.steps {
                ctx.publish_feedback(position).await.ok();
            }
            ctx.complete(true, None, outcome.final_position).await.ok();
        }
        _ = ctx.cancel_signal() => {
            // This goal received its cancel signal; wind down and report it.
            let reason = ctx.cancel_cause().map_or("cancelled", |cause| cause.reason());
            ctx.complete_cancelled(reason, false, None, last_known_position)
                .await
                .ok();
        }
    }
});
```
  </TabItem>
</Tabs>

Cancellation is **auto-acknowledged** by the framework: the client's `cancel_goal` returns a typed `CancelState`: `Signalled` when a goal with that `goal_id` is in flight (the signal was delivered), `AlreadyTerminal` when it had already finished, or `Unknown`. `Signalled` means *delivered*, not *will stop*; a worker is free to ignore the signal and keep running. The worker decides the goal's fate: calling `complete_cancelled` (or `complete`, or `fail`) is what a subsequent `get_result` returns. Whichever end runs first wins; the framework closes this goal's feedback stream when the goal ends, so the client's `on_next_feedback_message` loop ends cleanly. The clean close is not the only way a stream ends: if the producer instance dies mid-goal, the client's loop ends with a producer-gone error instead (see [Receiving feedback](#receiving-feedback)). A goal's cancel never affects other concurrent goals.

A member that ends the goals of other clients, such as a `stop` that ends every running move, ends each of them with `complete_cancelled` and a reason of its own, such as `"stopped by a stop request"`. The clients of those goals read the reason with the `Cancelled` outcome.

### Goals that end with their sender

A goal ends when the process that sent it is gone, so no robot goes on for a client that is gone. Each client process advertises its presence, and each goal carries the presence of its sender. The action watches the sender of each goal. When the sender is gone and the **sender grace** of the action passed, each goal of that sender that did not end receives its cancel signal, with the cause `SenderGone` (`"sender_gone"` in Python). The worker then ends the goal with `complete_cancelled`, as for any other cancel.

The sender grace is zero unless the provider sets it. Set it when a client that stops and starts again within some time must find its goals still running, such as a robot initializer that attaches a robot to a simulation:

<Tabs>
  <TabItem label="Python">
```python
action = await move_arm.ActionHandle.expose(node_runner)
await action.set_sender_grace(5.0)  # seconds
```
  </TabItem>
  <TabItem label="Rust">
```rust
let action = move_arm::ActionHandle::expose(&node_runner).await?;
action.set_sender_grace(std::time::Duration::from_secs(5));
```
  </TabItem>
</Tabs>

The sender grace applies to each sender that is found gone after the call. A sender is found gone when its presence disappears and two probes confirm it.

### Firing a goal

The code generator creates a module for each consumed action under `peppygen::consumed_actions`.
Use `fire_goal` to send a goal, then listen for feedback and request the result:

<Tabs>
  <TabItem label="Python">
```python
import asyncio

from peppygen import NodeBuilder
from peppygen.consumed_actions.brain import move_arm


async def run(node_runner):
    # `one`: the accessor returns the slot's sole producer directly.
```

`fire_goal` requires the caller to pass one explicit target for every [cardinality](/advanced_guides/topics/#dependency-cardinality), including the default `one`; obtain it from the slot's cardinality-typed accessor (the singular, infallible `bound_producer()` on a `one` slot, the same name returning an `Option` on a `zero_or_one` slot, where a vacant slot has no target to fire at and the caller branches on that first, and `bound_producers()` on the multi cardinalities, never empty for `one_or_more`). The target must belong to the slot's own set; anything else fails with a runtime error before the goal reaches the wire. Firing a goal at every bound producer of a multi-cardinality slot is a plain loop over `bound_producers()`; each returned handle drives its own feedback stream, cancel, and result, exactly as a single goal does.

`fire_goal` returns an `ActionHandle`. Its `accepted` flag and its `refusal` are decoded from the framework goal ack: `refusal` is the `Failure` of a refused goal (`kind`, a [failure kind](#how-a-goal-ends) of the action, and `message`), and absent for an accepted goal. When the action declares a `response_message_format`, its `data` field holds the declared goal response of an accepted goal; a refused goal has none. The handle retains the selected target: goal submission, feedback, result retrieval, and cancellation all stay pinned to that same producer; no stage uses a wildcard, fallback producer, discovery, or automatic retargeting. The handle is what you use for subsequent feedback, result, and cancel calls. You can fire multiple goals concurrently, and each returns its own handle, so the server can drive them in parallel.

### Receiving feedback

Use `on_next_feedback_message` on the handle to receive feedback. The idiomatic pattern is a loop that drains feedback until a terminal error ends the stream:

<Tabs>
  <TabItem label="Python">
```python
import peppylib

while True:
    try:
        feedback = await action_handle.on_next_feedback_message()
        print(f"new_position={feedback.new_position}", flush=True)
    except ConnectionError:
        break  # producer instance died; get_result yields ABANDONED
    except peppylib.FeedbackOverflowError:
        break  # this caller fell behind its bound; the handle cancelled the goal
    except Exception:
        break  # the goal ended
```
  </TabItem>
  <TabItem label="Rust">
```rust
use peppygen::Error;

loop {
    match action_handle.on_next_feedback_message().await {
        Ok(feedback) => println!("new_position={:?}", feedback.new_position),
        Err(Error::ActionFeedbackProducerGone { .. }) => {
            break; // producer instance died; get_result yields Abandoned
        }
        Err(Error::ActionFeedbackOverflow { bound, .. }) => {
            // This caller fell behind by more than `bound` unread messages;
            // the handle cancelled the goal.
            println!("lost feedback beyond {bound} unread messages");
            break;
        }
        Err(_) => break, // the goal ended
    }
}
```
  </TabItem>
</Tabs>

Feedback the handle has not read yet waits in the handle's buffer. The buffer keeps **every** message until the handle reads it, up to the feedback bound that you pass to `fire_goal`: a number of unread messages, `DEFAULT_FEEDBACK_BOUND` (1024) in Rust, or `feedback_bound=None` for the same default in Python. The end of the stream is always kept. Receiving never waits for the handle: feedback read late, or never, does not hold up `get_result` or any other message to the node.

A handle that falls behind by more unread messages than its bound **overflows**: the buffer drops the unread messages and takes no message after them, and the handle cancels the goal itself. The next read gives the loss as an error, `ActionFeedbackOverflow` (`peppylib.FeedbackOverflowError` in Python), so a client never misses a feedback message without notice. Set a bound that holds every message your client can fall behind by, or read the feedback as it arrives.

Each goal has its own feedback stream, addressed by `goal_id`, so feedback for one goal never reaches another handle, even when several goals run concurrently on the same server. Three terminal errors end the drain loop:

- **Clean close** (`ActionFeedbackChannelClosed`; `RuntimeError` in Python): the server closed this goal's stream: its worker ended the goal (`complete`, `fail` or `complete_cancelled`) or abandoned it without an end (an early return or a panic). Call `get_result` to learn the outcome.
- **Producer gone** (`ActionFeedbackProducerGone`; `ConnectionError` in Python): the producer instance this goal is pinned to died without closing the stream (process killed, host lost). Feedback already in flight (including a clean close that did make it out) is drained first, so a graceful shutdown never surfaces as producer-gone. After this error, `get_result` resolves to the `Abandoned` outcome.
- **Overflow** (`ActionFeedbackOverflow`; `peppylib.FeedbackOverflowError` in Python): this caller fell behind its bound, and the handle cancelled the goal. `get_result` then gives the outcome the worker ended the goal with, usually `Cancelled`.

Either way, a client draining feedback always terminates rather than hanging. In Python, catch `ConnectionError` and `peppylib.FeedbackOverflowError` before the generic handler when you want to tell them from a clean close; a bare `except Exception` treats all three as end-of-stream.

:::note
Producer death is confirmed via liveliness probes, so a transport outage (e.g. a router restart) that outlasts the confirmation window can surface as producer-gone even though the process survived. The `Abandoned` outcome remains the correct consumer-side interpretation: the goal's results are unreachable.
:::

### Getting the result

Use `get_result` on the handle to request the final result. The call is routed to this goal by `goal_id` and **parks until the goal reaches a definitive terminal state**, then returns a typed outcome:

<Tabs>
  <TabItem label="Python">
```python
result = await action_handle.get_result(5.0)

if result.status == move_arm.ResultStatus.COMPLETED:
    print(f"completed at {result.data.final_position}", flush=True)
elif result.status == move_arm.ResultStatus.FAILED:
    print(
        f"failed: kind={result.failure.kind.value} message={result.failure.message}",
        flush=True,
    )
elif result.status == move_arm.ResultStatus.CANCELLED:
    print(
        f"cancelled ({result.cancel_reason}) at {result.data.final_position}",
        flush=True,
    )
elif result.status == move_arm.ResultStatus.ABANDONED:
    print("the worker abandoned the goal without producing a result", flush=True)
elif result.status == move_arm.ResultStatus.EXPIRED:
    print("the result expired before it was fetched", flush=True)
```
  </TabItem>
  <TabItem label="Rust">
```rust
let result = action_handle.get_result(Duration::from_secs(5)).await?;

match result.outcome {
    move_arm::ResultOutcome::Completed(data) => {
        println!("completed at {:?}", data.final_position)
    }
    move_arm::ResultOutcome::Failed(failure) => {
        println!("failed: kind={} message={}", failure.kind, failure.message)
    }
    move_arm::ResultOutcome::Cancelled { reason, data } => {
        println!("cancelled ({reason}) at {:?}", data.final_position)
    }
    move_arm::ResultOutcome::Abandoned => {
        println!("the worker abandoned the goal without producing a result")
    }
    move_arm::ResultOutcome::Expired => {
        println!("the result expired before it was fetched")
    }
}
```
  </TabItem>
</Tabs>

A poll on a still-running goal **parks** until the goal reaches a terminal state, then returns a typed outcome, so you can call `get_result` whenever you like; a forwarding/relaying node does not have to time its poll to the worker's lifecycle. The returned outcome (a Rust `ResultOutcome` enum, or `result.status` with `result.data`, `result.failure` and `result.cancel_reason` in Python) tells you exactly what happened:

- **`Completed`**: the worker delivered a result via `complete`; the goal is a success and the payload is in `data`.
- **`Failed`**: the worker ended the goal via `fail`; the `Failure` gives the kind and the message, and there is no result.
- **`Cancelled`**: the worker ended the goal via `complete_cancelled`; the outcome gives the `reason` (`cancel_reason` in Python), and the payload is in `data`.
- **`Abandoned`**: the worker dropped the goal without ever delivering a result (an early return or a panic), or the producer instance itself died mid-goal. A poll on a goal whose producer is confirmed gone resolves to `Abandoned` instead of parking forever.
- **`Expired`**: the goal finished, but its result was retained only for a bounded window (30&nbsp;s by default) that has since elapsed, or the result was already evicted.

A terminal result stays fetchable for that retention window, and you can fetch it more than once within it, which makes relaying it reliable. If the poll outlives the caller's own `timeout`, you get a normal timeout error like any other request.

### Cancelling a goal

Use `cancel_goal` on the handle to request cancellation of that specific goal. It returns a typed `CancelState`:

<Tabs>
  <TabItem label="Python">
```python
cancel_response = await action_handle.cancel_goal(5.0)

if cancel_response.state == move_arm.CancelState.SIGNALLED:
    print("cancel delivered to a live goal", flush=True)
elif cancel_response.state == move_arm.CancelState.ALREADY_TERMINAL:
    print("goal had already finished", flush=True)
elif cancel_response.state == move_arm.CancelState.UNKNOWN:
    print("no goal with that id is known", flush=True)
```
  </TabItem>
  <TabItem label="Rust">
```rust
let cancel_response = action_handle.cancel_goal(Duration::from_secs(5)).await?;

match cancel_response.state {
    move_arm::CancelState::Signalled => println!("cancel delivered to a live goal"),
    move_arm::CancelState::AlreadyTerminal => println!("goal had already finished"),
    move_arm::CancelState::Unknown => println!("no goal with that id is known"),
}
```
  </TabItem>
</Tabs>

The `CancelState` reports what the cancel found:

- **`Signalled`**: a live goal received the cancel signal. *Delivered*, not necessarily *will stop*: the worker may ignore it.
- **`AlreadyTerminal`**: the goal had already reached a terminal state, so there was nothing to cancel. This answer survives result eviction: a bounded tombstone set remembers terminal goals after their results are dropped.
- **`Unknown`**: no goal with that `goal_id` is known (it never existed, or its tombstone has aged out of the bounded set).

The cancel targets only this goal; other concurrent goals are unaffected. To learn the goal's final state, call `get_result`: if the worker reacted with `complete_cancelled` you get a `Cancelled` outcome with its reason; if it ignored the cancel and finished normally you get `Completed`.

## Bindings and routing

Routing for actions uses the same consumer-side model as topics and services. A binding `KEY: VALUE` creates a private channel from producer instance `VALUE` to one of the client's declared slots; the action server itself is binding-agnostic.

An action slot resolves through its bindings: the generated `fire_goal` checks the caller-selected target against the slot's bound set and pins the goal, cancel, result, and feedback channels to that one producer's full `(core_node, instance_id)` wire address. How many producers may be bound to the slot is its declared [cardinality](/advanced_guides/topics/#dependency-cardinality) (`one` when omitted); because the whole goal cycle needs exactly one server, every fired goal selects exactly one member of the bound set, and a `one` / `one_or_more` slot with no binding is rejected at launch validation, before anything spawns.

In a launcher / stack config:

```json5
{
  source: { name: "consumer:v1" },
  instances: [{
    instance_id: "my_consumer",
    links: { brain: "left-arm-1" },
  }],
}
```

or, when launching a single node during development:

```sh
peppy node run --link brain@left-arm-1 consumer:v1
```

### Worked example: `openarm01_backbone`

A client that wires two depth cameras to two dedicated slots:

```json5
// openarm01_backbone/peppy.json5
{
  manifest: {
    name: "openarm01_backbone",
    tag: "v1",
    depends_on: {
      contracts: [
        { name: "depth_camera", tag: "v1", link_id: "wrist_left_camera" },
        { name: "depth_camera", tag: "v1", link_id: "wrist_right_camera" },
      ],
    },
  },
  // ...
}
```

```json5
// peppy_launcher.json5
{
  deployments: [
    { source: { name: "depth_camera:v1" }, instances: [
      { instance_id: "left_cam" },
      { instance_id: "right_cam" },
    ]},
    { source: { name: "openarm01_backbone:v1" }, instances: [
      { instance_id: "backbone_inst_1", links: {
        wrist_left_camera: "left_cam",
        wrist_right_camera: "right_cam",
      }},
    ]},
  ],
}
```

Three contract statements follow from this manifest:

1. `fire_goal` on the nested `wrist_left_camera.<action>` (Python) / `wrist_left_camera::<action>` (Rust) module reaches `left_cam`.
2. `fire_goal` on the nested `wrist_right_camera.<action>` (Python) / `wrist_right_camera::<action>` (Rust) module reaches `right_cam`.
3. If the `wrist_right_camera` binding line were removed, validation would reject the launch (a declared slot has a binding, or a written vacancy where its cardinality is `zero_or_one`): a goal cycle has no wildcard fallback.

### Why an explicit single target?

Without a pinned target, a goal request would be broadcast to every matching producer and each one would execute the goal concurrently, which for state-changing actions (motor commands, file writes, payment dispatches) is a real-world hazard. Requiring every `fire_goal` to name one member of the slot's validated bound set removes that hazard by construction: the selected target carries the producer's full `(core_node, instance_id)` wire address, so the goal addresses exactly one producer with no probe round-trip, the goal, cancel, result, and feedback channels all stay on that producer for the whole goal cycle, and an out-of-set target (never checked by plan-time binding validation) is rejected before it reaches the wire. If the selected producer dies mid-cycle, the failure surfaces per stage: `fire_goal` and `cancel_goal` report `ServiceUnreachable`, `get_result` reports `ActionResultUnreachable` (or resolves the goal `Abandoned` once the producer is confirmed gone), and the feedback stream ends with `ActionFeedbackProducerGone`. The caller can retry once the producer is back: a producer dying never changes the bound set. On a `one_or_more` or `zero_or_more` slot a [copy joining or leaving](/guides/launch_files/#copies) does, so read `bound_producers()` at the point of use.

### Validator rules

The launcher validator runs these checks before the stack starts:

1. **Every `KEY` must name a declared slot, and every declared slot must resolve.** A binding whose `KEY` matches no `depends_on` `link_id` is rejected; there are no free-form keys. A declared `one` / `zero_or_one` / `one_or_more` slot with no `links` entry fails the launch before anything is spawned; a `zero_or_more` slot with no entry resolves to the empty set, and so does a `zero_or_one` slot the deployment declared vacant.
2. **The value's shape must match the slot's cardinality.** A scalar slot (`one` or `zero_or_one`) takes a scalar, a multi slot takes an array, an empty array meets only `zero_or_more`, and duplicate targets within one slot are rejected. Repeated `--link KEY@…` flags accumulate on a multi-slot and are a hard error on a scalar slot.
3. **Every target must satisfy the slot, checked per bound instance.** A target `instance_id` that deploys a different node than the slot expects (or one that does not implement the requested contract) is rejected.
4. **Stack-wide `instance_id` uniqueness.** Every `instance_id` must be unique across the entire stack, not just within a `(node_name, node_tag)` group. The `--link` syntax names producers by `instance_id`, so a duplicate would make the binding ambiguous.
5. **Bindings are stamped with the producer's `core_node`.** The wire addresses producers by the full `(core_node, instance_id)` pair; the validator stamps each target producer instance's resolved `core_node` into the binding (equal to the launching daemon's only in the single-machine case), preserving plan order, so generated calls address exactly the selected producer and never match on `instance_id` alone. Plan order is the launcher's array order, then the members each joined copy adds, in the order the copies joined (see [validator rule 5](/advanced_guides/topics/#validator-rules)).

## Concurrent processing

A single action server can drive many goals at once. The accept loop only waits
for the next goal; each accepted goal runs in its own spawned task with its own
`GoalContext`. The framework routes every cancel and result request to the right
goal by `goal_id`, and each goal has its own feedback stream, so goals never
interfere with one another.

This makes the "one server, many resources" pattern natural: include a
discriminator in the goal request (e.g. `arm_id` or `device_id`) and route to a
per-resource worker. Your goal handler is responsible for the concurrency
policy: accept goals to run them in parallel, or refuse a goal (with
`GoalDecision::refuse(kind, message)`) when its target resource is already busy. A
goal that is not accepted yields no `GoalContext` and cannot be cancelled or ended.
