Three CLI commands let you inspect and interact with any running node instance directly from your terminal or scripts, without writing code:

- `peppy node describe <instance>`: prints all interfaces, descriptions, and message formats.
- `peppy node call <instance> <member>`: calls a service or action and prints JSON output with structured exit codes.
- `peppy node echo <instance> <topic>`: streams topic messages as JSON lines until Ctrl+C.

Pass `--core-node <name>` to target a remote daemon instead of the local one.

## What the commands read

These commands read the **pinned documents** stored by the daemon when the node was added (never source files on disk):

- The node's `peppy.json5` manifest (including any `refine` array-length overrides).
- Every contract and pairing document referenced by that manifest, at the exact bytes used during codegen (with `name`, `tag`, and `sha256`). Re-add the node to pick up document edits.

This gives access to all exposed interfaces on the instance: implemented contract members (`manifest.implements`), native node members (no `link_id`), and topics emitted over [pairing](/advanced_guides/pairing/) slots.

## Naming a member

| Member source | Full name | Example |
| --- | --- | --- |
| Implemented contract | `<slot>.<member>` | `motion.move_arm` |
| Emitted pairing topic | `<slot>.<topic>` | `controller.joint_states` |
| Native node member | `<member>` | `set_depth_gain` |

You can omit `<slot>.` whenever the short name is unambiguous among the matching kind (`call` searches services and actions; `echo` searches topics). If a service and an action share the same full name, disambiguate with `--kind service` or `--kind action`.

## `peppy node describe`

```sh
peppy node describe arm_inst
```

The [description](/reference/concepts/#descriptions) of the node follows the first lines, and the description of each contract and pairing follows its heading, one paragraph at a time. Each member shows the full name that `call` and `echo` take, its description, its message formats with the `$description` of their fields, and the [failure kinds](/advanced_guides/actions/#how-a-goal-ends) of its contract that it lists. Every member can also give the failure kinds of peppy, which the listing does not repeat. The descriptions wrap to the width of the terminal. `--json` prints the same as one JSON document, for a program: the node and each contract and pairing have `description`, the list of their paragraphs, and each member has `description`.

## `peppy node call`

```sh
peppy node call arm_inst move_to --set 'joints=[0.1, 0.2, 0.3]'
```

### The message

Build the service request or action goal using three flags:

- `--args <file.json5>`: load the base message from a JSON5 file.
- `--set <field>=<value>`: set one field by dotted path (e.g., `--set pose.position.x=0.2`). String-encoded JSON types (`string`, `bytes`, `time`, `i64`/`u64`) take `<value>` literally; all other types parse `<value>` as JSON5.
- `--file <field>=@<path>`: populate a field from disk (UTF-8 text for `string`, raw bytes for `bytes`). Passing `@<directory>` populates a list of `{ path, content }` objects (sorted by relative path) for fields matching that schema.

`--set` and `--file` merge on top of `--args`, and setting the same field (or overlapping parent/child paths) twice is rejected. Encoding matches the MCP JSON schema: 64-bit integers are decimal strings (`--set count=18446744073709551615`), bytes are base64, and timestamps are RFC 3339 (`--set stamp=2026-10-25T10:00:00Z`). Contracts representing maps as JSON5-encoded strings also take `--set` literally (e.g., `--set roles='{ arm: "openarm" }'`). The CLI validates the message against the pinned manifest before sending and points directly to any mismatched field.

### The output

The command sends the call directly using the CLI process's sender identity, printing newline-delimited JSON to stdout and diagnostics to stderr:

- One `{"feedback": ...}` line per action feedback message.
- One final outcome line:

| `outcome` | Fields | Exit status |
| --- | --- | --- |
| `completed` | `response` (service) or `result` (action) | 0 |
| `refused` | `failure_kind`, `message` | 3 |
| `failed` | `failure_kind`, `message` | 4 |
| `cancelled` | `reason`, `result` | 5 |
| `abandoned` | `message` | 6 |
| `expired` | `message` | 7 |

```text
{"feedback":{"progress":0.5}}
{"feedback":{"progress":1.0}}
{"outcome":"completed","result":{"reached":true}}
```

- A service error reply maps to `outcome: "refused"` (exit `3`). A normal response whose payload happens to list errors (such as a validator) still exits `0`.
- If a provider returns an undeclared `failure_kind`, the CLI warns on stderr and still prints the outcome with its exit code.
- Local command errors (unknown instance/member, invalid message) print nothing to stdout and exit `1`. CLI syntax errors exit `2`.

### Ctrl+C

- **Action (1st Ctrl+C):** Sends a cancel to the provider and waits for the terminal outcome. If the goal cancels, it prints `cancelled` and exits `5` (including actions like `record_episode` where cancelling is the normal way to finish and save). If the goal already finished before the cancel arrived, it keeps that outcome.
- **Action (2nd Ctrl+C or process exit):** Exits immediately with `130`. Because the sender process is gone, the provider cancels the goal automatically.
- **Service (Ctrl+C):** Services cannot be cancelled; Ctrl+C exits immediately with `130`.

### Members that move a robot

For members marked `moves_robot` ([Marks](/advanced_guides/contract_implementation/#marks)), `peppy node call` enforces the same [fleet safety rules](/advanced_guides/fleet/) as an MCP server (acting under the caller's own identity, with no scope restrictions):

- Before sending, it calls `check_move` on the stack coordinator (discovered via the target daemon's stack listing when using `--core-node`). If refused, nothing is sent to the provider; it prints a `refused` line (`halted`, `leased`, or `not_leased`) and exits `3`.
- While a `moves_robot` action runs, it watches fleet `changes` and cancels the goal on any stack halt, waiting for the provider's terminal outcome.

## `peppy node echo`

```sh
peppy node echo arm_inst limb_states
```

```text
{"joints":[0.1,0.2,0.3]}
{"joints":[0.11,0.2,0.3]}
```

Prints each published topic message as one JSON line until Ctrl+C (exits `0`). It subscribes directly by topic key without requiring a launcher slot:

- **Contract or own topics:** Streams from that instance (replaying retained messages first if the topic uses `retention`).
- **Pairing topics:** Observes all active pairs on that slot (prints nothing until the instance pairs).

Messages that fail schema validation log a warning on stderr. Closing stdout (e.g., `| head -n 5`) exits cleanly with `0`. Slow terminals or downstream pipes never stall the publisher; unread oldest messages are dropped to keep up.

## Exit statuses of the other commands

Daemon-goal CLI commands (`peppy stack launch`, `build`, `join`, `remove`, `benchmark`; `peppy node add`, `build`, `run`; `peppy repo refresh`) use the same exit codes:

| Exit status | Meaning |
| --- | --- |
| 0 | Goal completed |
| 1 | Local CLI error (for example, a command timeout expired) |
| 2 | Invalid command-line arguments |
| 3 | Daemon refused the goal or returned a service error reply (for example, `leased` on a blocked join/remove) |
| 4 | Goal failed |
| 5 | Goal was cancelled |
| 6 | Daemon abandoned the goal |
| 7 | Goal result expired before the CLI read it |
| 130 | Interrupted by a second Ctrl+C while waiting, or by Ctrl+C between multi-step goals (e.g., `peppy node add --run`) |

Each goal command cancels on the first Ctrl+C and exits with the resulting outcome code (see [Stopping a stack command with Ctrl+C](/guides/launch_files/#stopping-a-stack-command-with-ctrlc)). Request-only commands (`peppy node stop`, `remove`, `init`, `sync`; `peppy repo add`, `list`, `exclude`, `remove`) exit `3` on a daemon error reply.
