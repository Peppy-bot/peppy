The `message_format` defines the structure of messages exchanged between nodes through [topics](/advanced_guides/topics/), [services](/advanced_guides/services/), and [actions](/advanced_guides/actions/).
It is a map of field names to schema types. A native interface entry declares it inline in `peppy.json5`; an entry that carries a `link_id` into a contract or pairing document takes its shape from that document instead, using the same syntax there, and an inline `message_format` on such an entry is rejected at parse time. Such an entry may pin the length of arrays the document leaves generic through a `refine` block; see [Refining the contract's generic arrays](/advanced_guides/contract_implementation/#refining-the-contracts-generic-arrays).

```json5
message_format: {
  temperature: "f32",
  label: "string",
}
```

Each field value is a **schema type**: either a bare type token, or a structured schema with modifiers.

:::note
A declared `message_format` holds at least one field. An endpoint that carries no payload omits the key entirely, and an empty `message_format: {}` is rejected when the config is parsed.
:::

---

## Primitive types

A bare type string is the simplest form. These map directly to language-native types.

| Type         | Rust type                 | Python type   |
|--------------|---------------------------|---------------|
| `"bool"`     | `bool`                    | `bool`        |
| `"u8"`       | `u8`                      | `int`         |
| `"u16"`      | `u16`                     | `int`         |
| `"u32"`      | `u32`                     | `int`         |
| `"u64"`      | `u64`                     | `int`         |
| `"i8"`       | `i8`                      | `int`         |
| `"i16"`      | `i16`                     | `int`         |
| `"i32"`      | `i32`                     | `int`         |
| `"i64"`      | `i64`                     | `int`         |
| `"f32"`      | `f32`                     | `float`       |
| `"f64"`      | `f64`                     | `float`       |
| `"string"`   | `String`                  | `str`         |
| `"bytes"`    | `Vec<u8>`                 | `bytes`       |
| `"time"`     | `std::time::SystemTime`   | `float`       |

One field name is reserved: `instance_id` is rejected anywhere in a `message_format`, at the root or nested, because peppy's transport metadata claims it.

## Optional modifier

A field with a presence bit on the wire can be made optional by using the structured form with `$optional`:

```json5
note: {
  $type: "string",
  $optional: true
}
```

| Field       | Required | Description                            |
|-------------|----------|----------------------------------------|
| `$type`     | Yes      | `string`, `bytes`, or `time` (arrays and objects take `$optional` in their own structured forms) |
| `$optional` | No       | When `true`, the field may be absent. Defaults to `false` |

Scalar-copy types (`bool`, the integer types, `f32`, `f64`) carry no presence bit, so an absent value is indistinguishable from a zero one: `$optional` on them is rejected when the config is parsed. Model an optional scalar as an optional `bytes`/`string` or restructure the message.

:::note
`$optional` can only be used on **root-level fields** of a `message_format`: direct children, not fields nested inside objects or array items. If a parent structure is present, all its fields must be present too.

In practice, this is used on **service and action response fields** where a value may or may not be present depending on the outcome; for example, a `note` that a response carries only for some requests. A message format never reports a failure: a refused or failed goal and the error reply of a service carry a [failure kind](/advanced_guides/actions/#how-a-goal-ends) and a message outside the message, so a response or a result is always a success.
:::

:::caution
`$optional` belongs to message formats only. Node parameters use [`$default`](/reference/parameters/#default-values) instead, which is a separate concept: a default value to fall back on when the runtime doesn't supply one.
:::

## Enum modifier

A `string` field can declare the closed set of strings that it holds, with `$enum`:

```json5
mode: {
  $type: "string",
  $enum: ["idle", "moving", "holding"]
}
```

| Field       | Required | Description |
|-------------|----------|-------------|
| `$type`     | Yes      | `string`. The parser refuses `$enum` on a field of another type |
| `$enum`     | Yes      | The strings of the set: at least one, each a non-empty string, each once, in the order you write them |
| `$optional` | No       | As on any `string` field |

An enum changes nothing on the wire and in the generated code: the field is a `string`. Peppy carries the set and acts on none of its values. A client that checks the values of a field, such as a checker of documents, reads the set through the [codec API](/advanced_guides/codec_api/).

## Marks modifier

A field can carry marks, names that the document gives to the field, with `$marks` in the structured form of the field. A mark tells a client what the field holds, for example the id of an item:

```json5
target: {
  $type: "object",
  item: { $type: "string", $marks: ["item_id"] },
  pose: { $type: "array", $items: "f64", $length: 7, $marks: ["pose"] }
}
```

| Field    | Required | Description |
|----------|----------|-------------|
| `$marks` | No       | The marks of the field: at least one, each once. Leave the key out for a field with no mark. A primitive, an array and an object take it in their structured forms |

A mark name is 1 to 64 lowercase ASCII letters, digits and `_`: words that each start with a letter, joined by one `_`, such as `item_id` or `pose2d`. Marks change nothing on the wire and in the generated code. Peppy keeps each mark of a field as written and acts on none: each client defines the marks that it reads, and reads them through the [codec API](/advanced_guides/codec_api/). A member of a contract carries [marks](/advanced_guides/contract_implementation/#marks) too.

## Description modifier

A field can say what it holds with `$description` in the structured form of the field. A primitive, an array and an object take it. On an array it sits beside `$items`, and on an object beside the keys of the fields:

```json5
message_format: {
  speed: { $type: "f64", $description: "The speed of the base, in meters per second." },
  target: {
    $type: "object",
    $description: "The point to go to, in the frame of the map.",
    x: "f64",
    y: "f64"
  },
  path: {
    $type: "array",
    $description: "The points on the way to the target, in order.",
    $items: { $type: "object", x: "f64", y: "f64" }
  }
}
```

| Field          | Required | Description |
|----------------|----------|-------------|
| `$description` | No       | What the field holds: one string that is not blank. Leave the key out for a field with no description |

A description changes nothing on the wire and in the generated code, and peppy reads no rule from it. The [codec API](/advanced_guides/codec_api/) gives it, [`peppy node describe`](/advanced_guides/calling_instances/#peppy-node-describe) prints it in each message format, and the [MCP server](/advanced_guides/mcp/#the-published-schemas) publishes it as the `description` of the property. A document and its members have descriptions of their own, which are required (see [Descriptions](/reference/concepts/#descriptions)).

## Object

An object groups related fields into a nested structure. It generates a nested struct in Rust and a dataclass in Python.

```json5
header: {
  stamp: "time",
  frame_id: "u32"
}
```

| Field       | Required | Description                                   |
|-------------|----------|-----------------------------------------------|
| `$type`     | No       | Only valid value is `"object"`. Can be omitted since the parser infers it from the structure |
| `$optional` | No       | When `true`, the entire object may be absent  |
| *other keys*| No       | Each additional key is a field with its own schema type |

Object fields can be any schema type, including arrays and nested objects:

```json5
sensor_reading: {
  $type: "object",
  header: {
    $type: "object",
    stamp: "time",
    frame_id: "u32"
  },
  samples: {
    $type: "array",
    $items: "f32"
  }
}
```

## Array

An array represents a list of items of the same type.

```json5
distances: {
  $type: "array",
  $items: "f32"
}
```

| Field       | Required | Description                                         |
|-------------|----------|-----------------------------------------------------|
| `$type`     | Yes      | Must be `"array"`                                   |
| `$items`    | Yes      | A primitive type or an object schema. Nested arrays (arrays of arrays) are not supported |
| `$length`   | No       | Fixed number of elements. Only supported when `$items` is a numeric or boolean primitive (not supported for `string`, `bytes`, `time`, or object items). Omit for variable-length; a node implementing or consuming the document may then pin it through its entry's `refine` block |
| `$optional` | No       | When `true`, the entire array may be absent          |

### Fixed-length array

When `$length` is provided, the array has an exact number of elements:

```json5
position: {
  $type: "array",
  $items: "f32",
  $length: 3
}
```

This maps to `[f32; 3]` in Rust and `list[float]` in Python, where the generated code raises a `ValueError` when a list of any other length is encoded or decoded.

### Variable-length array

Without `$length`, the array can contain any number of elements:

```json5
frame: {
  $type: "array",
  $items: "u8"
}
```

This maps to `Vec<u8>` in Rust and `bytes` in Python (for `u8` items) or `list[T]` for other types.

### Array of objects

`$items` can be an object, allowing arrays of structured records:

```json5
frames: {
  $type: "array",
  $items: {
    $type: "object",
    name: "string",
    parent: "string",
    position: {
      $type: "array",
      $items: "i32",
      $length: 3
    },
    orientation: {
      $type: "array",
      $items: "i32",
      $length: 4
    }
  }
}
```

This accepts messages like:

```json
{
  "frames": [
    { "name": "link1", "parent": "world", "position": [0, 0, 1], "orientation": [1, 0, 0, 0] },
    { "name": "link2", "parent": "link1", "position": [0, 1, 0], "orientation": [1, 0, 0, 0] }
  ]
}
```

## Nesting rules

Schema types can be nested arbitrarily:

- **Object fields** can be primitives, arrays, or other objects
- **Array items** can be primitives or objects (nested arrays are not supported)

This enables complex hierarchical message structures. For example, a robotics transform tree:

```json5
message_format: {
  timestamp: "time",
  root_frame: "string",
  transforms: {
    $type: "array",
    $items: {
      $type: "object",
      name: "string",
      parent: "string",
      translation: { $type: "array", $items: "f64", $length: 3 },
      rotation: { $type: "array", $items: "f64", $length: 4 }
    }
  }
}
```

## Complete example

A full `peppy.json5` topic using multiple schema types:

```json5
{
  peppy_schema: "node/v1",
  manifest: {
    name: "arm_controller",
    tag: "v1",
    description: ["The controller of a six-joint arm with a gripper: it publishes the state of the arm."]
  },
  execution: {
    language: "rust",
    run_cmd: ["./target/release/arm_controller"],
  },
  interfaces: {
    topics: {
      emits: [
        {
          name: "arm_state",
          description: "The joints and the end effector of the arm, at each control step.",
          qos_profile: "sensor_data",
          message_format: {
            timestamp: { $type: "time", $description: "The time of the measure." },
            joint_positions: { $type: "array", $items: "f64", $length: 6 },
            joint_velocities: { $type: "array", $items: "f64", $length: 6 },
            end_effector: {
              $type: "object",
              position: { $type: "array", $items: "f64", $length: 3 },
              orientation: { $type: "array", $items: "f64", $length: 4 },
              gripper_open: "bool"
            }
          }
        }
      ]
    }
  }
}
```
