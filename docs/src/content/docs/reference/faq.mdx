<details>
<summary>What languages does Peppy support?</summary>

Peppy supports Rust and Python. The daemon and tooling are built in Rust; nodes in either language use the same `peppy.json5` interfaces through the generated `peppygen` code and the `peppylib` runtime.

</details>

<details>
<summary>What tech are you using under the hood?</summary>

Peppy is written in [Rust](https://rust-lang.org/). Nodes communicate over [Zenoh](https://zenoh.io/), messages are encoded with [Cap'n Proto](https://capnproto.org/), and container nodes run on [Apptainer](https://apptainer.org/) (with Lima providing the Linux VM on macOS).

</details>

<details>
<summary>Can Peppy instances on different machines communicate with each other?</summary>

Yes. Core nodes connect into a unified network through [federation](/advanced_guides/federation/): each core node manages its own machine, and a single launch can place nodes across machines, with the coordinator resolving every deployment once and the other machines running exactly what it resolved. Machines join the same network by enrolling in the same project with [`peppy platform enroll`](/advanced_guides/platform/).
</details>

<details>
<summary>Will Peppy maintain backward compatibility?</summary>

Not until version 1.0. Since Peppy is still in alpha/beta, maintaining backward compatibility would introduce additional complexity and divert effort away from core development.

</details>

<details>
<summary>Any plans to make Peppy compatible with Windows?</summary>

No. Official support is limited to Linux (x86_64 and ARM64) and macOS (Apple Silicon).
</details>

<details>
<summary>Is Peppy free to use?</summary>

Yes. Peppy is open source under the [Apache License, Version 2.0](https://www.apache.org/licenses/LICENSE-2.0), the same license as ROS 2. You can use, modify and distribute it for free, including in a commercial product or service.
Alongside the open code, the [Peppy platform](/advanced_guides/platform/) lets you sign in and enroll a machine in a project with `peppy platform login`, and watch your machines with `peppy platform peers` (the peers of a project's cloud router) and `peppy platform status` (this machine's enrollment and the state of its router link).

</details>

<details>
<summary>My launch failed with an error that looks unrelated to what I changed. Where do I start?</summary>

Run `peppy repo list` on the machine where you submitted the launch first.

- **Default repositories** are pinned to your installed Peppy release (`peppy-release/<version>`), so their content only changes when you upgrade or downgrade Peppy.
- **Branch-tracked repositories** move whenever you run `peppy repo refresh`, so upstream merges can change your launch without a Peppy upgrade.
- **Federated launches** always resolve from the submitting machine's caches and push pinned bytes to the other machines. Stale or different caches on remote machines never affect what runs.
- **Duplicate identities** inside one repository are caught at publish time: `peppy repo index` rejects duplicate `name:tag` entries and names both manifests.

See [When a repository fails](/advanced_guides/repositories/#when-a-repository-fails) for details.

</details>

<details>
<summary>Why is <code>peppy repo refresh</code> reporting repositories it could not update, and can I still work?</summary>

Yes, in most cases you can keep working. Refresh failures are isolated to the failing repository:

- All other repositories refresh normally.
- The failing repository **keeps its last valid entries**, so existing launches continue to work.
- The command still succeeds, lists every failing repository in one summary, and prompts you to retry `peppy repo refresh`.

Check the failure reason in the output:

- **`unreachable`**: Peppy could not read the repository (network outage, invalid ref, unmounted path, or missing committed `peppy_repository.json5`). For a missing index, run `peppy repo index` in that repository and commit the file.
- **`conflict`**: Peppy read the repository, but its committed index is invalid or contradicts the files in the tree. The error message names the files to fix.

`peppy repo list` marks retained entries with `[retained, last read <date>]`. Keep an eye on that date so you do not silently run weeks-old content.

If a machine has never read that repository successfully, there are no cached entries to fall back to. Excluding the repository removes all items it provides until the repository is fixed.

</details>

<details>
<summary>What does Ctrl+C do while a <code>peppy</code> command waits for the daemon?</summary>

Long-running CLI commands (`peppy stack launch`, `build`, `join`, `remove`, `benchmark`; `peppy node add`, `build`, `run`; `peppy repo refresh`) each track a goal on the daemon.

| Press | What happens | Exit code |
| --- | --- | --- |
| **1st Ctrl+C** | Sends a cancel request to the daemon. The daemon stops at the current step and cleans up (a cancelled launch clears the stack; a cancelled join rolls back). The CLI waits for cleanup to finish (bounded only by its max timeout) and reports the outcome. | `5` (cancelled), `0` (already completed), or `4` (failed). Chained commands like `peppy node add --run` always exit `130` and skip remaining steps. |
| **2nd Ctrl+C** | Stops waiting for cleanup once the cancel reaches the daemon (cleanup continues in the background). | `130` |
| **3rd Ctrl+C** | Terminates the CLI immediately. | `130` |

Closing the terminal or killing the CLI process also triggers daemon-side cancellation.

**Timeouts:** Each command runs a client-side watchdog. If the daemon sends no output past the watchdog window, the CLI exits with code `1`, which causes the daemon to cancel the goal. Stack commands also pass per-phase idle budgets to the daemon (such as `--node-add-idle-timeout-secs`); exceeding one fails the goal with failure kind `timeout`.

See [Stopping a stack command with Ctrl+C](/guides/launch_files/#stopping-a-stack-command-with-ctrlc), [When a node command ends early](/guides/node_stack/#when-a-node-command-ends-early), and [Exit statuses of the other commands](/advanced_guides/calling_instances/#exit-statuses-of-the-other-commands).

</details>
