[ROS 2](https://docs.ros.org/en/lyrical/About-ROS.html) is an open-source framework of tools and libraries for robot applications. If you already know ROS 2, this page maps familiar ROS 2 concepts to their Peppy equivalents and compares the two across eleven core workflows.

All ROS 2 links refer to the Lyrical Luth distribution.

## The graph

**ROS 2.** Nodes create publishers and subscriptions at runtime in code (for example, `create_publisher` in [Writing a simple publisher and subscriber (Python)](https://docs.ros.org/en/lyrical/ROS-Framework/client-libraries/Working-with-Client-Libraries/Writing-A-Simple-Py-Publisher-And-Subscriber.html#write-the-publisher-node)). [Discovery](https://docs.ros.org/en/lyrical/ROS-Framework/About-Nodes.html#discovery) connects nodes dynamically after startup. You inspect the live graph with `ros2 node list` or `rqt_graph` (see [Understanding ROS 2 Topics](https://docs.ros.org/en/lyrical/ROS-Framework/interfaces/topics/Understanding-ROS2-Topics/Understanding-ROS2-Topics.html)), assisted by the [ROS 2 Daemon](https://docs.ros.org/en/lyrical/Developer-Tools/Introspection-and-analysis/About-Command-Line-Tools.html#ros-2-daemon-background-discovery-service) cache.

**Peppy.** Each machine's daemon owns a [node stack](/reference/concepts/#node-stack): a directed acyclic graph built from `depends_on.nodes` declarations in `peppy.json5`, not from runtime code. Edges are validated when nodes are added, before any instance starts. `peppy stack list` prints each daemon's nodes, instance bindings, and dependencies (or JSON with `--json`). [Contract](#contracts) dependencies do not add static graph edges; `peppy stack list` shows them as explicit instance bindings.

## Interfaces and errors before the start

**ROS 2.** `.msg`, `.srv`, and `.action` files define message types only (see [Interface specifications](https://docs.ros.org/en/lyrical/ROS-Framework/interfaces/Working-with-interfaces/Interface-specifications.html)), built via `CMakeLists.txt` and `package.xml` ([Custom ROS 2 interfaces](https://docs.ros.org/en/lyrical/ROS-Framework/client-libraries/Working-with-Client-Libraries/Custom-ROS2-Interfaces.html)). Topic names are strings in node code. Because topics can have zero publishers ([Topics](https://docs.ros.org/en/lyrical/ROS-Framework/interfaces/About-Topics.html#publish-subscribe)), a misspelled topic name silently fails at runtime and receives no messages.

**Peppy.** `peppy.json5` is the single source of truth for a node's identity, interfaces, parameters, and build/run commands ([Node](/reference/concepts/#node)). `peppy node sync` generates typed Rust or Python modules for every interface ([Publishing messages](/advanced_guides/topics/#publishing-messages)), so node code never writes raw topic strings. Consumers declare sources in `depends_on`, and Peppy validates that every dependency exists and exposes the required interfaces before any instance starts ([How dependencies work](/reference/concepts/#how-dependencies-work)).

## Running and testing one node alone

**ROS 2.** `ros2 run` launches an executable containing one or more nodes ([Node management](https://docs.ros.org/en/lyrical/ROS-Framework/About-Nodes.html#node-management)), debuggable via `--prefix 'gdb -ex run --args'` ([Getting Backtraces in ROS 2](https://docs.ros.org/en/lyrical/Developer-Tools/Debugging/Getting-Backtraces-in-ROS-2.html)). Integration tests use `launch_testing` ([Integration testing](https://docs.ros.org/en/lyrical/Developer-Tools/Debugging/Testing/Integration.html)), where you write mock publisher/subscriber nodes by hand and synchronize with helpers like `WaitForTopics`.

**Peppy.** In standalone mode, a node runs directly with `cargo run` or `uv run <node>` under any IDE or debugger while still talking to the live stack ([Debugging a node](/guides/standalone_node/#debugging-a-node)).

For automated tests, `peppy node sync` generates typed mocks for every dependency and an in-process test harness ([What sync generates](/advanced_guides/testing/#what-sync-generates)). Pass `-r` to resolve dependencies from repositories without adding them to the stack ([Syncing against repositories](/advanced_guides/repositories/#syncing-against-repositories)). Tests run with no daemon, no external binaries, and no sleeps: startup uses deterministic readiness barriers ([A first test](/advanced_guides/testing/#a-first-test)).

## Build tools

**ROS 2.** Uses its own build system (`ament`) and workspace tool (`colcon`) across CMake and setuptools packages ([Creating a package](https://docs.ros.org/en/lyrical/ROS-Framework/client-libraries/Working-with-Client-Libraries/Creating-Your-First-ROS2-Package.html#what-is-a-ros-2-package), [Colcon tutorial](https://docs.ros.org/en/lyrical/ROS-Framework/client-libraries/Working-with-Client-Libraries/Colcon-Tutorial.html#build-the-workspace)). You build the workspace with `colcon build`, source `install/local_setup.bash`, and run with `ros2 run`.

**Peppy.** Has no custom build system. Nodes are standard language projects (`cargo` for Rust, `uv` for Python, or any tool such as `pip`, `poetry`, or `pixi` by adding the generated `.peppy/libs/peppygen` and `peppylib` paths). `peppy.json5` specifies `build_cmd` and `run_cmd` ([Execution](/reference/concepts/#execution)). `peppy node build` runs `build_cmd` and caches the artifact; `peppy node run` executes `run_cmd`. [Container nodes](/advanced_guides/containers/) build through an Apptainer definition file instead of `build_cmd`.

## Several machines

**ROS 2.** Nodes on the same network with the same `ROS_DOMAIN_ID` discover each other automatically ([Discovery](https://docs.ros.org/en/lyrical/ROS-Framework/About-Nodes.html#discovery)). However, ROS 2 launch files do not support ROS 1's `machine` tag ([Migrating Launch Files](https://docs.ros.org/en/lyrical/Migration-and-Upgrades/Migrating-from-ROS1/Migrating-Launch-Files.html#machine)), so you start launch files separately on each machine ([Security on Two](https://docs.ros.org/en/lyrical/Developer-Tools/Launch/Security/Security-on-Two.html#launch-the-nodes)).

**Peppy.** Launchers declare logical machine placeholders (`core_nodes`) instead of hostnames ([Core node links](/advanced_guides/federation/#core-node-links)). Run `peppy platform login` once on each machine to enroll it in the same project ([Signing in](/advanced_guides/platform/#signing-in)), then launch the entire distributed stack with one command:

```sh
peppy stack launch --place robot_onboard@self \
                   --place cloud_inference@cn-atlas-h100 \
                   split_compute_manipulation
```

Pass `--local` to run the same multi-machine launcher on one workstation with no file edits ([Developing without a second machine](/advanced_guides/federation/#developing-without-a-second-machine)). You can also federate without the Peppy platform using your own Zenoh router ([Federation outside the Peppy platform](/advanced_guides/platform/#federation-outside-the-peppy-platform)).

## Contracts

**ROS 2.** Topics are anonymous: any publisher and subscriber sharing a topic name and message type connect automatically ([Topics](https://docs.ros.org/en/lyrical/ROS-Framework/interfaces/About-Topics.html#anonymous)), making publishers swappable by convention. Interface files define message types only, not topic, service, or action names.

**Peppy.** A [contract](/advanced_guides/contract_implementation/#1-the-contract-document) is a standalone document bundling named topics, services, and actions under a `name:tag`. Producers explicitly declare `manifest.implements` and cover every member ([Producer](/advanced_guides/contract_implementation/#2-a-producer-that-implements-the-contract)); consumers declare `depends_on.contracts` ([Consumer](/advanced_guides/contract_implementation/#3-a-consumer-that-depends-on-the-contract)). The launcher wires a specific implementing instance to the consumer slot, and Peppy rejects any non-implementing instance before startup. Direct node dependencies (`depends_on.nodes`) remain available when you do not need abstraction.

## Simulation and real hardware with one launcher

**ROS 2.** Launch files toggle between simulation ([Simulation](https://docs.ros.org/en/lyrical/Capabilities/About-Simulation.html)) and hardware using launch arguments (`DeclareLaunchArgument` / `<arg>`) paired with conditional checks (`IfCondition` / `if`) ([Using substitutions](https://docs.ros.org/en/lyrical/Developer-Tools/Launch/Using-Substitutions.html)).

**Peppy.** Launchers declare **component axes**: named slots with swappable options (such as `mujoco`, `isaac_sim`, or `real`) ([Swapping parts at launch time](/guides/launch_files/#swapping-parts-at-launch-time)). Each axis declares `provides` (the instance IDs every option defines) so links remain valid across swaps. Select options at launch time with `--with <option>`, as in the [Quickstart](/quickstart/#step-2-launch-the-simulated-robot): `peppy stack launch openarm_simulation --with mujoco`.

## MCP

**ROS 2.** Does not ship a built-in [Model Context Protocol (MCP)](https://modelcontextprotocol.io) server ([CLI tools](https://docs.ros.org/en/lyrical/Developer-Tools/Introspection-and-analysis/About-Command-Line-Tools.html#usage), [Related projects](https://docs.ros.org/en/lyrical/Integrations-and-related/Related-Projects.html)); you integrate third-party bridges separately.

**Peppy.** Includes an MCP server inside the `peppy` binary. An [exposure document](/advanced_guides/mcp/) acts as a strict allowlist mapping contract members to MCP primitives: topics to resources, services to tools, and actions to action-backed tools or MCP tasks ([What an exposure publishes](/advanced_guides/mcp/#what-an-exposure-publishes)). Add the exposure to a launcher and the daemon serves it automatically ([Deploy it](/advanced_guides/mcp/#deploy-it)). Anything not listed in the exposure stays private.

## The first run of a robot stack that another team made

**ROS 2: 7 steps with 4 tools (`git`, `rosdep`, `colcon`, and `ros2`).** Steps follow [Creating a workspace](https://docs.ros.org/en/lyrical/ROS-Framework/client-libraries/Working-with-Client-Libraries/Creating-A-Workspace/Creating-A-Workspace.html#tasks) and [Launching multiple nodes](https://docs.ros.org/en/lyrical/ROS-Framework/nodes/Working-with-nodes/Launching-Multiple-Nodes/Launching-Multiple-Nodes.html).

<Steps>
1. Install ROS 2, `colcon`, `git`, and `rosdep` ([Installation](https://docs.ros.org/en/lyrical/Get-Started/Installation.html)).
2. Source the ROS 2 environment: `source /opt/ros/<distro>/setup.bash`.
3. Create a workspace and clone the source: `mkdir -p ~/ros2_ws/src && cd ~/ros2_ws/src && git clone <repository>`.
4. Install package dependencies: `rosdep install -i --from-path src --rosdistro <distro> -y`.
5. Build the workspace: `colcon build`.
6. Open a new terminal, source ROS 2 again, and source `install/local_setup.bash`.
7. Start the stack: `ros2 launch <package> <launch file>`.
</Steps>

**Peppy: 2 steps with 1 tool (`peppy`).** For launchers in the default repositories ([Quickstart](/quickstart/)):

<Steps>
1. Install Peppy: `curl -fsSL https://peppy.bot/install.sh | sh`. This installs the CLI, registers the daemon, and indexes the default repositories ([Installation](/guides/installation/)).
2. Launch by name: `peppy stack launch <launcher>` ([Launching from a repository](/guides/launch_files/#launching-from-a-repository)). Peppy fetches, builds, and starts all nodes in dependency order.
</Steps>

For a third-party Git repository (containing a committed `peppy_repository.json5`), register it once first with `peppy repo add <repository>` and `peppy repo refresh` ([Add a repository](/advanced_guides/repositories/#add-a-repository)). Non-container nodes require their build tool (`uv`, `cargo`, etc.) installed on the host.

## A new message between two nodes

**ROS 2: 5 steps** ([Creating custom msg and srv files](https://docs.ros.org/en/lyrical/ROS-Framework/client-libraries/Working-with-Client-Libraries/Custom-ROS2-Interfaces.html#tasks)):

<Steps>
1. Add a `.msg` file inside the `msg/` directory of an `ament_cmake` interface package.
2. Add `find_package(rosidl_default_generators REQUIRED)` and `rosidl_generate_interfaces(...)` to `CMakeLists.txt`.
3. Add `rosidl_default_generators`, `rosidl_default_runtime`, and `rosidl_interface_packages` entries to `package.xml`.
4. Build with `colcon build --packages-select <interface_pkg>`.
5. Source `install/setup.bash` in a new terminal.
</Steps>

Then add the interface package to each consumer's `package.xml` and rebuild ([Test the new interfaces](https://docs.ros.org/en/lyrical/ROS-Framework/client-libraries/Working-with-Client-Libraries/Custom-ROS2-Interfaces.html#test-the-new-interfaces)).

**Peppy: 2 steps** ([Writing your first node](/guides/first_node/#writing-your-first-node)):

<Steps>
1. Declare the topic and its `message_format` under `interfaces.topics.emits` in the producer's `peppy.json5`.
2. Run `peppy node sync` in the node directory to generate the typed code.
</Steps>

On the consumer side, add the producer to `depends_on.nodes` and the topic to `interfaces.topics.consumes`, then run `peppy node sync` (or `peppy node sync -r` to read from repositories) ([Consuming a topic](/advanced_guides/topics/#consuming-a-topic)).

## The tools that build, run and test one node in Python

**ROS 2: `ament` and `colcon`.** Requires `package.xml`, `setup.py`, `setup.cfg`, a `resource/` marker file, and a package directory inside a workspace ([What makes up a ROS 2 package?](https://docs.ros.org/en/lyrical/ROS-Framework/client-libraries/Working-with-Client-Libraries/Creating-Your-First-ROS2-Package.html#what-makes-up-a-ros-2-package)):

<Steps>
1. **Build**: `colcon build` from the workspace root.
2. **Run**: source ROS 2 and `install/local_setup.bash`, then `ros2 run <package> <node>`.
3. **Test**: `colcon test` ([Python testing](https://docs.ros.org/en/lyrical/Developer-Tools/Debugging/Testing/Python.html)).
</Steps>

**Peppy: standard Python tools.** `peppy node init --toolchain uv` creates a normal `uv` project with a `peppy.json5`, and `peppy node sync` generates its local bindings ([Project structure](/guides/first_node/#project-structure)). Run everything from the node directory:

<Steps>
1. **Build**: `uv sync --no-editable` (the same command listed in `peppy.json5`).
2. **Run standalone**: `uv run <node>` ([Debugging a node](/guides/standalone_node/#debugging-a-node)).
3. **Test**: `uv run --group dev pytest` ([A first test](/advanced_guides/testing/#a-first-test)).
</Steps>

Rust nodes follow the same pattern with `cargo build --release`, `cargo run`, and `cargo test`. When running inside the stack, `peppy node build` and `peppy node run` invoke the commands declared in `peppy.json5`.
