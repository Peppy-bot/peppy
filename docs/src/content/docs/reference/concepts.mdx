## Node

A **Node** is the fundamental unit of computation in Peppy. It represents a runnable application or service that can expose interfaces (topics, services, actions) and consume interfaces from other nodes.

A node is defined by its **configuration** file (`peppy.json5`) which includes:

- **`peppy_schema`**: The schema identifier, always `"node/v1"`
- **Manifest**: The node's identity and its description
- **Execution**: Commands to build and run the node, plus the parameters it accepts
- **Interfaces**: What the node exposes and consumes (optional; a node with no interfaces omits it)
- **Framework**: the restart policy, a knob peppy reads the same way for every node (optional)

### Manifest

The manifest defines a node's identity:

| Field | Description |
|-------|-------------|
| `name` | A validated identifier (ASCII letters, digits, `_`, `-`) |
| `tag` | A short contract identifier (e.g., `v1`, `donut`). Must start with an ASCII letter; allowed chars are letters, digits, `_`, `-`. Dots are forbidden. |
| `description` | What the node does and what it needs to run, as a list of paragraphs. The first paragraph is the summary. Required; see [Descriptions](#descriptions) |
| `labels` | Optional metadata labels |
| `implements` | Optional list of contracts this node implements, making it eligible to fill contract slots; see [Contract implementation](/advanced_guides/contract_implementation/) |
| `depends_on` | Optional dependency declarations, in five lists: `nodes`, `contracts`, `daemon`, `pairings`, and `pairing_observers`; see [Contract implementation](/advanced_guides/contract_implementation/), [Daemon targets](/advanced_guides/core_node_functions/#daemon-targets) and [Pairing](/advanced_guides/pairing/) |

A node is uniquely identified by its `name:tag` combination.

Tags are **not** semver. Bumping a tag always means "incompatible with the previous one": there is no notion of a backward-compatible patch or minor release. Pick a label that identifies the contract (`v1`, `v2`, `donut`), not a version number.

### Execution

The execution section defines how to prepare and launch the node:

| Field | Description |
|-------|-------------|
| `language` | The programming language of the node (`rust`, `python`) |
| `parameters` | Optional parameter schema for runtime configuration |
| `build_cmd` | Command to run during the node build phase |
| `run_cmd` | Command to launch the node |
| `container` | Optional container configuration. Exactly one of `run_cmd` or `container` must be present; a container node's build goes through the container image, so `build_cmd` is not used |
| `endpoints` | Optional map of the sockets the node binds during setup, keyed by label (lowercase letters, digits and underscores, starting with a letter). Each entry declares a `kind`, `page` for a URL opened in a browser or `mcp` for one an MCP client attaches to, and a non-empty `description`. The node announces the socket it bound under each label, and the daemon reports the URLs; a declared label that setup never announces fails the start |
| `setup_timeout_secs` | Optional setup budget of the node: how long the daemon waits for its setup to end once the node answers ready, a whole number of seconds from 1 to 540. Without it, the default setup budget of 15 seconds applies. The node reads its budget at run time; see [How an instance starts](/guides/node_stack/#how-an-instance-starts) |

### Framework

The `framework` block holds framework knobs peppy reads the same way for every node; a launcher writes `restart` under the same key.

| Field | Description |
|-------|-------------|
| `restart` | Optional: what the daemon does when the instance's process exits on its own or stops answering health checks, `never`, `on_failure` or `always`, or `{ policy, max_restarts }`, where `max_restarts` caps the restart attempts in a row, failed starts included, and the next exit or failed start past them leaves the instance `failed`. Under `on_failure` or `always` the daemon also kills an instance that stops answering health checks and treats that exit as a failure (the rule and its outage guard are in [Instance health and lifecycle](/guides/node_stack/#instance-health-and-lifecycle)). A launcher's instance entry, an adjustment or `--restart` on `peppy node run` or `peppy node add --run` wins over this value, which wins over the launcher root's; with none declared the policy is `on_failure`. See [Restart policy](/guides/launch_files/#restart-policy) |

### Interfaces

Nodes communicate through three types of interfaces:

| Type | Description |
|------|-------------|
| **Topic** | Publish/subscribe messaging for streaming data |
| **Service** | Request/response communication for synchronous calls |
| **Action** | Long-running tasks with feedback and cancellation support |

A node can **expose** interfaces (make them available to others) and **consume** interfaces from other nodes.

Three higher-level constructs build on these: [contract implementation](/advanced_guides/contract_implementation/), where the contract lives in a standalone document and any implementing producer can fill the consumer's slot; [pairing](/advanced_guides/pairing/), an exclusive 1:1 bidirectional topic exchange between two instances; and [observer slots](/advanced_guides/pairing/#observers-watching-a-pairing-without-joining-it), read-only taps on one role of an existing pairing. See [Choosing a communication pattern](/advanced_guides/communication_patterns/) for how to pick between all of them.

## Descriptions

A contract, a pairing, a node and a launcher give their meaning as data, in their **descriptions**. The people who choose a document read them, and so do the programs and the models that call its members.

| Part | Key | Rule |
| --- | --- | --- |
| A contract, a pairing or a node | `manifest.description` | Required. A list of paragraphs, at least one. Each paragraph is a string that is not blank |
| A launcher | `description`, at the root of the document, because a launcher has no manifest | Required. The same form as `manifest.description` |
| A topic, a service or an action of a contract, and a topic of a pairing | `description`, after `name` | Required. One string that is not blank |
| A member that a node declares itself: a native entry of `emits` or `exposes`, with no `link_id` | `description`, after `name` | Required. One string that is not blank |
| A field of a message format | [`$description`](/reference/message_format/#description-modifier), beside `$type` | Optional. One string that is not blank |

The first paragraph of a document is its summary: `peppy repo search` prints it. The summary of a node or a launcher also says what it needs to run, such as a GPU, a device or a simulation. The description of an action tells its goal, its feedback and its result.

```json5
// gripper/peppy.json5
{
  peppy_schema: "contract/v1",
  manifest: {
    name: "gripper",
    tag: "v1",
    description: [
      "A gripper with two fingers: it moves its fingers to an opening and gives the measured opening.",
      "Each opening is the distance between the two fingers, in meters.",
    ],
  },
  interfaces: {
    topics: [
      {
        name: "opening",
        description: "The measured opening of the fingers, at the rate of the driver.",
        qos_profile: "sensor_data",
        message_format: {
          opening: { $type: "f64", $description: "The distance between the fingers, in meters." },
        },
      },
    ],
    actions: [
      {
        name: "move_fingers",
        description: "Move the fingers to an opening. The goal gives the target opening, each feedback gives the measured opening, and the result gives the opening at the end of the motion.",
        goal_service: { request_message_format: { opening: "f64" } },
        feedback_topic: { message_format: { opening: "f64" } },
        result_service: { response_message_format: { opening: "f64" } },
      },
    ],
  },
}
```

The parser refuses a document whose description is missing or blank, and the error names the part by its path, for example `manifest.description[1]: the description is blank; write what it describes`, or ``Native entry `beat` in `topics.emits` has no `description` ``. Other rules:

- An entry with a `link_id`, document-backed or consumed, takes no `description`, and the parser refuses the key on it. The contract, the pairing or the producer node that declares the member describes it.
- A launcher fragment, an MCP exposure and a `peppy_repository.json5` have no description. The text of an exposure is already data.
- The comments of a document are notes for its maintainers. No reader shows them.
- Peppy reads no rule from a description. The rules stay in the data that the checkers read: [enums](/reference/message_format/#enum-modifier), [marks](/advanced_guides/contract_implementation/#marks) and [failure kinds](/advanced_guides/contract_implementation/#failure-kinds).

These readers show the descriptions:

| Reader | What it shows |
| --- | --- |
| [`peppy repo search`](/advanced_guides/repositories/#search-the-repositories) | The summary of each match. With `--text`, the query also finds a document by the words of its descriptions |
| [`peppy repo show`](/advanced_guides/repositories/#show-what-a-query-matches) | Each paragraph, and each member of a contract or topic of a pairing with its description |
| [`peppy node info`](/guides/node_stack/#inspecting-a-node-with-peppy-node-info) | Each paragraph of the description of the node |
| [`peppy node describe`](/advanced_guides/calling_instances/#peppy-node-describe) | The description of the node, of each contract and pairing, of each member and of each field |
| [The codec API](/advanced_guides/codec_api/#parse-a-contract) | The description of a contract, of each member and of each field |
| [The MCP server](/advanced_guides/mcp/#the-published-schemas) | The `$description` of each field, as the `description` of its property in the published schemas |
| [The fleet listing](/advanced_guides/fleet/#the-fleet-listing) | The pinned document of each contract of a robot, with its descriptions |

## Node Instance

A **Node Instance** is one deployment of a node under an id; a restart starts a new process under the same id. Each instance has:

- **Instance ID**: The instance's unique identifier, kept across its restarts
- **State**: Its runtime lifecycle state: `starting` while it comes up (until its ready signal, then until its setup ends, within its setup budget), `running` once started, then the terminal `finished` (clean exit) or `failed` (crash) if its process exits on its own, or `restarting` while the daemon waits to start it again under its restart policy
- **Health**: Whether a running instance answers the core node's health checks, `healthy` or `unhealthy`; it turns `unhealthy` only after three consecutive missed health checks (not applicable while the instance is `restarting` or terminal)

A node can have multiple instances running simultaneously. For example, you might run multiple instances of a camera node, each connected to separate physical devices.

## Node Stack

The **Node Stack** is the central data structure that manages all active nodes in the system. It maintains a directed acyclic graph (DAG) where:

- **Vertices** are node entities
- **Edges** represent dependency relationships, pointing from a dependent node to its dependency. Edges come from each node's `depends_on.nodes` declarations; contract, pairing, and observer slots do not add DAG edges. The declared interfaces are then validated against those edges.

### Key responsibilities

1. **Dependency Management**: Tracks which nodes depend on which other nodes
2. **Interface Validation**: Ensures nodes expose the interfaces their dependents require
3. **Instance Lifecycle**: Manages the creation, health tracking, and removal of node instances. Running instances are continuously health-checked; a sustained run of missed health checks flags an instance `unhealthy`, and under `on_failure` or `always` an instance that stops answering is killed and its exit treated as a failure, by the rule in [Instance health and lifecycle](/guides/node_stack/#instance-health-and-lifecycle). The monitor never removes an instance, so an instance leaves the stack only when it is explicitly stopped or removed. See [Instance health and lifecycle](/guides/node_stack/#instance-health-and-lifecycle) for details.
4. **Root Node**: Always contains a root node (the core node) that cannot be removed

### How dependencies work

When a node is added, the stack:

1. Validates that all required dependencies exist
2. Checks that dependencies expose the required interfaces
3. Tracks pending requirements when dependencies are not yet available
4. Resolves pending requirements when dependencies are added

### Stack inspection

The stack-list API exposes the nodes and dependency edges as a serialized JSON graph for programmatic access. The `peppy stack list` command renders that graph as operator-friendly tables inside a separate outer panel for each live core node.

## The Core Node

The **Core Node** is a special node that serves as the root of the node stack and is always present. It is the daemon (`peppy service serve`) that the `peppy` CLI talks to. It is responsible for:

- **Dependency Attachment**: When a node declares a dependency in `depends_on.nodes`, the core node attaches the edge and validates that the dependency exposes the interfaces the dependent consumes
- **Stack Management**: Managing the lifecycle of all other nodes in the system: spawning them, probing their health, and tearing them down so none is left orphaned when the daemon stops or dies
- **System Coordination**: Acting as the central coordinator for the local Peppy runtime

When the core node shuts down cleanly it stops every spawned node (cooperatively, then force-killing any straggler's process group); if it dies unexpectedly, each node's watchdog notices the missing heartbeat and shuts the node down after a grace period, or at once when a new daemon of the same core node sends its first heartbeat. See [Daemon shutdown and orphan prevention](/guides/node_stack/#daemon-shutdown-and-orphan-prevention) for details.

Each Peppy runtime has exactly one core node that manages its local DAG of nodes. 
In a distributed deployment, multiple runtimes (each with their own core node) can run on separate machines, and nodes communicate across runtimes through the shared messaging layer. 
Each core node owns only its local stack. A federated launch is driven by a coordinator: the daemon that received the launch resolves every deployment once and drives the participating core nodes, which run exactly what it resolved (see [Federation](/advanced_guides/federation/)).

Each machine runs at most one daemon per Peppy data root. `peppy service serve` takes an exclusive lock at startup, and a second invocation refuses to boot while the first runs.

Because core nodes are addressed by name over the messaging layer, every core node reachable over the same router or federation must have a **unique name**. Each daemon derives a stable, machine-specific name by default, or you can pin one with [`core_node_name`](/advanced_guides/daemon_config/#core_node_name-the-daemons-core-node-name); a daemon whose name is already taken refuses to boot.

## The fleet

The **fleet** of a stack is the robots of the launch that the core node coordinates: each [copy](/guides/launch_files/#copies) of the launch is a robot, a device that a client changes included. The core node serves the fleet in the daemon interface `robot_leases:v1` (see [Robot leases and the halt](/advanced_guides/fleet/)):

- A **lease** gives one client the right to move one robot. Only a node whose launcher scopes it to hold leases takes one.
- A **mark** on a contract member, such as `moves_robot`, says what the member does. Each MCP server of peppy, `peppy node call` and each lease holder ask the core node before they call a member with the mark `moves_robot`.
- The **halt** ends every lease and stops each client that asks before it moves a robot, until a person or a program clears it. It stays after a restart of the core node.
- The **robot commander** of a robot is the option of its copy on the axis that the launcher marks with `role: "robot_commander"`: a node that drives its own robot outside the leases and the halt, such as a leader arm or the browser panel.

The leases and the halt prevent conflicts between clients. They are not a safety function.

## Summary

```
Node Stack
├── Core Node (always present)
│   └── Instance (always a single instance)
│
└── Other Nodes
    ├── Node A
    │   ├── Configuration
    │   └── Instances (1 or more)
    │
    └── Node B
        ├── Configuration
        └── Instances (1 or more)
```
