## Node

A **Node** is the fundamental unit of computation in Peppy. It represents a runnable application or service that can expose interfaces (topics, services, actions) and consume interfaces from other nodes. Code that several nodes call as functions is a shared library, not a node; see [Choosing between a node and a shared library](/advanced_guides/node_or_library/).

A node is defined by its **configuration** file (`peppy.json5`) which includes:

- **`peppy_schema`**: The schema identifier, always `"node/v1"`
- **Manifest**: The node's identity and its description
- **Execution**: Commands to build and run the node, plus the parameters it accepts
- **Interfaces**: What the node exposes and consumes (optional; a node with no interfaces omits it)
- **Framework**: the restart policy, a knob peppy reads the same way for every node (optional)

### Manifest

The manifest defines a node's identity:

| Field | Description |
|-------|-------------|
| `name` | A validated identifier (ASCII letters, digits, `_`, `-`) |
| `tag` | A short contract identifier (e.g., `v1`, `donut`). Must start with an ASCII letter; allowed chars are letters, digits, `_`, `-`. Dots are forbidden. |
| `description` | What the node does and what it needs to run, as a list of paragraphs. The first paragraph is the summary. Required; see [Descriptions](#descriptions) |
| `labels` | Optional metadata labels |
| `implements` | Optional list of contracts this node implements, making it eligible to fill contract slots; see [Contract implementation](/advanced_guides/contract_implementation/) |
| `depends_on` | Optional dependency declarations, in five lists: `nodes`, `contracts`, `daemon`, `pairings`, and `pairing_observers`; see [Contract implementation](/advanced_guides/contract_implementation/), [Daemon targets](/advanced_guides/core_node_functions/#daemon-targets) and [Pairing](/advanced_guides/pairing/) |

A node is uniquely identified by its `name:tag` combination.

Tags are **not** semver. Bumping a tag always means "incompatible with the previous one": there is no notion of a backward-compatible patch or minor release. Pick a label that identifies the contract (`v1`, `v2`, `donut`), not a version number.

### Execution

The execution section defines how to prepare and launch the node:

| Field | Description |
|-------|-------------|
| `language` | Programming language of the node (`rust` or `python`). |
| `parameters` | Optional parameter schema for runtime configuration. |
| `build_cmd` | Command run during the node build phase. |
| `run_cmd` | Command used to start a process node. |
| `container` | Optional container configuration. Provide either `run_cmd` or `container`, never both. Container nodes build through their container image, so `build_cmd` is not used. |
| `endpoints` | Optional map of network sockets the node binds during setup, keyed by label (lowercase letters, digits, and underscores, starting with a letter). Each entry sets `kind` (`page` for a browser URL or `mcp` for an MCP endpoint) and a non-empty `description`. The node announces each bound socket during setup so the daemon can report its URLs; failing to announce a declared label fails startup. |
| `setup_timeout_secs` | Optional time limit (1 to 540 seconds; default 15) the daemon waits for `setup` to return after the node signals ready. See [How an instance starts](/guides/node_stack/#how-an-instance-starts). |

### Framework

The `framework` block holds runtime settings that Peppy handles uniformly for every node. Launchers use the same `framework` key.

| Field | Description |
|-------|-------------|
| `restart` | Optional restart policy when the process exits or stops answering health checks: `"never"`, `"on_failure"` (default), `"always"`, or `{ policy, max_restarts }`. `max_restarts` limits consecutive restart attempts (including failed starts), after which the instance stays `failed`. Under `on_failure` or `always`, an unresponsive instance is killed and restarted (see [Instance health and lifecycle](/guides/node_stack/#instance-health-and-lifecycle)). Precedence: instance entry / CLI `--restart` > node `peppy.json5` > launcher root > default (`on_failure`). See [Restart policy](/guides/launch_files/#restart-policy). |

### Interfaces

Nodes communicate through three interface types:

| Type | Description |
|------|-------------|
| **Topic** | Publish/subscribe messaging for continuous data streams |
| **Service** | Request/response communication for synchronous calls |
| **Action** | Long-running tasks with progress feedback and cancellation |

A node can **expose** interfaces (make them available to others) and **consume** interfaces from other nodes.

Three higher-level patterns build on these:

- [**Contract implementation**](/advanced_guides/contract_implementation/): a standalone contract defines the interfaces, and any implementing node can fill a consumer's slot.
- [**Pairing**](/advanced_guides/pairing/): an exclusive 1:1 bidirectional topic connection between two specific instances.
- [**Observer slots**](/advanced_guides/pairing/#observers-watching-a-pairing-without-joining-it): read-only taps on one side of an existing pairing.

See [Choosing a communication pattern](/advanced_guides/communication_patterns/) for a side-by-side comparison.

## Descriptions

Contracts, pairings, nodes, and launchers store human- and machine-readable **descriptions** directly in their JSON5 files. CLI search tools, inspection commands, and AI models all read these fields.

| Document or element | Key | Rule |
| --- | --- | --- |
| Contract, pairing, or node | `manifest.description` | Required. List of one or more non-blank paragraphs. |
| Launcher | `description` (at root, since launchers have no manifest) | Required. Same list of paragraphs. |
| Topic, service, or action in a contract, or topic in a pairing | `description` (after `name`) | Required. Single non-blank string. |
| Native member declared directly by a node (`emits` or `exposes` with no `link_id`) | `description` (after `name`) | Required. Single non-blank string. |
| Message format field | [`$description`](/reference/message_format/#description-modifier) (beside `$type`) | Optional. Single non-blank string. |

The first paragraph of a document is its **summary**, printed by `peppy repo search`. For a node or launcher, include what hardware or runtime it needs (such as a GPU, USB device, or simulator). For an action, describe its goal, feedback, and result.

```json5
// gripper/peppy.json5
{
  peppy_schema: "contract/v1",
  manifest: {
    name: "gripper",
    tag: "v1",
    description: [
      "A gripper with two fingers: it moves its fingers to an opening and gives the measured opening.",
      "Each opening is the distance between the two fingers, in meters.",
    ],
  },
  interfaces: {
    topics: [
      {
        name: "opening",
        description: "The measured opening of the fingers, at the rate of the driver.",
        qos_profile: "sensor_data",
        message_format: {
          opening: { $type: "f64", $description: "The distance between the fingers, in meters." },
        },
      },
    ],
    actions: [
      {
        name: "move_fingers",
        description: "Move the fingers to an opening. The goal gives the target opening, each feedback gives the measured opening, and the result gives the opening at the end of the motion.",
        goal_service: { request_message_format: { opening: "f64" } },
        feedback_topic: { message_format: { opening: "f64" } },
        result_service: { response_message_format: { opening: "f64" } },
      },
    ],
  },
}
```

Validation rules:

- Missing or blank required descriptions fail parsing with the exact field path (for example, `manifest.description[1]: the description is blank; write what it describes` or ``Native entry `beat` in `topics.emits` has no `description` ``).
- Entries with a `link_id` (implementing or consuming a contract, pairing, or producer node) must **not** set `description`; the defining document owns the description.
- Launcher fragments, MCP exposures, and `peppy_repository.json5` files have no document description (MCP exposures already carry their own tool and resource descriptions).
- JSON5 comments are for maintainers only and are never surfaced by Peppy tools.
- Peppy never parses behavioral rules from description text. Use structured fields instead: [enums](/reference/message_format/#enum-modifier), [marks](/advanced_guides/contract_implementation/#marks), and [failure kinds](/advanced_guides/contract_implementation/#failure-kinds).

Where descriptions appear:

| Tool or API | What it displays |
| --- | --- |
| [`peppy repo search`](/advanced_guides/repositories/#search-the-repositories) | Document summary. With `--text`, searches inside descriptions as well. |
| [`peppy repo show`](/advanced_guides/repositories/#show-what-a-query-matches) | All paragraphs, plus every contract member or pairing topic description. |
| [`peppy node info`](/guides/node_stack/#inspecting-a-node-with-peppy-node-info) | All paragraphs of the node description. |
| [`peppy node describe`](/advanced_guides/calling_instances/#peppy-node-describe) | Descriptions of the node, its contracts and pairings, every member, and every field. |
| [Codec API](/advanced_guides/codec_api/#parse-a-contract) | Descriptions of a contract, its members, and its fields. |
| [MCP server](/advanced_guides/mcp/#the-published-schemas) | Field `$description` values exported as JSON Schema property descriptions. |
| [Fleet listing](/advanced_guides/fleet/#the-fleet-listing) | Pinned contract documents for each robot, including their descriptions. |

## Node Instance

A **Node Instance** is a single running deployment of a node with a unique ID. If the instance restarts, Peppy launches a new OS process under the same instance ID.

Each instance tracks:

- **Instance ID**: Unique identifier preserved across restarts.
- **State**: Lifecycle state:
  - `starting`: process is booting, signalling ready, and running `setup` within its setup timeout.
  - `running`: setup succeeded and the instance is active.
  - `restarting`: process exited and the daemon is waiting to restart it under its restart policy.
  - `finished` / `failed`: terminal states after a clean exit (`finished`) or crash/exhausted restarts (`failed`).
- **Health**: Whether a `running` instance responds to core node health checks (`healthy` or `unhealthy`). Three consecutive missed checks mark it `unhealthy`. Not applicable while `restarting`, `finished`, or `failed`.

You can run multiple instances of the same node at once (for example, two camera node instances connected to different USB devices).

## Node Stack

The **Node Stack** is the directed acyclic graph (DAG) that tracks all registered nodes and their dependencies on a daemon:

- **Vertices** are registered nodes.
- **Edges** point from a dependent node to its direct dependencies declared in `depends_on.nodes`. (Contract, pairing, and observer slots are bound per instance and do not add static DAG edges.)

### Key responsibilities

1. **Dependency Management**: Tracks direct node dependencies and validates that required nodes exist.
2. **Interface Validation**: Verifies that dependencies expose every topic, service, and action their dependents consume.
3. **Instance Lifecycle**: Starts instances, monitors health, restarts crashed or unresponsive instances according to their restart policy, and stops them cleanly. Instances stay listed until explicitly stopped, removed, or replaced by a new launch. See [Instance health and lifecycle](/guides/node_stack/#instance-health-and-lifecycle).
4. **Root Node**: Always contains the core node as an irremovable root.

### How dependencies work

When you add a node, the stack:

1. Verifies that all required dependencies exist.
2. Checks that each dependency exposes the consumed interfaces.
3. Tracks pending requirements if dependencies are not yet available.
4. Resolves pending requirements once those dependencies are added.

### Stack inspection

The stack-list API returns nodes and dependency edges as JSON for programmatic use. `peppy stack list` renders the same graph as readable tables, grouped in one panel per live core node.

## The Core Node

The **Core Node** is the local Peppy daemon (`peppy service serve`) and the permanent root of the node stack. Every `peppy` CLI command talks to it. It handles:

- **Dependency Attachment**: Adds dependency edges from `depends_on.nodes` and validates interface compatibility.
- **Stack Management**: Builds, spawns, health-checks, restarts, and stops node instances without leaving orphan processes behind.
- **System Coordination**: Serves local runtime services (datastore, system clock, stack inspection, and fleet coordination).

On clean shutdown, the core node asks every spawned instance to stop cooperatively and force-kills any process group that misses the grace window. If the core node crashes, each node's watchdog shuts the node down after a grace period, or immediately when a replacement daemon starts on the same core node. See [Daemon shutdown and orphan prevention](/guides/node_stack/#daemon-shutdown-and-orphan-prevention).

Key deployment rules:

- **One daemon per data root**: `peppy service serve` holds an exclusive lock on its Peppy data root; a second daemon refuses to start while the first is running.
- **Unique name across the network**: Every core node sharing a Zenoh router or federation needs a unique name. By default each daemon derives a stable machine-specific name (`cn-...`), or you can set [`core_node_name`](/advanced_guides/daemon_config/#core_node_name-the-daemons-core-node-name). A daemon refuses to boot if its name is already live.
- **Distributed stacks**: In a multi-machine [federation](/advanced_guides/federation/), each machine runs its own core node and owns its local stack. The daemon that receives a `peppy stack launch` acts as the coordinator, resolving all deployments once and instructing each participating core node what to run.

## The fleet

The **fleet** is the set of robots running in a stack, coordinated by the launch's core node. Each [copy](/guides/launch_files/#copies) in the launch counts as one robot (including controllable devices such as a smart appliance or fixture).

The core node exposes fleet coordination through the `robot_leases:v1` daemon interface (see [Robot leases and the halt](/advanced_guides/fleet/)):

- **Lease**: Grants one client exclusive permission to move a specific robot. Only nodes given a `robot_leases` scope by the launcher can hold leases.
- **Mark**: A metadata tag on a contract member. Members tagged `moves_robot` require a check with the core node before any Peppy MCP server, `peppy node call`, or lease holder invokes them.
- **Halt**: Immediately revokes all leases and blocks all `moves_robot` calls across the stack until explicitly cleared. Persists across core node restarts.
- **Robot commander**: The local manual controller for a robot (such as a leader arm or browser panel), identified by the launcher axis marked `role: "robot_commander"`. A robot commander drives its own robot directly, outside leases and the halt.

Leases and the halt prevent software clients from fighting over the same robot. They are **not** a safety system; hardware e-stops and certified safety layers remain responsible for physical safety.

## Summary

```
Node Stack
├── Core Node (always present)
│   └── Instance (always a single instance)
│
└── Other Nodes
    ├── Node A
    │   ├── Configuration
    │   └── Instances (1 or more)
    │
    └── Node B
        ├── Configuration
        └── Instances (1 or more)
```
