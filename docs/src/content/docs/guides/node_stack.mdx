The **node stack** is the central registry that manages all your nodes and their relationships in Peppy. Think of it as a directed graph where:

- **Nodes** are registered configurations that can have multiple running instances
- **Edges** represent explicit dependencies declared via `depends_on` in the node manifest

When you add a node to the stack, Peppy verifies that its required dependencies are already in the stack and expose every topic, service, and action it consumes. Slots that allow zero bindings (`cardinality: "zero_or_one"` or `"zero_or_more"`) are the exception: if absent from the stack, Peppy resolves their interfaces from the [repository cache](/advanced_guides/repositories/#syncing-against-repositories) so code generation still succeeds (failing only if missing from both). At launch time, `zero_or_one` slots require an explicit vacant binding, while `zero_or_more` slots may be omitted. Validating dependencies up front catches wiring errors before any instance starts.

The stack always contains a **core node** and an instance of it at its root, which coordinates the lifecycle of all other nodes. You can query the stack to see which nodes depend on each other and manage node instances.
The **node stack** is started as a daemon on your system and the `peppy` binary communicates with it to execute user actions.

:::note
The `peppy node` lifecycle commands (`add`, `build`, `run`, `stop`, and `remove`) serialize with stack operations on the same daemon. Each is refused while a `stack launch`, `stack build`, `stack join`, `stack remove`, or `stack reset` holds the stack, and any one already in flight when a `stack reset` starts is cancelled once the reset has given it its cleanup window.
:::

## Adding `hello_world` to the stack

Inside your node directory, add it to the Peppy stack by running:

```sh
peppy node add .
```

This command registers the node with the core node by staging a snapshot of the source directory. After a successful add, the node enters the `Added` stage: its config is known to the daemon, but no runnable artifact exists yet (since `build_cmd` has not been run). You'll produce that artifact in the next section with [`peppy node build`](#building-hello_world).

The output of this command provides some useful information:

```
Adding node from /private/tmp/hello_world...
Log file: ~/.peppy/logs/add/hello_world_v1_20260121_224824_699Z.log
Added node hello_world:v1 to the node stack
```
The log file records every step reported by the daemon and any failure details.

What happens during `peppy node add`:

- **Staging**: Peppy copies the source directory into a temporary snapshot under `~/.peppy/tmp/` and generates bindings there (never modifying your source tree). The temporary copy is cleaned up automatically if the add fails or when you run `peppy node remove`. Later, `peppy node build` saves the runnable artifact under `~/.peppy/built_nodes/<name>_<tag>/`, named by the snapshot's content fingerprint.
- **Replacing an existing `name:tag`**: Only one entry per `name:tag` can exist in the stack. Re-adding the same `name:tag` replaces it, with three safety rules:
  1. If other nodes depend on it and the new version changes its interfaces, the overwrite is refused.
  2. If any instance is currently `starting`, the overwrite is refused without stopping anything.
  3. If instances are running or waiting to restart, `peppy node add` prompts for confirmation for local directories or `name:tag` sources (git/URL adds proceed without prompting), then stops and clears all tracked instances (exited ones are cleared silently) before replacing the node.

## Building `hello_world`

An added node has no runnable artifact until it's built. Building runs the node's `build_cmd` (for example `uv sync` for Python or `cargo build --release` for Rust) against the snapshot that `peppy node add` staged, unless an artifact built from that same snapshot is already cached (see below):

```sh
peppy node build hello_world:v1
```

The format is `<node_name>:<tag>` for a node that is already part of the node stack. While the build is running the node sits in the `Building` stage; once it completes, it moves to `Ready` and can be run.

    [uv](https://docs.astral.sh/uv/getting-started/installation/) must be installed on your system. Without it, the build will fail with a `No such file or directory` error.
    :::

    :::note
    Container builds on the peppy Python base image cache the packages and the Python interpreter archives uv downloads automatically, so a rebuild downloads neither again; see [Build caching](/advanced_guides/containers/#build-caching).
    :::
  </TabItem>
  <TabItem label="Rust">
    :::caution
    [cargo](https://doc.rust-lang.org/cargo/getting-started/installation.html) must be installed on your system. Without it, the build will fail with a `No such file or directory` error.
    :::

    :::note
    For faster Rust builds, install [sccache](https://github.com/mozilla/sccache#installation). When Peppy detects `sccache` on your system PATH and you have not set `RUSTC_WRAPPER` yourself, it automatically sets `RUSTC_WRAPPER=sccache` for process-node builds. Container builds on the peppy base images cache the cargo registry and sccache artifacts automatically, no installation needed; see [Build caching](/advanced_guides/containers/#build-caching).

The output looks like:

```
Building node hello_world:v1...
Log file: ~/.peppy/logs/build/hello_world_v1_20260121_224901_312Z.log
Built node hello_world:v1. Artifact: ~/.peppy/built_nodes/hello_world_v1/3f9a1c2e5d7b8a4f.tar.zst
```

The artifact is a `.tar.zst` archive. When you start an instance with `peppy node run`, the daemon extracts it into a per-instance directory and executes `run_cmd` there.

The file name is the fingerprint of the staged sources, mixed with the peppy version, the host platform and the artifact kind. Building the node again from byte-identical sources with the same peppy version on the same platform reuses the artifact instead of running `build_cmd`, and the build log says so:

```
Reusing cached build of hello_world:v1 (fingerprint 3f9a1c2e5d7b8a4f) at ~/.peppy/built_nodes/hello_world_v1/3f9a1c2e5d7b8a4f.tar.zst
```

Pass `peppy node build hello_world:v1 --rebuild` to build from the sources anyway, for instance after a toolchain change on the host; the result replaces the cached artifact. See [Build caching](/advanced_guides/containers/#build-caching) for what the fingerprint covers.

## Starting your node

Start your node:

```sh
peppy node run hello_world:v1
```
This will run the `run_cmd` command from the `peppy.json5` process configuration.
The format is `<node_name>:<tag>` for a node that is already part of the node stack.

`peppy node run` also decides which [clock](/advanced_guides/system_clock/#clock-domains) the instance reads. `--clock <DOMAIN>` binds it to a domain that is already running, named as `wall`, a short name, or a qualified `name@core_node` when one name runs on several machines; `--publish-clock <DOMAIN>` declares a domain and starts this instance as its publisher. The two flags conflict, and an instance that names neither reads wall time:

```sh
peppy node run waldo:v1 -i simulation_inst --publish-clock simulation
peppy node run openarm_sim_arm:v1 -i arm_inst --clock simulation
```

`--restart POLICY` sets the instance's [restart policy](/guides/launch_files/#restart-policy), `never`, `on_failure` or `always`, over the node's `framework.restart`; `--max-restarts N` caps the restart attempts in a row, failed starts included, and the next exit or failed start past them leaves the instance `failed`; it requires `--restart on_failure` or `--restart always`.

A node whose manifest declares [`execution.endpoints`](/guides/first_node/#serving-a-page-or-an-mcp-endpoint) ends `node run` with the URLs its instance serves, one per address of the machine hosting it, loopback first:

```
Started node instance 'panel_inst' (pid: 12345)
Web pages:
  panel_inst (openarm_web_commander:v1) @cn-sweet-edison
    panel  http://127.0.0.1:8765
           http://100.123.58.116:8765
```

The `node run` command outputs the path to a log file where you can inspect the node's output.
For example:
```sh
cat /home/ubuntu/.peppy/logs/run/elegant-solomon-5423_20260217_101523_412Z.log
[2026-02-17T10:15:23.599+00:00] Executing run_cmd: uv run hello_world (working_dir: /home/ubuntu/.peppy/instances/elegant-solomon-5423)
[2026-02-17T10:15:23.837+00:00] [stdout] hello world count 1
[2026-02-17T10:15:26.848+00:00] [stdout] hello world count 2
[2026-02-17T10:15:29.852+00:00] [stdout] hello world count 3
```

Each line starts with the time of the machine, to the millisecond, with its UTC offset, so the lines of two machines in different time zones can be put in order. The name of a log file gives the UTC time at which the file was created (the `Z` suffix), so the names of the logs of an instance sort in time order.

### How an instance starts

`peppy node run`, `peppy stack launch`, and `peppy stack join` all start an instance in three phases:

1. **Ready (up to 600 s):** The daemon starts `run_cmd` (or the container) as the leader of a new process group and waits for `peppylib` to signal ready. `peppylib` signals ready as soon as it connects to messaging and starts listening for shutdown requests, *before* your `setup` function runs.
2. **Setup (`setup_timeout_secs`, default 15 s):** The daemon waits for your `setup` function to return. Nodes that wait for external hardware, simulators, or remote services can raise this in `peppy.json5` with `execution.setup_timeout_secs` (1 to 540 seconds). Keep the value tight so a hung setup fails promptly. If it times out, the error names the timeout and whether it came from the manifest or the default.
3. **Endpoints (up to 15 s):** If the manifest declares [`execution.endpoints`](/guides/first_node/#serving-a-page-or-an-mcp-endpoint), the daemon waits for the node to announce every declared socket.

```json5 title="peppy.json5"
{
  // ...
  execution: {
    language: "rust",
    run_cmd: ["./target/release/arm_driver"],
    // The setup waits for the arm controller, which can take two minutes to boot.
    setup_timeout_secs: 180,
  },
}
```

Nodes can read their effective setup timeout at runtime (`node_runner.setup_timeout()` in Rust as a `Duration`, `node_runner.setup_timeout_secs()` in Python as an `int`) to report a clearer error before the daemon times them out. Standalone nodes and the [test harness](/advanced_guides/testing/) read the same value from the manifest.

When the instance signals ready, the daemon emits a progress line that resets the launch's run idle timer ([Launch timeouts](/guides/launch_files/#launch-timeouts)). Because the maximum setup budget (540 s) is shorter than the default run idle timeout (600 s), a silent hung setup always reports the clearer setup timeout error rather than a generic idle timeout.

**If startup is aborted** (setup timeout, failed endpoint announcement, launch timeout, `peppy stack reset`, or CLI Ctrl+C):

- **Before the ready signal**: the node cannot receive shutdown requests yet, so the daemon immediately kills its entire process group.
- **After the ready signal**: the daemon runs the normal graceful-then-forced stop sequence ([`peppy node stop`](#stopping-your-node)), sending a shutdown request, waiting for the shutdown grace and runtime teardown, and then killing the process group. Registered [shutdown hooks](/guides/first_node/#graceful-shutdown) run so half-initialized locks or simulation state are released cleanly. `peppy stack reset` waits for this stop to finish before clearing the stack.

In Python, an `async def setup` cancels at its next `await`, whereas a synchronous `setup` blocks shutdown handling until it returns (or is force-killed at the deadline). See the [shutdown lifecycle guide](/advanced_guides/shutdown/).

### Chaining add, build, and run

Now that you've seen all three steps, `peppy node add` exposes flags that chain them for you:

- `--build` (`-b`) runs `peppy node build` immediately after the add succeeds.
- `--run` (`-r`) also spawns an instance once the build finishes, and implies `--build`.
- `--sync` (`-s`) runs `peppy node sync` **before** the add, so the snapshot picks up any edits you made to `peppy.json5`. Only valid for local filesystem sources; remote git/HTTP sources are synced server-side on fetch.

```sh
peppy node add -sb .    # sync, then add, then build
peppy node add -sr .    # sync, then add, then build, then run an instance
```

:::tip
`-sb` and `-sr` are the shorthands you'll reach for constantly during development. The typical edit-loop is: change `peppy.json5` or source, hit `peppy node add -sr .`, watch the logs, iterate. Without `-s`, a stale `.peppy/` bindings directory can make the daemon see an out-of-date interface; without `-r`, you have to follow every add and build with a separate `peppy node run`. Bundling them collapses the whole "I edited something, now run it" cycle to a single command.

Run-only options (trailing `key=value` arguments, `--instance-id`, `--link KEY@VALUE`, `--vacant-link SLOT=<why>`, `--clock DOMAIN`, `--publish-clock DOMAIN`, `--restart POLICY` and `--max-restarts N`) are only accepted alongside `-r`/`--run`; combining them with a plain `peppy node add` is rejected at parse time so an arg you cared about isn't silently dropped. Keep `key=value` arguments **after** the source path (e.g. `peppy node add -sr . frequency=30`) so the source positional isn't confused with the trailing args. `--link` mirrors the `peppy node run --link` flag and runs the same validator; see [Bindings and routing](/advanced_guides/topics/#bindings-and-routing).
:::

### When a node command ends early

`peppy node add`, `build`, and `run` each submit a goal to the daemon and track it to completion. If the daemon refuses or fails the goal, the CLI prints the [failure kind](/guides/launch_files/#how-a-stack-command-ends), the reason, and (on failure) the log path, then exits with code `3` (refused) or `4` (failed). See [Exit statuses of the other commands](/advanced_guides/calling_instances/#exit-statuses-of-the-other-commands).

```
Error: Node add refused (busy): action already in progress (times out in 590s), use `--force` to force adding the node
Error: Node build failed (attempt_failed): build_cmd `uv sync` failed with status exit status: 2. Log file: ~/.peppy/logs/build/hello_world_v1_20260121_224901_312Z.log
```

**Busy refusals:** The daemon refuses `add`, `build`, `run`, `stop`, and `remove` with kind `busy` while another conflicting operation holds the stack (a stack change, `peppy stack reset`, a remote launch reservation, or a concurrent add/build/run of the same node). Retry once that work finishes, or pass `--force` on `peppy node add` / `peppy node build` to cancel and supersede an in-flight add or build of that node (the superseded command exits with code `5`).

**Ctrl+C and disconnection:**

- **1st Ctrl+C**: Sends a cancel request to the daemon. The daemon aborts at the current step (a cancelled add publishes nothing; a cancelled build kills `build_cmd` and leaves the node `Added`; a cancelled run stops the starting instance). The CLI waits for cleanup under `--max-timeout` alone and exits with the goal's outcome (`5` cancelled, `0` if already completed, `4` if already failed). For chained commands (`peppy node add --run`, `--build`, or `peppy node run` triggering a build), Ctrl+C exits with `130` and skips all later steps even if the active step finished first.
- **2nd Ctrl+C**: Stops waiting for cleanup once the cancel reaches the daemon (cleanup continues in the background) and exits `130`.
- **3rd Ctrl+C**: Exits immediately.
- **Process/terminal closed**: If the CLI disappears without sending a cancel, the daemon detects the missing caller and cancels the goal 1 minute later (matching [stack commands](/guides/launch_files/#how-a-stack-command-ends)).

```
Cancelling the node build; press Ctrl-C again to stop waiting for its end
Error: Node build was cancelled by its caller. Log file: ~/.peppy/logs/build/hello_world_v1_20260121_224901_312Z.log
```

**Timeouts and output lag:**

- `--idle-timeout` and `--max-timeout` limit how long the CLI waits. When exceeded, the CLI exits with code `1`, causing the daemon to cancel the goal.
- The CLI buffers up to 65,536 unread output lines. If output falls further behind, the CLI cancels the goal, reports the lag, and exits with code `1`.

By default, `peppy stack list` discovers every live core node in the same messaging namespace and prints one panel per core node (local first, then alphabetical):

- **Filter to one machine**: `peppy stack list --core-node <name>`.
- **Machine-readable output**: `peppy stack list --json` prints one JSON document with each core node's identity, `launch`, `reservation`, [`copies`, `copy_change`, `launch_copies`](/guides/launch_files/#copies), and either its `stack` graph (`nodes`, `edges`) or `error`.
- **Extra panels shown when present**: `Instance endpoints` (web pages and MCP URLs), `Instance pairings`, and launch ownership lines (`Slice of launch ...`, or `Reserved for launch ...` with the reset command that clears it).
- **Edge cases**: If two live daemons collide on the same name, they are grouped into one warning panel. If a core node disappears mid-query, other panels still print, the missing one shows an error, and the command exits non-zero. Tables wrap automatically to fit a terminal and never wrap when piped.

The `STAGE` column shows each node's build lifecycle:

- **`Added`**: Registered and staged, but not yet built.
- **`Building`**: Build in progress. A concurrent `peppy node build` is refused unless `--force` is passed to cancel and replace it. Matching cached artifacts skip `build_cmd` unless `--rebuild` is passed.
- **`Ready`**: Built artifact is on disk and ready to run (zero or more instances).
- **`Root`**: The built-in core node (always 1 running instance).

The `INSTANCES` column summarizes per-instance states (`starting`, `running`, `restarting`, `finished`, `failed`). Use [`peppy node info`](#inspecting-a-node-with-peppy-node-info) to see individual instance IDs and logs.

The **`Instance bindings`** table lists one row per instance (for nodes with at least one instance) and shows its resolved `depends_on` bindings:

- **Producer slots** (`depends_on.nodes` / `depends_on.contracts`): shown as `link_id → producer` (multi-cardinality slots list all members in plan order; empty `zero_or_more` or vacant `zero_or_one` slots show `(empty set)`).
- **Daemon targets** ([`depends_on.daemon`](/advanced_guides/core_node_functions/#daemon-targets)): bound automatically to the hosting daemon under its per-boot instance ID.
- **`(none)`**: the instance has no producer bindings (pairing and observer slots appear in the separate `Instance pairings` table).

See [Bindings and routing](/advanced_guides/topics/#bindings-and-routing) for slot rules and `--link`.

### Instance health and lifecycle

The `Instance bindings` table tracks four runtime columns for every instance:

- **`STATUS`**:
  - `starting`: process is booting and clearing its startup health gate.
  - `running`: started and active.
  - `restarting`: exited and waiting for its [restart policy](/guides/launch_files/#restart-policy) backoff timer. A failed restart returns to `restarting` until `max_restarts` is reached (or the daemon refuses the restart), leaving the instance `failed`.
  - `finished` / `failed`: terminal states after a clean exit (`finished`) or crash/kill (`failed`).
- **`HEALTH`**: `healthy` or `unhealthy` for `running` instances; `-` when no process is running (`restarting`, `finished`, `failed`).
- **`RESTARTS`**: number of times a restarted process reached `running`.
- **`CLOCK`**: `wall`, or a simulated domain (`name@core_node`). See [System clock](/advanced_guides/system_clock/).

#### Health monitoring

While an instance is `running`, the daemon probes it every **5 seconds** (3-second timeout per check):

- **1 to 2 missed checks**: stays `healthy` (brief host/VM stalls are logged at debug level only).
- **3 consecutive missed checks (~20 s)**: marked `unhealthy`. The process is still alive, just unresponsive (deadlocked or disconnected from messaging).
- **1 successful check**: returns to `healthy`.
- **60 seconds with no answered check (under `on_failure` or `always`)**: the daemon kills the unresponsive process (`SIGTERM`, then `SIGKILL` of its process group after shutdown grace + runtime teardown, 12 s by default) and treats the exit as a failure for restart policy purposes.
  - The kill occurs 52 to 68 seconds after the node goes silent (60 s from the last answered check plus the in-flight check window), intentionally outlasting a managed Zenoh router watchdog restart (up to 45.5 s plus in-flight checks) so router recovery never kills healthy nodes.
  - **Outage guard**: if two or more non-core instances are running on the daemon and *none* of them is healthy, the daemon assumes a local messaging outage and holds off killing instances until at least one responds again. A lone silent instance is still killed.
  - Under `never`, an `unhealthy` instance is never killed.

#### Exited processes and cleanup

When a process exits on its own, the daemon detects the exit directly (no health check in between), kills any leftover children in its process group (up to 30 s for macOS Lima containers), and moves it to `restarting`, `finished`, or `failed` according to its restart policy.

Instances are **never auto-removed** from the stack when `unhealthy`, `finished`, or `failed`, so you can inspect what happened. Clear them with [`peppy node stop`](#stopping-your-node) (also cancels a `restarting` instance), [`peppy node remove`](#removing-your-node), or a new launch. See [Starting a failed instance again](/guides/launch_files/#starting-a-failed-instance-again) for recovery steps.

Every lifecycle event (health changes, exits, health kills, outage holds, and restarts) is recorded in `~/.peppy/stack_log.log` and exported when [OpenTelemetry log export](/advanced_guides/opentelemetry/) is enabled.

### Daemon shutdown and orphan prevention

Peppy ensures that no node (or subprocess it spawned) outlives the daemon:

- **Process group cleanup on exit**: Whenever a node exits (cleanly, by crash, or via health kill) or fails to start, Peppy kills its entire process group. (Subprocesses that explicitly detach into a new process group or session are outside this group.)
- **Clean daemon shutdown (`Ctrl+C`, `systemctl stop`, `SIGTERM`)**: The daemon sends a cooperative shutdown request to every spawned node (firing cancellation tokens and [shutdown hooks](/advanced_guides/shutdown/)), waits for `shutdown_grace_secs` (default **5 s**) plus brief runtime teardown, then force-kills any remaining process groups. It does **not** wait for `daemon_grace_secs`.
- **Unclean daemon death (crash, OOM, `SIGKILL`)**:
  - **Router behavior**: On Linux, the kernel stops `zenohd` when the daemon dies. On macOS, a terminal-launched daemon may leave `zenohd` behind (stop it with `pkill -f zenohd_config_<port>.json5` if the next start reports port in use); under the installed macOS `launchd` service, `launchd` cleans up the daemon's process group and restarts it. Under Linux `systemd`, `systemd` kills all unit processes (including nodes) and restarts the daemon.
  - **Node watchdog**: Each spawned node tracks the unique boot ID of the daemon that started it and shuts itself down if either:
    1. Its own daemon's heartbeat is silent for `daemon_grace_secs` (default **180 s**, minimum 30 s). The generous window prevents false shutdowns during brief stalls or managed router restarts (which keep the same daemon boot ID).
    2. A *new* daemon for the same core node sends a heartbeat after the old daemon's presence disappears. Because a new daemon starts with an empty stack, orphaned nodes shut down immediately instead of waiting 3 minutes. (Daemons on other core nodes, other ports, or name-colliding daemons never stop your nodes.)

Configure both windows in `~/.peppy/conf/peppy_config.json5` ([Daemon configuration](/advanced_guides/daemon_config/)); restart the daemon to apply changes:

```json5
// peppy_config.json5
{
  lifecycle: {
    // Seconds a node waits without a daemon heartbeat before it self-terminates
    // to avoid orphaning. Default: 180 (3 minutes). Minimum: 30.
    daemon_grace_secs: 180,

    // Seconds a clean shutdown and `peppy node stop` wait for a node to exit
    // cooperatively before force-killing it. Raise it for nodes that need longer
    // to park actuators or release hardware. Default: 5. Minimum: 1.
    shutdown_grace_secs: 5,
  },
}
```

:::caution
`daemon_grace_secs` must be at least 30 seconds so brief stalls or router restarts do not trip node watchdogs. `shutdown_grace_secs` must be at least 1 second.
:::

## Inspecting a node with `peppy node info`

When you need more than the one-line view from `stack list`, `peppy node info` dumps the node's [description](/reference/concepts/#descriptions), its stage, its currently-tracked instances with their individual states and last-known health, and the paths to its add log and per-instance run logs. It takes a `<node_name>:<node_tag>` reference to a node **that has already been added to the stack**; it doesn't touch the filesystem or any git/http source, so run `peppy node add` first if the node isn't in the stack yet:

```sh
peppy node info hello_world:v1
```

```
[INFO] Getting node info for hello_world:v1...

Node Information
==================================================

Name:      hello_world
Tag:       v1
Language:  Python
```

This is usually the fastest way to answer "is my node built yet?" and "where is the log for this specific instance?". The `Add log` path is what `peppy node add` writes to; a run log is what one process of an instance writes to, `<instance_id>_<timestamp>.log`, so a restart opens a new file and the listing names the latest one. Build logs live under `~/.peppy/logs/build/` and are surfaced by `peppy node build` directly when it runs.

Each instance line ends with its [restart policy](/guides/launch_files/#restart-policy) and the level that set it, then the restarts so far:

- The level is `instance entry` (the launcher's entry, or an adjustment), `--restart` (the flag of `peppy node run` and `peppy node add --run`), `peppy.json5` (the node's own `framework.restart`), `launcher root`, or `default` (no level set one, so `on_failure`). A cap prints beside the policy as `max_restarts N`.
- A `restarting` instance adds the attempt it waits for and `next start in N s`, or ``next start due; it waits for the last exit's notices to other daemons, or for a stack launch, build, join or removal or a `peppy node remove` in progress on this daemon`` once the wait has passed and the restart has not begun.
- A `failed` instance adds ``attempt N refused: max_restarts M reached, failed starts included`` when the cap ended its restarts, or `attempt N refused` when the daemon refused to start it again (the stack log says why).
- Every instance that has exited adds its last exit, such as `last exit: exit code 1`, `last exit: signal 9 (SIGKILL)` or `last exit: killed after 60 s without an answered health check`, or why a start failed.

The `Description` section follows the basic facts of the node and prints each paragraph of its `manifest.description`, wrapped to the width of the terminal. `Exposed Interfaces` summarizes the topics, services, and actions the node publishes per its `peppy.json5`; consumed interfaces get their own `Consumed Interfaces` section, and a `Dependencies` section lists the slots (`link_id`) they go through. A node with parameters gets a `Parameters` section too, and labels or a container block add a `Labels:` or `Container:` line under `Node Information`; each is omitted when empty, as in the listing above. Under `Emitted Topics`, a native topic (one whose shape the node declares in its own `peppy.json5`) states its QoS, such as `message_stream` above. A native topic that retains its newest messages for subscribers that join later also states its retention, for example `  - robot_mode (qos: Reliable, retention: latest 3)`. A [contract-backed](/advanced_guides/contract_implementation/) or [pairing-backed](/advanced_guides/pairing/) topic names its slot instead of a QoS, for example `  - video_stream (via implements slot: cam)`. Its QoS comes from the contract or the pairing; a contract-backed topic takes its retention from the contract, and a pairing-backed topic is always live only. `Config SHA256` is the fingerprint of the config that was fed through peppygen; it's what `peppy node add` checks against to refuse a stale snapshot and tell you to run `peppy node sync`.

An instance of a node that declares [`execution.endpoints`](/guides/first_node/#serving-a-page-or-an-mcp-endpoint) lists each endpoint under its instance line as `label (kind)  url`, one line per URL:

```

```

## Calling a running instance

`peppy node describe <instance>` shows the topics, services and actions of a running instance with their descriptions and their message formats. `peppy node call <instance> <member>` calls one of its services or actions, and `peppy node echo <instance> <topic>` prints the messages of one of its topics, with no code of your own:

```sh
peppy node call camera_inst camera.set_brightness --set value=12
```

```text
{"outcome":"completed","response":{"applied":true}}
```

See [Calling a running instance](/advanced_guides/calling_instances/) for the names of the members, the flags that give a message, the output and the exit statuses.

## Stopping your node

When you're done, you can stop your node:

```sh
peppy node stop <instance-id>
```

This stops **one instance** of the `hello_world:v1` node, but the node itself remains in the node stack. `peppy node stop` also clears a `finished`, `failed` or `restarting` instance, and ends the start of an instance its [restart policy](/guides/launch_files/#restart-policy) is starting again; a first start in flight is refused until it completes.

Stopping is a **graceful-then-forced** operation, and the command blocks until the instance's process has actually exited:

1. The daemon asks the instance to shut down cooperatively and gives it a grace period (`shutdown_grace_secs`, 5 seconds by default; see [Daemon shutdown and orphan prevention](#daemon-shutdown-and-orphan-prevention)) for its cleanup to run. For a robot node this is its chance to park actuators, release hardware, and flush state. Inside the node, this ask fires the runtime's cancellation token and then runs the node's registered shutdown hooks; see [Graceful shutdown](/guides/first_node/#graceful-shutdown) for the quick-start and the [shutdown lifecycle guide](/advanced_guides/shutdown/) for the full node-side contract.
2. If the instance doesn't exit cooperatively in time (the grace window plus the brief teardown its runtime needs afterward), the daemon **force-kills its whole process group** (the node and any child processes it spawned), so nothing is left running.

If the instance had to be force-killed, `peppy node stop` warns you instead of reporting a clean stop:

```
WARN Node instance 'hello_world-...' did not shut down gracefully within the grace period and was force-killed
```

:::caution
A force-kill is abrupt: the node gets no chance to run its own shutdown logic. A node that must stop hardware cleanly should handle the cooperative shutdown signal and exit promptly within the grace period. The same graceful-then-forced sequence runs for every node when the daemon itself shuts down; see [Daemon shutdown and orphan prevention](#daemon-shutdown-and-orphan-prevention).
:::

## Removing your node

To remove the node from the node stack, run:
```sh
peppy node remove hello_world:v1
```

If the node still has tracked instances, pass `--stop-instances` (otherwise the command asks for confirmation). When stopping instances:

- The daemon sends a cooperative shutdown request to each running instance (or `SIGTERM` for containers whose shutdown service is unreachable) and waits until the force-kill deadline (`shutdown_grace_secs` plus runtime teardown, 12 seconds by default).
- Any instance still alive at the deadline has its entire process group force-killed, with a warning printed for each.
- If a shutdown request itself fails, the removal aborts without force-killing remaining instances; stop the failing instance manually with [`peppy node stop`](#stopping-your-node).
- If any instance is currently `starting` (or transitions to `running` after removal began), removal fails and names that instance; re-run `peppy node remove <name>:<tag> --stop-instances` once startup finishes.
