Launch files let you start multiple nodes simultaneously, including those with dependencies on each other. 
With a single launch file, you or your team can recreate an entire node environment using just one command.

## Running the example

Start by cloning [this repository](https://github.com/Peppy-bot/launchers-hub):

<Steps>
1. Clone the repository:
   ```sh
   git clone https://github.com/Peppy-bot/launchers-hub
   ```

2. Navigate into the directory:
   ```sh
   cd launchers-hub
   ```
</Steps>

In the `examples/` directory, you'll find a launcher file for each language. Opening it reveals the following structure:

<Tabs>
  <TabItem label="Python">
[`examples/python_robot.json5`](https://github.com/Peppy-bot/launchers-hub/blob/main/examples/python_robot.json5)
  </TabItem>
  <TabItem label="Rust">
[`examples/rust_robot.json5`](https://github.com/Peppy-bot/launchers-hub/blob/main/examples/rust_robot.json5)
  </TabItem>
</Tabs>

 1. The file is identified by `peppy_schema: "launcher/v1"` at the root: peppy uses this to distinguish launcher files from node `peppy.json5` files (which use `"node/v1"`)
 2. All deployments are defined in the `deployments` array
 3. Each deployment requires a `source` (the node to run, or the MCP exposures to serve) and an `instances` array (how many copies to start, and how each one is configured). Every entry needs an `instance_id`; `arguments`, `env_vars`, `framework`, `core_node`, and `links` are optional. See [Instance attributes](#instance-attributes) for what each one does

The `source` attribute references a node from your configured repositories by `name` and `tag`. Specify them as separate fields, or use the combined `name: "<name>:<tag>"` shorthand. The node is resolved against your local nodes cache at `~/.peppy/cache/nodes.json5`. A source can instead list [MCP exposures](/advanced_guides/mcp/) to serve, as shown [below](#serving-mcp-exposures).

If a node you want to deploy lives outside your configured repositories, add its location first: register a local directory with `peppy repo add /path/to/my/nodes`, or a git repository with `peppy repo add https://github.com/org/repo.git`. A repository states what it publishes through a committed `peppy_repository.json5`, so run `peppy repo index /path/to/my/nodes` to write it, and re-run it after adding, moving, or renaming a node, since the refresh reads the index rather than the filesystem. Then `peppy repo refresh` makes the nodes resolvable (see [Repositories](/advanced_guides/repositories/)).

:::note
The source resolves nodes from the locally cached index of the machine the launch is submitted to. Run `peppy repo refresh` on that machine before launching to ensure its cache is up to date. In a federated launch it is the only machine whose cache matters: it resolves every deployment and its dependencies once and ships the result to the other machines as pinned content, so their caches need no refresh and cannot change what the launch runs.

If a node or tag is missing from the cache, the launch fails with a "not found" error. If the cache instead contains the same `name:tag` **twice from one repository**, the launch fails with a distinct ambiguity error naming both manifests, never "not found", since the node is present rather than absent. The refusal happens while sources are being resolved, before anything is added, built, or run, and it covers transitive dependencies too: an ambiguity two levels down is exactly as fatal as one at the top. See [Using a repository-indexed node](/advanced_guides/repositories/#using-a-repository-indexed-node).
:::

```json5
// Repository source (long form)
{
  source: {
    name: "openarm01_controller",
    tag: "v1",
  },
  instances: [
    { instance_id: "the_nervous_system" }
  ]
}
```

```json5
// Repository source (combined shorthand, equivalent to the example above)
{
  source: {
    name: "openarm01_controller:v1",
  },
  instances: [
    { instance_id: "the_nervous_system" }
  ]
}
```

#### Serving MCP exposures

A deployment whose `source` lists `exposures` runs the MCP server built into `peppy` for them instead of a node. Each entry is an [MCP exposure](/advanced_guides/mcp/) as `"<name>:<tag>"`, resolved against `~/.peppy/cache/mcp_exposures.json5`, and the contracts the exposures reference resolve through the contracts cache. The daemon derives the server's node from those documents, so the deployment behaves like any other: its instances take `arguments` (the server's single `port`), `links` for the contract slots the exposures' targets become, and `core_node` for placement. The list must not be empty or repeat an exposure, and two deployments cannot list the same set.

```json5
// Exposure source: the built-in MCP server serving two exposures on one port
{
  source: {
    exposures: ["camera_and_recording:v1", "arm_status:v1"],
  },
  instances: [
    {
      instance_id: "mcp_server",
      arguments: { port: 8900 },
      links: { front_camera: "front_cam_inst", recorder: "recorder_inst", arm: "arm_inst" },
    }
  ]
}
```

:::caution
A git ref pinned in `repositories.json5` and the node `tag` declared in `peppy.json5` are independent values, and they do not share the same format: git refs can contain dots (e.g. `v0.1.0`), but node tags must start with an ASCII letter and forbid dots (e.g. `v1`, `donut`). This means a repository could be pinned to the git ref `v0.1.0` while `peppy.json5` specifies `tag: "v1"`. Keep them coordinated so a checkout of a given git ref lines up with the tag your launcher expects.
:::

  </TabItem>

```sh

```
  </TabItem>

### Launching from a repository

Launchers discovered by `peppy repo refresh` (see [Repositories](/advanced_guides/repositories/)) can be invoked by bare name, no path required:

```sh
peppy stack launch openarm01_sim_teleop
```

An argument that contains a path separator or ends in `.json5` is resolved as a filesystem path: `./my_launcher.json5`, `/abs/my_launcher.json5`, `my_launcher.json5`. A bare name (no separator, no extension) is a repository launcher and is never looked up on disk, whatever the current directory holds: `peppy stack launch my_launcher` resolves through the repository cache at `~/.peppy/cache/launchers.json5` even when a `my_launcher.json5` sits next to the caller. Run `peppy repo refresh` first on the machine you submit the launch to; the launcher document, like every repository source, resolves on that machine alone.

If the name resolves neither to a file nor to a cached launcher, the launch fails with an explicit "not found" error. If one repository provides two launcher files with that name, the launch fails with a distinct ambiguity error naming both: launchers are keyed by filename, so two identically named `.json5` files anywhere in one repository contest the same name even in different directories.

:::caution
Running the `peppy stack launch` command clears the existing node stack and stops all running instances
:::

The `Instance bindings` table breaks that down per instance: the consumers (`fake_robot_brain`, `fake_video_reconstruction`) list the `depends_on` slots they resolved, while the producers (`fake_openarm01_controller`, `fake_uvc_camera`) and the core node declare no slots and show `(none)`. A resolved binding shows the chosen producer(s) as `instance_id@core_node`, ordered by link ID; a multi-cardinality slot lists every bound member in binding order, and an empty slot, whether a `zero_or_more` slot bound to nothing or a `zero_or_one` slot declared vacant, shows `(empty set)`. Every declared producer slot (`depends_on.nodes` / `depends_on.contracts`) is either bound or, where its manifest declares `cardinality: "zero_or_one"`, declared [`vacant`](#links-optional); only a `zero_or_more` slot may be left out entirely, and a launcher that leaves any other one out is rejected at validation (see [dependency cardinality](/advanced_guides/topics/#dependency-cardinality)). Pairing and observer slots follow the same shape: a participant slot is paired or, where its manifest declares it `optional: true`, declared vacant; an observer slot is linked or, where its manifest declares it `cardinality: "zero_or_one"`, declared vacant, unless its cardinality is `zero_or_more`, where omitting it IS its empty set. The launch also prints a `Slice of launch ...` line above the tables naming the launch that produced this stack and its coordinator.

## Instance attributes

Every entry in an `instances` array configures one running copy of the deployment's node. Two instances of the same node are independent: they get their own arguments, their own environment, and their own bindings.

```json5 title="peppy_launcher.json5"
{
  source: { name: "uvc_camera:v1" },
  instances: [
    {
      instance_id: "camera_front",
      arguments: { device: { path: "/dev/video0" }, frame_rate: 30 },
      env_vars: { GST_DEBUG: "2" },
      framework: { use_sim_time: false },
    },
    {
      instance_id: "camera_rear",
      arguments: { device: { path: "/dev/video1" }, frame_rate: 15 },
    },
  ],
}
```

### `instance_id` (required)

The name this copy runs under. It labels the instance in `peppy stack list`, in its log file, and in every `links` value that points at it.

Allowed characters are letters, digits, `_` and `-`. The id must be unique across the whole stack, not just within its own deployment: two deployments cannot both declare `camera_front`, and no instance may take the core node's own id. A collision is reported before anything starts.

### `arguments` (optional)

Values for the parameters the node declares in its `execution.parameters` block, written with the same nesting as that schema. See the [Parameters reference](/reference/parameters/) for the full syntax.

A parameter that declares a `$default` may be omitted, and the daemon fills it in before the node starts. A required parameter left without a value fails the launch as that instance starts, naming the leaf it is missing (`Missing required parameters: device.serial`). Unknown keys and type mismatches are caught by the node itself as it boots, so they surface as that instance failing to come up.

A [container node](/advanced_guides/containers/) can also reference these values in its `mount_paths` with `${parameters:<path>}`, which is how two instances of one node mount two different host devices.

### `env_vars` (optional)

Environment variables for this instance's process.

`peppy stack launch` forwards a filtered copy of your shell environment to the instances it starts on the machine you launch from, so a node there already sees your `PATH` and the rest. The filter drops `PWD`, `OLDPWD`, `TMPDIR`, `TEMP`, `TMP`, `PYTHONPATH`, and `PYTHONHOME`, plus any name that is not a shell identifier, any value with whitespace or shell metacharacters, and the injection-prone names listed below. `PYTHONPATH` and `PYTHONHOME` are stripped so a caller shell that exports them cannot displace a container node's vendored `peppylib`/`peppygen` path; a node that genuinely needs either sets it through its own `env_vars`. An instance placed on another machine receives only its declared `env_vars`. `env_vars` is layered on top of the forwarded set for what differs per instance (a device path, a board serial, a log level), and a name declared here replaces the forwarded value:

```json5
{
  source: { name: "esp32_board:v1" },
  instances: [
    { instance_id: "esp32_left",  env_vars: { ESP32_DEVICE: "/dev/ttyUSB0" } },
    { instance_id: "esp32_right", env_vars: { ESP32_DEVICE: "/dev/ttyUSB1" } },
  ],
}
```

Entries are checked when the launcher file is read, before the running stack is touched:

- **Names** must be shell identifiers: a letter or `_` first, then letters, digits and `_`. `ESP32_DEVICE` is fine, `esp32-device` is not.
- **Values** may hold letters, digits and `` _ - . / : , = @ + % ``. Whitespace, quotes and shell metacharacters (`;`, `$`, `` ` ``, `|`, and friends) are rejected, so a value like `"--flag other"` has to reach the node another way, typically as an [argument](#arguments-optional).
- **Injection-prone names** are rejected outright: the dynamic-linker and shell hooks (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `BASH_ENV`, `IFS`, and the rest of that family).

:::note
The name and value rules exist because a container node receives its environment through Apptainer, which writes each variable unquoted into a script the container sources at startup. A name or value that does not survive that step would take `PEPPY_RUNTIME_CONFIG` down with it and leave the node running on its standalone defaults. The same rule applies to process nodes so that adding a `container` block to a node later cannot break the launchers that already deploy it.
:::

`env_vars` reach the instance when it starts. Fetching and building a node happen once for the node, not once per instance, so a variable your build needs (a registry token, a toolchain path) belongs in the shell you run `peppy stack launch` from, where it is forwarded to build steps on that machine too. A build on another machine sees none of your caller environment: your environment describes your machine, so it stays there.

### `framework` (optional)

Framework knobs owned by peppylib rather than by the node author, so they mean the same thing for every node. The block holds two knobs:

- `use_sim_time`: read the clock from a simulator or bag replay instead of the daemon's wall clock. Omitting it falls through to the daemon's `--clock-source` flag (which defaults to `wall`). The two directions are not symmetric: `false` forces wall time on a daemon serving simulated time, while `true` needs a daemon started with `--clock-source=sim` and is refused on one serving wall time, because that daemon's own ticks land on the key the instance would read. See [System clock](/advanced_guides/system_clock/#sim-and-replay-clocks).
- `publishes_sim_time`: this instance is the launch's source of simulated time. On a simulated launch it is handed every machine the launch runs on, and its `SimTimePublisher` feeds each machine's `clock` topic so a fleet shares one instant; on a wall-time launch it publishes nothing, so the same launcher works either way. At most one instance per launch may declare it, refused otherwise, and a simulated launch names its declared source in the launch feedback. See [One clock across a fleet](/advanced_guides/system_clock/#one-clock-across-a-fleet).

An unknown key inside `framework` is an error rather than a no-op, so a typo like `use_simulation_time` fails the launch instead of silently leaving the instance on wall time.

### `core_node` (optional)

The machine this instance runs on, named by one of the placeholders the launcher declares under `core_nodes`. An instance that omits it runs on the daemon you launched from. See [Running one launcher across several machines](#running-one-launcher-across-several-machines).

### `links` (optional)

One map filling every kind of `depends_on` slot the node declares, keyed by the slot's `link_id`. A value is interpreted against the slot it names:

- a producer slot (`depends_on.nodes` / `depends_on.contracts`) takes the producer instance to bind: a scalar for a `one` or `zero_or_one` slot, an array for a multi-cardinality slot;
- a [pairing](/advanced_guides/pairing/) participant slot takes a single peer instance, `"<peer>"` or `"<peer>/<peer_link_id>"` to disambiguate which of the peer's slots to use;
- an [observer](/advanced_guides/pairing/#observing-several-pairings-through-one-slot) slot takes the source instance(s) to observe, each `"<source>"` or `"<source>/<source_link_id>"`: a scalar for a `one` slot, an array for a multi-cardinality slot, in the order the node reads them back.

A slot that starts unresolved on purpose says so here too, as `{ vacant: "<why>" }`. That value binds nothing and covers the slot, so the fate of every declared slot is one entry in this one map and a slot you forgot is an absence rather than a value. The reason is required, is trimmed, and travels with the instance, so `peppy stack launch` reports it back when the node starts.

Vacancy is a two-sided contract, and the node owns one side of it. A slot is vacatable only where the node's own manifest declares it emptiable, one key per slot kind: `optional: true` on a `depends_on.pairings` entry, or `cardinality: "zero_or_one"` on a `depends_on.pairing_observers`, `depends_on.nodes` or `depends_on.contracts` entry. On a slot the manifest declares required, a vacancy is rejected and the error names the manifest key that would lift the bar. Every other slot is rejected with the spelling it does have: a `zero_or_more` slot, producer or observer, writes its empty set as `[]` (or omits the key), and a `one_or_more` slot of either kind has no empty state at all. The manifest says "may be empty", the launcher says "is empty here, because", and forgetting the slot entirely stays an error whichever the manifest says.

One instance filling all three kinds, plus a slot left deliberately empty:

```json5
{
  source: { name: "session_recorder:v1" },
  instances: [
    {
      instance_id: "rec_1",
      links: {
        // Producer slots: `storage` is `one`, `cameras` is multi-cardinality.
        storage: "disk_1",
        cameras: ["cam_left", "cam_right"],
        // A participant slot names the peer to pair with, with
        // `/<peer_link_id>` when the peer declares more than one slot.
        arm: "arm_1/limb",
        // A scalar observer slot names a single source instance to observe.
        // The multi cardinalities take these same values in an array.
        watch: "ctrl_1",
        // A slot this deployment leaves empty on purpose, and why. The
        // manifest declares `gripper` `optional: true`, which is what makes
        // this legal.
        gripper: { vacant: "bench rig: no gripper on this frame" },
      },
    },
  ],
}
```

Every target must name an `instance_id` declared somewhere in the same launcher.

Two instances of the same node can choose different fates for the same slot, which is why the decision is written per instance rather than in the node's manifest (whose `optional: true` on this slot only says that some deployment may make it):

```json5
instances: [
  {
    instance_id: "backbone_governed",
    links: { leader_left_arm: "commander_inst/left_arm" },
  },
  {
    instance_id: "backbone_monitor",
    links: { leader_left_arm: { vacant: "monitor rig: nothing commands this backbone" } },
  },
]
```

## Reusing built nodes across launches

Every node build a launch performs goes through the [build artifact cache](/advanced_guides/containers/#build-caching): when a deployment's staged sources match an earlier build byte for byte, and that build ran with the same peppy version, OS, architecture and artifact kind, the launch reuses its artifact. Launching the same launcher again, after a daemon restart or on another machine booted from the same disk, therefore spends seconds on the build phase instead of rebuilding every node. Each reuse is reported in the launch output and in that node's build log:

```
Reusing cached build of waldo:v1 (fingerprint 3f9a1c2e5d7b8a4f) at ~/.peppy/built_nodes/waldo_v1/3f9a1c2e5d7b8a4f.sif
```

`peppy stack launch --rebuild` builds every node of the launch from its staged sources even when a matching artifact exists, on the coordinator and on every peer; use it when something the fingerprint does not cover changed, such as the image behind a floating base image tag.

## Running one launcher across several machines

A launcher can span machines. It declares named placeholders under `core_nodes`,
each instance says which one it runs on via `core_node`, and
`peppy stack launch --place <core-node-link>@<core-node>` binds those
placeholders to real hardware at launch time. Producer links, pairings, and
observations all work across the boundary, and consumers still start after their
producers. See [Federation](/advanced_guides/federation/).

Every placeholder the launcher declares must be bound with `--place`; a launch
that leaves one unwired is refused. The escape hatch is
`peppy stack launch --local`, which ignores the launcher's placements and runs
every instance on the daemon you launched from. `--local` and `--place` are
mutually exclusive.

## Swapping parts at launch time

A launcher file can describe a family of stacks whose members differ in which implementation fills a slot: a real robot or a simulator, a browser panel or a headset, with or without a recorder. The launcher declares **component axes**, `deployments` says which option of each it starts, and the launch command swaps one with `--with`. A launcher without `components` is a plain flat stack, and that stays the ordinary way to write a one-off.

The whole feature fits in one file. Here is a viewer stack with two swappable cameras:

<Code code={viewerLauncher} lang="json5" title="viewer.json5" />

```sh
peppy stack launch ./viewer.json5              # runs the camera the file deploys (uvc)
peppy stack launch ./viewer.json5 --with=zed   # runs the ZED camera instead
```

Components declare what may run; `deployments` says what runs. An axis entry has four fields:

| Field | Meaning |
|---|---|
| `name` | The axis's name, unique in the launcher. Used in `--with axis=option`, in `deployments`, and in adjustment guards. |
| `options` | The alternatives that fill this axis, at least one. Each option is a fragment: a body using the same `deployments` grammar the launcher's own `deployments` use, written inline or in its own [file](#fragments-splitting-a-launcher-across-files). |
| `cardinality` | How many selections of the axis a stack allows. `one` (the default): exactly one option runs. `zero_or_one`: at most one. `zero_or_more`: any number, each a named [copy](#copies). |
| `provides` | Instance IDs every option defines, so a link written against one is valid whichever option is selected. On a `zero_or_more` axis the IDs are checked as written, before a copy's name prefixes them. |

A `deployments` entry deploys a node, `{ source, instances }`, or a component's option, `{ <component>: "<option>" }`:

- On a `one` axis the entry names the option that runs, ids as written, and `--with` swaps it for another option of that axis. A `one` axis the file does not deploy must be named with `--with`.
- A `zero_or_one` axis is never deployed by the file, since nothing on the command line could switch it off. `--with` turns it on. A feature that is on by default and switchable is a `one` axis with a `none` option (its body can be empty), deployed by the file and swapped off with `--with none`.
- On a `zero_or_more` axis the entry lists the copies that run, each under `instances` with a name; see [copies](#copies). `--with` cannot name one, since a copy needs a name.

Each `--with` entry is either `option` (looked up across every axis in reach) or `axis=option`. A bare word matching options on more than one axis is refused, naming the axes, so `axis=option` says which you mean. An axis takes one option; repeating it, or naming it once bare and once as `axis=option`, selects it once. The `default` and `optional` keys are refused: the file's `deployments` entry is the default, and `cardinality: "zero_or_one"` is what optional means. On `stack launch`, `NAME.option` or `NAME.axis=option` selects the own axis of a copy the file deploys, over the file's `with`.

A launch of a launcher with components echoes the full resolution before anything runs, marking the axes the file filled:

```
components: simulation=waldo (from file)  scene_commander=(off)
copy alpha: robot=openarm_v2_sim  robot_commander=web_commander  recorder=(off)  camera_rig=(off)
```

Passing `--with` to a launcher that declares no `components` is refused.

## A fragment's own axes

An option's fragment can declare `components` of its own: the axes that belong to that option. An OpenArm robot fragment declares its robot commander and its recorder, and deploys the browser panel unless told otherwise:

```json5
// fragments/openarm_v2_sim.json5
{
  peppy_schema: "launcher_fragment/v1",
  deployments: [
    { source: { name: "openarm_sim_arm", tag: "v1" }, instances: [ /* ... */ ] },
    { control: "control_common" },
    { robot_commander: "web_commander" },
  ],
  components: [
    { name: "control", provides: ["init_inst", "backbone_inst"],
      options: { control_common: "control_common.json5" } },
    { name: "robot_commander", provides: ["commander_inst"],
      options: { web_commander: "web_commander.json5", xr_commander: "../../robot_commanders/fragments/xr_commander.json5" } },
    { name: "recorder", cardinality: "zero_or_one", provides: ["recorder_inst"],
      options: { lerobot_recorder: "../../recording/fragments/lerobot_recorder.json5" } },
  ],
}
```

A fragment's axes are `one` or `zero_or_one`; how many robots run is the launcher's `robot` axis. They are in reach whenever the fragment runs once: on the SO-101 launcher, whose `robot` axis is `one`, `--with xr_commander` reaches into the robot's fragment, and `--with robot_commander=xr_commander` says so explicitly. A fragment's `adjustments` and `constraints` speak in its own axis names and the launcher's, so the recorder's shape guard and the "cameras need a consumer" rule live beside the axes they speak about, and a v1 robot's "MuJoCo or Isaac Sim" requirement names the launcher's `simulation` axis. A launcher's own `adjustments` and `constraints` speak in the launcher's axis names. A fragment two levels below the launcher declares no axes: an option of a fragment's axis is a plain fragment.

## Copies

An axis with cardinality `zero_or_more` runs as **copies**: named instances of one of its options, exactly as a node runs as named instances. The launcher's `deployments` list the copies a launch starts, `peppy stack join` adds one to a running stack, and `peppy stack remove` takes one out. Every instance a copy's fragments define is minted as `NAME_<id>`, so any number of copies run side by side under one launcher.

The simulated OpenArm fleet holds the simulation as a `one` axis, and the robot as copies:

```json5
components: [
  { name: "simulation", provides: ["simulation_inst"],
    options: { mujoco: "...", isaac_sim: "...", waldo: "..." } },
  { name: "robot", cardinality: "zero_or_more",
    options: { openarm_v1_sim: "...", openarm_v2_sim: "..." } },
],
deployments: [
  { simulation: "waldo" },
  { robot: "openarm_v2_sim", instances: [
      { instance_id: "alpha", with: { robot_commander: "web_commander" },
        arguments: { commander_inst: { http_port: 8765 } } },
  ] },
],
```

A copy entry has four fields: `instance_id`, the copy's name; `with`, the selection of the option's own axes, an axis left out taking what the fragment deploys; `arguments`, overrides of the copy's instances' arguments, keyed by the id written in the fragment and then by argument; and `adjustments`, the fragment verbs over the copy's instances. The option entry itself takes `with` and `arguments` too, shared by every copy it lists, and a copy's own values win per axis and per argument:

```json5
{ robot: "openarm_v2_sim", with: { robot_commander: "xr_commander" }, instances: [
    { instance_id: "alpha" },
    { instance_id: "bravo", arguments: { commander_inst: { https_port: 4444 } } },
] },
```

An entry and a copy also take `adjustments`, the same verbs a fragment's adjustments use (`set_arguments`, `set_links`, `add_links`, `unset_links`) with an optional `when` over the launcher's axes and the copy's own, targeting the copy's instances by the ids written in the fragment. They run after the launcher's adjustments, the entry's before the copy's, and the copy's `arguments` last. On `stack launch`, a `--with` word `NAME.axis=option` or `NAME.option` selects one file copy's own axis for that launch, over the file's `with`:

```sh
peppy stack launch simulation --with mujoco,alpha.xr_commander
```

One robot, two robots, many:

```sh
# The simulation and the copies the file deploys.
peppy stack launch simulation

# The same copies in MuJoCo.
peppy stack launch simulation --with mujoco

# Another robot in place of the first, on another machine, then its removal.
peppy stack remove alpha
peppy stack join openarm_v2_sim -i bravo --with xr_commander --place bravo@jetson-2
peppy stack list
peppy stack remove bravo

# A stack with no robot yet, then robots as they arrive.
peppy stack launch fleet
peppy stack join openarm_v2 -i alpha --place alpha@jetson-1
peppy stack join openarm_v1 -i bravo --with xr_commander --place bravo@jetson-2
```

`stack join` names the option to copy and, with `-i`, the copy's name, the way `node run` names a node and an instance. Its `--with` words select the copied option's own axes. Every instance the copy's fragments define receives the name as a prefix: `alpha_left_arm_inst`, `alpha_backbone_inst`, `alpha_commander_inst`. Every link naming one of them follows it under the prefix, including array links and pairing targets such as `alpha_backbone_inst/leader_left_arm`; links to stack instances such as `simulation_inst` keep their IDs. The name is also the copy's core node link: `--place alpha@jetson-1` runs the whole copy there, at launch or at join, and a copy with no placement runs on the coordinator.

`--set-arguments INSTANCE.ARGUMENT=JSON5` on `stack join` overrides one argument of one of the copy's instances, named as the fragment writes it, the way a copy entry's `arguments` does in the file. It applies after every adjustment, once per argument. Numbers must be finite; quote string values:

```sh
peppy stack join openarm_v2 -i charlie --with xr_commander \
  --set-arguments backbone_inst.max_ee_velocity_m_s=0.2 \
  --set-arguments commander_inst.https_port=4444
```

A launch snapshots its launcher and fragment files, and every join composes against that snapshot; launch again to load edits. Constraints see the stack's selection and the copy's together, so `openarm_v1_sim` on a Waldo stack is refused at join with the v1 fragment's reason. A copy's adjustments may write to a stack instance, and each field they write is what the copy needs of it: two copies deployed together must agree on every field they both write, and a join may write to a stack instance only what already runs there, except that its relays may pair into the slots the instance declares vacant: the relay's own `links` name the slot, and the copy's fragment releases the vacancy with `unset_links` on the instance. A join that would change a running instance is refused, naming the instance and each field that differs. That is why the OpenArm v1 simulation, which sets the simulation's hardware generation, and the rendered camera rig, which turns the simulation's rendering on, are selected in the file at launch.

One simulation per stack, and the simulations available today pair with one simulated robot: the simulated fleet ships one copy, and a second simulated robot in one simulation is refused where its relays reach for limb slots the first one paired, so remove the first before joining the second. Physical robots join beside a simulated one.

`stack remove NAME` stops the copy's instances in reverse dependency order and takes it out of the stack; a copy another copy links to is refused until that copy goes first, and a copy the stack's own instances link to stays until the next launch. Removal leaves the stack's own instances running: removing the simulated robot leaves the simulation up with its model loaded, and `stack reset` stops everything. A failed join stops what it started, removes the nodes it added, and reports the failure; when that cleanup itself fails the copy stays in `stack list` and the message says to retry `stack remove`.

`stack list` names each copy, the option it copies, its host, its selection and its instances; `stack list --json` carries the same under `copies`. Preview a launch, or a join onto it, without starting anything:

```sh
peppy stack resolve simulation --with mujoco
peppy stack resolve fleet --join openarm_v1 --join-name bravo --join-with xr_commander
```

Join and remove run on the coordinator (`--core-node NAME` reaches it from another machine), serialize with launches and with each other, and reserve only the machines they touch: an unrelated host that is offline blocks neither. A reset cancels the operation in flight, waits for its cleanup, and empties the stack. A restarted coordinator has no launcher to compose against; launch again before joining.

`peppy repo index --check` composes every legal selection the way a launch does: the stack under every selection of its axes, then every copy a `zero_or_more` axis can add, as a launch beside the stack and as a join onto it.

## Adjustments

A family of stacks often needs more than swapped deployments: the recorder attaches itself to whichever commander was selected, and the headset flips a mode argument on the backbone. An **adjustment** names one instance defined elsewhere and one change to it, and every change names its operation:

```json5
adjustments: [
  {
    target: "backbone_inst",              // the instance to change
    when: { robot_commander: "xr_commander" },  // optional guard, see below

    set_arguments: { upstream_mode: "pose" },
    set_links: { collision_ctrl: { vacant: "the headset never produces governor_control" } },
    add_links: { recorder: ["recorder_inst"] },
    unset_links: ["leader_left_arm_pose"],
  },
]
```

| Operation | Effect |
|---|---|
| `set_arguments` | Replaces the target's value for each named argument key, creating it when absent. Nested objects replace wholesale. |
| `set_links` | Replaces the target's whole entry for each named slot, creating it when absent. The value uses the ordinary [links](#links-optional) grammar, including vacancies. |
| `add_links` | Appends targets to each named slot's array binding, creating the binding when the slot has no entry. Refused when the slot holds a scalar or a vacancy: replacing is `set_links`'s job. Appending is what lets independent fragments each contribute bindings to one multi-cardinality slot. |
| `unset_links` | Drops each named slot's entry entirely, returning the slot to absent. |

Fragments refuse to fight: two selected fragments writing the same argument key or the same slot on one target are refused, naming both. The launcher's own top-level `adjustments` apply after all fragment adjustments and may override anything a fragment set, which is how one launcher specializes fragments it shares with another. Within the launcher's own list, a later entry wins over an earlier one: both lines live in one file one author edits. A launcher adjustment guarded on a `zero_or_more` axis applies to every copy of the matching option, its target resolved inside each copy.

An adjustment whose target the current selection does not define is **skipped**, not refused: the recorder's attach simply does not run when no recorder was selected. A target no option of the launcher defines anywhere is a dead reference and fails when the launcher is read. `when` guards are for conditions existence cannot express, mostly shape: two leaders may both provide `commander_inst`, but only one of them has camera slots. A launcher's guards name the launcher's axes; a fragment's name its own axes and the launcher's. Each axis accepts an option name or a nonempty list of option names. Lists match **any** listed option (OR); **every** named axis must match (AND).

For example, the OpenArm real-robot fragment binds physical-driver alerts for either commander that consumes alerts:

```json5
when: { robot_commander: ["web_commander", "xr_commander"] }
```

This guard matches both, and the MCP commander does not match. The same scalar-or-list syntax applies inside constraint `when`, `requires`, and `forbids` conditions.

The ownership rule of thumb: if a value is something the operator genuinely decides, make it another option on the axis, visible in the command line. If it is a *consequence* of a choice already made, write the adjustment into that option's own fragment, where it needs no guard: it runs exactly when its fragment is selected and skips when its target is absent.

## Constraints

Adjustments change what a selection builds; a **constraint** refuses selections nobody should run. Some members of a family are stacks no operator should be able to name: the ZED camera that films only the physical rig must not launch against the simulator. Those members flatten cleanly, so neither `provides` (which only promises ids exist) nor an adjustment's `when` guard (which only decides whether one adjustment applies inside a legal selection) can say it. A constraint can, and it only ever refuses: a violating selection is rejected before anything is pinned or started. It never picks an option to satisfy itself, because a `--with` whose meaning shifted as constraints evolve would launch stacks the operator did not name.

```json5
constraints: [
  // With the ZED camera selected, the robot must be the real one.
  { when: { camera: "zed" }, requires: [{ robot: "real" }],
    reason: "the ZED films the physical rig" },

  // The whole combination is refused, no guard needed.
  { forbids: [{ robot: "mujoco", camera: "zed" }],
    reason: "the stereo camera pairs with the real rig only" },
]
```

| Field | Meaning |
|---|---|
| `when` | The guard: the selections this constraint speaks about, in the same `axis: options` grammar as an adjustment's `when`: every named axis holds one of its listed options (an AND across axes, an OR within one). Omit it to speak about every selection. |
| `requires` | What the guarded selections must also contain: a list of alternatives, at least one of which must match wholly. Each alternative is an `axis: options` map where every axis must match (an AND); listing several alternatives is an OR. |
| `forbids` | What the guarded selections must not contain: a list of `axis: options` maps, and matching any one of them (each an AND of its axes) refuses the selection outright. |
| `reason` | Why the refused selections must not run. Required, and quoted verbatim in the refusal: peppy can render what was required or forbidden, but only the author knows what the dead combination would have done. |

A constraint states at least one of `requires` and `forbids`; with neither it refuses nothing, and the document is refused when it is read. The rest of the shape is held to the same standard: `when` and every entry name at least one axis, an entry may not repeat an axis the guard already fixes (under the guard that axis is decided before anything is selected), the same map may not be listed twice in one list, and one map may not appear in both lists.

Matching treats an unfilled axis as matching no entry, on either side: a guard on `camera: "zed"` stays quiet when the camera axis is off, and a `requires` alternative naming that option is satisfied only by selecting it, never by leaving the axis unfilled. That asymmetry is the tool for optional features: `requires` is how an option demands company, while `forbids` is the only way to say an optional option never launches with another one (nothing requirable means "that axis stays off"). Where the axis is required, prefer `requires` of the wanted option instead: `requires` fails closed for options added later, while a `forbids` list names today's options and stays silent about tomorrow's.

The refusal happens at selection time and names the document that declared the constraint, the full resolution (with its `(from file)` markers showing the axes the operator never named), what was required or forbidden, and the author's `reason`. When several constraints overlap, the first declared one refuses, so the author controls which reason the operator reads.

A launcher's constraints speak in the launcher's axis and option names; a fragment's speak in its own axes and the launcher's, which is where a rule about an option's own axes belongs. `peppy repo index --check` holds them to leaving a usable family behind: a constraint that refuses no selection, an option no legal selection can pick, and a bare launch that violates a constraint are each reported when the launcher is indexed.

## Fragments: splitting a launcher across files

An option's body can live in its own file, called a **fragment**. This is an organizational choice, never a requirement: a launcher whose options are all inline is self-contained. Extract a fragment once a second launcher wants the same body, so the body is stated once.

A fragment file carries the `launcher_fragment/v1` tag:

<Code code={zedCameraFragment} lang="json5" title="fragments/zed_camera.json5" />

The launcher references it by path, and the option value becomes that path string:

```json5
options: {
  uvc: { deployments: [ /* inline, as above */ ] },
  zed: "fragments/zed_camera.json5",
}
```

Fragment paths are relative to the declaring document's directory: the launcher's for its options, the fragment file's for the options of its own axes. Inside a Peppy repository, the nearest ancestor containing a valid `peppy_repository.json5` sets the boundary: `openarm/fragments/openarm_v2_sim.json5` can include `../../robot_commanders/fragments/xr_commander.json5`. Parent segments and resolved symlinks must stay within that repository. Standalone launchers use their own directory as the boundary. Absolute paths are rejected. Repository names and filesystem paths use the same resolution rules.

Two options can share one body with the list form, which merges its parts in order before the option contributes anything:

```json5
options: {
  mujoco: ["fragments/relays.json5", "fragments/mujoco.json5"],
  isaac_sim: ["fragments/relays.json5", "fragments/isaac_sim.json5"],
}
```

The parts of one option declare its axes between them, each axis once, and deploy each of those axes once. Besides `deployments`, `components`, `constraints` and `adjustments`, a fragment may declare `core_nodes`: additional placement placeholders its instances need, unioned with the launcher's own, so selecting the option makes the matching `--place` bindings required exactly as if the launcher declared them.

A fragment is not a stack. The repository indexer never lists a fragment as a launchable launcher, it needs no entry in `peppy_repository.json5`, and it cannot collide with a launcher name. `peppy repo index --check` validates every fragment a launcher references and flattens every legal selection of its axes, so a broken combination is refused on the branch that introduced it.

## Auditing a composed launch

Composition changes instances from a distance, so it ships with an audit command:

```sh
peppy stack resolve so101 --with xr_commander,lerobot_recorder
```

`stack resolve` needs no running stack. It prints the flattened `launcher/v1` document to stdout and a resolution report to stderr. An excerpt:

```
components: robot=so101 (from file)  robot_commander=xr_commander  recorder=lerobot_recorder  camera_rig=(off)

adjustments applied:
  backbone_inst.arguments.upstream_mode: "joints" -> "pose"  (fragments/so101.json5)
  recorder_inst.arguments.robot_type: (absent) -> "so101"  (fragments/so101.json5)
  commander_inst.links.recorder: + recorder_inst  (../recording/fragments/lerobot_recorder.json5)

link rules hold: slot keys, vacancies and pairing coverage checked over 6 node manifest(s)
```

Every applied adjustment is listed with the value it replaced and the fragment it came from, and every skip says why. Because stdout is a plain launcher, it doubles as the escape hatch: flatten, hand-edit, launch the flat file. A launcher that deploys copies resolves with them, one `copy NAME:` line each, and `--join OPTION` previews one more joined onto it, with `--join-name`, `--join-with` and `--join-set-arguments` standing in for the join's own flags. The resulting flat launcher declares each copy's name in `core_nodes`; launch that file with `--place NAME@CORE_NODE` or `--local`.

The report ends by holding the flat plan to the launch-time link rules that need no daemon. `stack resolve` reads this machine's nodes cache at `~/.peppy/cache/nodes.json5`, loads each deployed node's manifest, and checks slot-key legality, vacancies, and pairing coverage across them; the `link rules hold` line names how many manifests it checked. The contract-binding rules stay launch-only, because satisfying them can involve the root node that only a running daemon knows. When the plan breaks a rule a launch would reject, say an optional pairing slot left neither paired nor vacant, `stack resolve` fails with that launch's own error instead of surfacing it minutes later at launch. When a manifest cannot be read locally the check is skipped rather than run on a partial picture: the report says `link rules not checked`, names the missing manifest, and advises `peppy repo refresh` when the cache is empty or unreadable.
