Launch files let you start multiple nodes simultaneously, including those with dependencies on each other. 
With a single launch file, you or your team can recreate an entire node environment using just one command.

## Running the example

Start by cloning [this repository](https://github.com/Peppy-bot/launchers-hub):

<Steps>
1. Clone the repository:
   ```sh
   git clone https://github.com/Peppy-bot/launchers-hub
   ```

2. Navigate into the directory:
   ```sh
   cd launchers-hub
   ```
</Steps>

In the `examples/` directory, you'll find a launcher file for each language. Opening it reveals the following structure:

<Tabs>
  <TabItem label="Python">
[`examples/python_robot.json5`](https://github.com/Peppy-bot/launchers-hub/blob/main/examples/python_robot.json5)
  </TabItem>
  <TabItem label="Rust">
[`examples/rust_robot.json5`](https://github.com/Peppy-bot/launchers-hub/blob/main/examples/rust_robot.json5)
  </TabItem>
</Tabs>

 1. The file is identified by `peppy_schema: "launcher/v1"` at the root: peppy uses this to distinguish launcher files from node `peppy.json5` files (which use `"node/v1"`)
 2. The `description` at the root says what the launcher starts and what it needs to run, such as a GPU, hardware or a simulation, as a list of paragraphs. It is required, and its first paragraph is the summary that `peppy repo search` prints. A launcher has no manifest, so its description sits at the root (see [Descriptions](/reference/concepts/#descriptions)). A [fragment](#fragments-splitting-a-launcher-across-files) has no description
 3. All deployments are defined in the `deployments` array
 4. Each deployment requires a `source` (the node to run, or the MCP exposures to serve) and an `instances` array (how many copies to start, and how each one is configured). Every entry needs an `instance_id`; `arguments`, `env_vars`, `env_from_launch`, `framework`, `core_node`, and `links` are optional. See [Instance attributes](#instance-attributes) for what each one does

The `source` attribute references a node from your configured repositories by `name` and `tag`. Specify them as separate fields, or use the combined `name: "<name>:<tag>"` shorthand. The node is resolved against your local nodes cache at `~/.peppy/cache/nodes.json5`. A source can instead list [MCP exposures](/advanced_guides/mcp/) to serve, as shown [below](#serving-mcp-exposures).

If a node you want to deploy lives outside your configured repositories, add its location first: register a local directory with `peppy repo add /path/to/my/nodes`, or a git repository with `peppy repo add https://github.com/org/repo.git`. A repository states what it publishes through a committed `peppy_repository.json5`, so run `peppy repo index /path/to/my/nodes` to write it, and re-run it after adding, moving, or renaming a node, since the refresh reads the index rather than the filesystem. Then `peppy repo refresh` makes the nodes resolvable (see [Repositories](/advanced_guides/repositories/)).

:::note
The source resolves nodes from the locally cached index of the machine the launch is submitted to. Run `peppy repo refresh` on that machine before launching to ensure its cache is up to date. In a federated launch it is the only machine whose cache matters: it resolves every deployment and its dependencies once and ships the result to the other machines as pinned content, so their caches need no refresh and cannot change what the launch runs.

If a node or tag is missing from the cache, the launch fails with a "not found" error. If the cache instead contains the same `name:tag` **twice from one repository**, the launch fails with a distinct ambiguity error naming both manifests, never "not found", since the node is present rather than absent. The refusal happens while sources are being resolved, before anything is added, built, or run, and it covers transitive dependencies too: an ambiguity two levels down is exactly as fatal as one at the top. See [Using a repository-indexed node](/advanced_guides/repositories/#using-a-repository-indexed-node).
:::

```json5
// Repository source (long form)
{
  source: {
    name: "openarm01_controller",
    tag: "v1",
  },
  instances: [
    { instance_id: "the_nervous_system" }
  ]
}
```

```json5
// Repository source (combined shorthand, equivalent to the example above)
{
  source: {
    name: "openarm01_controller:v1",
  },
  instances: [
    { instance_id: "the_nervous_system" }
  ]
}
```

#### Serving MCP exposures

A deployment whose `source` lists `exposures` runs the MCP server built into `peppy` for them instead of a node. Each entry is an [MCP exposure](/advanced_guides/mcp/) as `"<name>:<tag>"`, resolved against `~/.peppy/cache/mcp_exposures.json5`, and the contracts the exposures reference resolve through the contracts cache. The daemon derives the server's node from those documents, so the deployment behaves like any other: its instances take `arguments` (the server's single `port`), `links` for the contract slots the exposures' contract targets become, and `core_node` for placement. A [daemon target](/advanced_guides/mcp/#daemon-targets) takes no link: the instance gives it a scope in [`daemon_scopes`](#daemon_scopes-optional). The list must not be empty or repeat an exposure, and two deployments cannot list the same set.

```json5
// Exposure source: the built-in MCP server serving two exposures on one port
{
  source: {
    exposures: ["camera_and_recording:v1", "arm_status:v1"],
  },
  instances: [
    {
      instance_id: "mcp_server",
      arguments: { port: 8900 },
      links: { front_camera: "front_cam_inst", recorder: "recorder_inst", arm: "arm_inst" },
    }
  ]
}
```

:::caution
A git ref pinned in `repositories.json5` and the node `tag` declared in `peppy.json5` are independent values, and they do not share the same format: git refs can contain dots (e.g. `v0.1.0`), but node tags must start with an ASCII letter and forbid dots (e.g. `v1`, `donut`). This means a repository could be pinned to the git ref `v0.1.0` while `peppy.json5` specifies `tag: "v1"`. Keep them coordinated so a checkout of a given git ref lines up with the tag your launcher expects.
:::

### Launching from a repository

Launchers discovered by `peppy repo refresh` (see [Repositories](/advanced_guides/repositories/)) can be invoked by bare name, no path required:

```sh
peppy stack launch openarm01_sim_teleop
```

An argument that contains a path separator or ends in `.json5` is resolved as a filesystem path: `./my_launcher.json5`, `/abs/my_launcher.json5`, `my_launcher.json5`. A bare name (no separator, no extension) is a repository launcher and is never looked up on disk, whatever the current directory holds: `peppy stack launch my_launcher` resolves through the repository cache at `~/.peppy/cache/launchers.json5` even when a `my_launcher.json5` sits next to the caller. Run `peppy repo refresh` first on the machine you submit the launch to; the launcher document, like every repository source, resolves on that machine alone.

If the name resolves neither to a file nor to a cached launcher, the launch fails with an explicit "not found" error. If one repository provides two launcher files with that name, the launch fails with a distinct ambiguity error naming both: launchers are keyed by filename, so two identically named `.json5` files anywhere in one repository contest the same name even in different directories.

:::caution
Running the `peppy stack launch` or `peppy stack build` command clears the existing node stack and stops all running instances
:::

A launch ends with the log file of every node it added, built and started, then the URLs the started instances serve, and the completion line. The URLs come from the nodes that declare [`execution.endpoints`](/guides/first_node/#serving-a-page-or-an-mcp-endpoint): the daemon hosting each instance expands the socket the node announced into one URL per address of its machine, loopback first, and the core node name after the `@` says which machine that is. Pages an operator opens in a browser and endpoints an MCP client attaches to are printed under separate headings, `Web pages:` before `MCP endpoints:`, and a heading appears only when it has an entry. `peppy stack join` prints the same blocks for the instances the copy started.

The output confirms that all nodes have been added to the stack along with their dependency relationships. When an instance serves an endpoint, an `Instance endpoints` table follows the bindings, one row per URL with the endpoint's `KIND` and `LABEL`. The `Instance bindings` table breaks that down per instance: the consumers (`fake_robot_brain`, `fake_video_reconstruction`) list the `depends_on` slots they resolved, while the producers (`fake_openarm01_controller`, `fake_uvc_camera`) and the core node declare no slots and show `(none)`. A resolved binding shows the chosen producer(s) as `instance_id@core_node`, ordered by link ID; a multi-cardinality slot lists every bound member in plan order, and an empty slot, whether a `zero_or_more` slot bound to nothing or a `zero_or_one` slot declared vacant, shows `(empty set)`. Every declared producer slot (`depends_on.nodes` / `depends_on.contracts`) is either bound or, where its manifest declares `cardinality: "zero_or_one"`, declared [`vacant`](#links-optional); only a `zero_or_more` slot may be left out entirely, and a launcher that leaves any other one out is rejected at validation (see [dependency cardinality](/advanced_guides/topics/#dependency-cardinality)). Pairing and observer slots follow the same shape: a participant slot is paired and an observer slot is linked, or, where its manifest declares it `cardinality: "zero_or_one"`, declared vacant, unless its cardinality is `zero_or_more`, where omitting it IS its empty set. The launch also prints a `Slice of launch ...` line above the tables naming the launch that produced this stack and its coordinator.

## Instance attributes

Every entry in an `instances` array configures one running copy of the deployment's node. Two instances of the same node are independent: they get their own arguments, their own environment, and their own bindings.

```json5 title="peppy_launcher.json5"
{
  source: { name: "uvc_camera:v1" },
  instances: [
    {
      instance_id: "camera_front",
      arguments: { device: { path: "/dev/video0" }, frame_rate: 30 },
      env_vars: { GST_DEBUG: "2" },
      framework: { clock: "simulation" },
    },
    {
      instance_id: "camera_rear",
      arguments: { device: { path: "/dev/video1" }, frame_rate: 15 },
    },
  ],
}
```

### `instance_id` (required)

The name this copy runs under. It labels the instance in `peppy stack list`, in its log file, and in every `links` value that points at it.

Allowed characters are letters, digits, `_` and `-`. The id must be unique across the whole stack, not just within its own deployment: two deployments cannot both declare `camera_front`, and no instance may take the core node's own id. A collision is reported before anything starts.

### `arguments` (optional)

Values for the parameters the node declares in its `execution.parameters` block, written with the same nesting as that schema. See the [Parameters reference](/reference/parameters/) for the full syntax.

A parameter that declares a `$default` may be omitted, and the daemon fills it in before the node starts. A required parameter left without a value fails the launch as that instance starts, naming the leaf it is missing (`Missing required parameters: device.serial`). Unknown keys and type mismatches are caught by the node itself as it boots, so they surface as that instance failing to come up.

A [container node](/advanced_guides/containers/) can also reference these values in its `mount_paths` with `${parameters:<path>}`, which is how two instances of one node mount two different host devices.

### `env_vars` (optional)

Environment variables for this instance's process.

`peppy stack launch` forwards a filtered copy of your shell environment to the instances it starts on the machine you launch from, so a node there already sees your `PATH` and the rest. The filter drops `PWD`, `OLDPWD`, `TMPDIR`, `TEMP`, `TMP`, `PYTHONPATH`, and `PYTHONHOME`, plus any name that is not a shell identifier, any value with whitespace or shell metacharacters, and the injection-prone names listed below. `PYTHONPATH` and `PYTHONHOME` are stripped so a caller shell that exports them cannot displace a container node's vendored `peppylib`/`peppygen` path; a node that genuinely needs either sets it through its own `env_vars`. An instance placed on another machine receives only its declared `env_vars`. `env_vars` is layered on top of the forwarded set for what differs per instance (a device path, a board serial, a log level), and a name declared here replaces the forwarded value:

```json5
{
  source: { name: "esp32_board:v1" },
  instances: [
    { instance_id: "esp32_left",  env_vars: { ESP32_DEVICE: "/dev/ttyUSB0" } },
    { instance_id: "esp32_right", env_vars: { ESP32_DEVICE: "/dev/ttyUSB1" } },
  ],
}
```

Entries are checked when the launcher file is read, before the running stack is touched:

- **Names** must be shell identifiers: a letter or `_` first, then letters, digits and `_`. `ESP32_DEVICE` is fine, `esp32-device` is not.
- **Values** may hold letters, digits and `` _ - . / : , = @ + % ``. Whitespace, quotes and shell metacharacters (`;`, `$`, `` ` ``, `|`, and friends) are rejected, so a value like `"--flag other"` has to reach the node another way, typically as an [argument](#arguments-optional).
- **Injection-prone names** are rejected outright: the dynamic-linker and shell hooks (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `BASH_ENV`, `IFS`, and the rest of that family).

:::note
The name and value rules exist because a container node receives its environment through Apptainer, which forwards each variable under the `APPTAINERENV_` prefix into a script the container sources at startup, where the shell expands the value. A name that is not a shell identifier would not parse as an assignment, and a value carrying `$`, a backtick or a quote would be expanded or run inside the container rather than arriving as written. The same rule applies to process nodes so that adding a `container` block to a node later cannot break the launchers that already deploy it.
:::

`env_vars` reach the instance when it starts. Fetching and building a node happen once for the node, not once per instance, so a variable your build needs (a registry token, a toolchain path) belongs in the shell you run `peppy stack launch` or `peppy stack build` from, where it is forwarded to build steps on that machine too, unless the launcher names it in an [`env_from_launch`](#env_from_launch-optional): such a variable reaches only the run of the instances that name it. A build on another machine sees none of your caller environment: your environment describes your machine, so it stays there.

A value that must not be in a launcher file, such as the API key of a hosted model, goes in [`env_from_launch`](#env_from_launch-optional) instead.

### `env_from_launch` (optional)

Lists environment variable names that this instance inherits from the launching shell. Use `env_from_launch` for secrets or user-specific values that should never be committed to a launcher file (such as an API key for a hosted model). Use `env_vars` for non-secret values like device paths or log levels.

<Code code={hostedBrainLauncher} lang="json5" title="hosted_brain_arm.json5" />

`env_from_launch` also takes one of several sets of variables, `{ any_of: [[...], [...]] }`: the instance takes the variables of the first set that the environment holds complete, and no variable of the other sets. A brain that calls its models either through an OpenAI-compatible API or at the provider of each model names both ways:

```json5
{ instance_id: "brain_inst",
  env_from_launch: { any_of: [
    ["OPENAI_COMPATIBLE_API_BASE", "OPENAI_COMPATIBLE_API_KEY"],
    ["GEMINI_API_KEY"],
  ] } }
```

With both sets in the shell of the launch, the brain gets `OPENAI_COMPATIBLE_API_BASE` and `OPENAI_COMPATIBLE_API_KEY`, and not `GEMINI_API_KEY`. With no set complete, the launch is refused, and the message names every set. A set held in part, some of its variables and not all, is refused too, also beside a complete set: with `OPENAI_COMPATIBLE_API_BASE` and `GEMINI_API_KEY` in the shell and no `OPENAI_COMPATIBLE_API_KEY`, the launch is refused, and the message names `OPENAI_COMPATIBLE_API_KEY`. So a shell that names an OpenAI-compatible API in part never gives the brain `GEMINI_API_KEY` in its place. An instance writes a list or an `any_of`, not both, and each variable is in one set only.

How launch variables work:

- **Isolated to named instances**: Any variable listed in `env_from_launch` (or added via [`set_env_from_launch`](#adjustments)) is delivered *only* to the runtime process of instances that take it: each variable of a list, and the variables of the chosen set of an `any_of`. Other instances, the other sets of an `any_of`, and add/build steps never receive it, even on the coordinator.
- **Kept in daemon memory for later joins**: The daemon holds the launch variables in memory for the lifetime of the stack so later joins (including `stack.join` from MCP or an external client) can pass the same keys to newly joined instances without writing secrets to disk. `peppy stack reset`, a new launch, or a daemon stop clears them.
- **Coordinator only**: Launch variables never leave the machine where you ran `peppy stack launch`. Placing an instance with `env_from_launch` on a remote peer is refused.
- **A join chooses a set as it reads a value**: A join through `robot_membership:v1` forwards no shell environment, so an `any_of` takes the set that the kept values complete, the set of the launch. A `peppy stack join` reads its own shell first, then the kept values, for the set of an `any_of` as for each value: a join shell that completes an earlier set gives that set to the instances the join starts. A set that the join shell and the kept values hold in part refuses the join, as it refuses a launch.
- **Never logged**: Values never appear in logs, feedback lines, errors, `peppy stack list`, fleet listings, MCP responses, data root files, or process command lines (on macOS, container env vars are passed over stdin to Apptainer inside Lima).

To add launch variables to an instance defined in a shared fragment, use a [`set_env_from_launch`](#adjustments) adjustment:

```json5
{ target: "brain_inst", when: { brain: "vlm_router_brain" },
  set_arguments: {
    perception_model: "gemini-robotics-er-2-preview",
    manipulation_model: "gemini-robotics-er-2-preview",
  },
  set_env_from_launch: ["GEMINI_API_KEY"] },
```

If a node can switch between multiple hosted models at runtime, list the API keys for all of them; switching to a model whose key was not provided fails inside the node.

Effective environment per start mode:

| How the instance starts | Environment it receives |
|---|---|
| `peppy stack launch` (coordinator) | Forwarded shell env (minus all launch variables) + requested `env_from_launch` values + `env_vars`. Missing any requested variable of a list, an `any_of` with no complete set, or a set of an `any_of` held in part aborts the launch. |
| `peppy stack join` (coordinator) | Forwarded join shell env (minus launch variables) + requested `env_from_launch` values (join shell overrides kept launch values, for a value and for the set of an `any_of`) + `env_vars`. |
| Join via `robot_membership:v1` (MCP / API) | Kept launch values for requested `env_from_launch`, the set of an `any_of` that they complete + `env_vars` (no shell env is forwarded). |
| Any remote peer | `env_vars` only (instances with `env_from_launch` cannot run on peers). |

Validation rules:

- **Allowed names**: Must follow `env_vars` naming rules and cannot be stripped shell vars (`PWD`, `OLDPWD`, `TMPDIR`, `TEMP`, `TMP`, `PYTHONPATH`, `PYTHONHOME`). Names form an unordered set (duplicates are refused; empty list equals omitted; `peppy stack resolve` sorts names).
- **An `any_of`**: names two sets or more, in order. Each set names at least one variable, and each variable once. Each variable is in one set only: two equal sets, a set that holds another, and two sets that share a variable are refused, because the later set is never taken (when it is complete, the earlier set is complete too, or held in part). Each set writes back in name order, and the sets in the order written.
- **No overlap with `env_vars`**: Declaring the same variable in both `env_vars` and `env_from_launch` on one instance (after adjustments), a name of any set of an `any_of` included, is refused.
- **Checked before touching the running stack**: `peppy stack launch` verifies that every variable of a list, and one complete set and no set held in part of each `any_of`, needed by its instances *and* by any copy a `robot_membership` scope can join (across all feature combinations, even with `--no-prebuild`) is present, non-empty, and free of forbidden characters. If any is missing, the existing stack stays untouched:

```
the launch needs `GEMINI_API_KEY`, and the launch environment does not hold it, or holds it empty or with characters that a node cannot receive: `brain_inst` of option `demo_arm` takes it from the launch, and stack.join through `framework_controls_inst` can add a copy of `demo_arm`. Export `GEMINI_API_KEY` in the shell that launches. A value must not be empty, and must hold letters, digits and `_ - . / : , = @ + %` only
```

For an `any_of` with no complete set, the refusal names every set:

Export every variable of one set in the shell that launches. A value must not be empty, and must hold letters, digits and `_ - . / : , = @ + %` only
```

For a set held in part, the refusal names the set and the variables that it lacks:

```

### `framework` (optional)

Framework-level settings applied uniformly to every node:

- `clock`: Timeline this instance reads (`wall` or a domain declared under [`framework.clocks`](#clock-domains)). Defaults to `wall`. Omit on an instance already declared as a domain's publisher. See [System clock](/advanced_guides/system_clock/#clock-domains).
- `restart`: What the daemon does when the instance exits or stops answering health checks (`"never"`, `"on_failure"`, `"always"`, or `{ policy, max_restarts }`). Overrides the node's `framework.restart` and the launcher root's. See [Restart policy](#restart-policy).

Unknown keys inside `framework` fail validation immediately.

### `core_node` (optional)

Places the instance on one of the logical machine links declared under `core_nodes`. If omitted, the instance runs on the coordinating daemon. See [Running one launcher across several machines](#running-one-launcher-across-several-machines).

### `links` (optional)

Wires every `depends_on` slot declared by the node, keyed by `link_id`:

- **Producer slots** (`depends_on.nodes` / `depends_on.contracts`): target producer instance ID (scalar for `one` / `zero_or_one`, array for `one_or_more` / `zero_or_more`).
- **Pairing participant slots** (`depends_on.pairings`): peer instance ID as `"<peer>"` or `"<peer>/<peer_link_id>"` when the peer has multiple matching slots (scalar or array matching cardinality).
- **Observer slots** (`depends_on.pairing_observers`): source instance ID as `"<source>"` or `"<source>/<source_link_id>"` (scalar or array matching cardinality, preserving order).

**Intentional vacancy:** To leave a slot empty on purpose, write `{ vacant: "<reason>" }`. Vacancy requires both sides to agree:

1. The node manifest must declare `cardinality: "zero_or_one"` on that slot.
2. The launcher must explicitly write `{ vacant: "<non-empty reason>" }` (reported when the node starts).

Leaving a `zero_or_one` slot out of `links` is still an error, so an accidental omission is never mistaken for an intentional vacancy. (`zero_or_more` slots use `[]` or omission for empty; `one` and `one_or_more` slots can never be empty.)

```json5
{
  source: { name: "session_recorder:v1" },
  instances: [
    {
      instance_id: "rec_1",
      links: {
        // Producer slots: `storage` is `one`, `cameras` is multi-cardinality.
        storage: "disk_1",
        cameras: ["cam_left", "cam_right"],
        // Participant slot: `/<peer_link_id>` disambiguates when the peer has several slots.
        arm: "arm_1/limb",
        // Observer slot: scalar or array matching cardinality.
        watch: "ctrl_1",
        // Deliberately empty `zero_or_one` slot with reason.
        gripper: { vacant: "bench rig: no gripper on this frame" },
      },
    },
  ],
}
```

Every target `instance_id` must be declared in the same launcher. Different instances of the same node can bind or vacate the same slot independently:

```json5
instances: [
  {
    instance_id: "backbone_governed",
    links: { leader_left_arm: "commander_inst/left_arm" },
  },
  {
    instance_id: "backbone_monitor",
    links: { leader_left_arm: { vacant: "monitor rig: nothing commands this backbone" } },
  },
]
```

Daemon targets take `daemon_scopes`, never `links`.

Write `{ vacant: "<reason>" }` to leave a daemon target disabled (an MCP server skips those tools; the daemon refuses node calls to that target). When the instance lives in a shared fragment, supply scopes from the launcher with a top-level [`set_daemon_scopes`](#adjustments) adjustment. Copies never set daemon scopes.

**Validation** runs before anything starts (during `launch`, `join`, and [`peppy stack resolve`](#auditing-a-composed-launch)):

1. **Instance & shape rules** (checked by `launch`, `join`, and `resolve`):
   - Every daemon target must have a valid scope matching its interface schema (for example, `robot_membership` requires non-empty `options` with `model`, `max_copies >= 1`, no empty `features: []`, and no duplicate axes; `robot_leases` requires non-empty unique `members`).
   - Unknown keys, `daemon_scopes` on an instance with no daemon target, or putting a daemon target in `links` are refused.

2. **Launcher & selection rules** (checked by `launch` and `resolve` once step 1 passes; see [Scopes](/advanced_guides/mcp/#scopes)):

If an instance with a daemon target is started outside a launcher (such as via `peppy node run`), it receives no scopes; the built-in MCP server refuses to serve and logs which target is missing a scope.

## Clock domains

A launcher declares the timelines its instances read in a root-level `framework` block, beside `deployments`:

```json5 title="peppy_launcher.json5"
{
  peppy_schema: "launcher/v1",
  description: ["An OpenArm in the Waldo simulation, on the clock of the simulation. It needs a machine that runs the simulation."],
  framework: {
    clocks: {
      // One instance supplies this timeline, and naming it here is what
      // makes `simulation_inst` the domain's publisher.
      simulation: { publisher: "simulation_inst" },
      // A name for the time every machine already keeps.
      physical_robot: "wall",
    },
  },
  deployments: [
    {
      source: { name: "waldo", tag: "v1" },
      instances: [{ instance_id: "simulation_inst" }],
    },
    {
      source: { name: "openarm_sim_arm", tag: "v1" },
      instances: [{ instance_id: "arm_inst", framework: { clock: "simulation" } }],
    },
  ],
}
```

A declaration is `{ publisher: "<instance_id>" }` for a timeline one instance supplies, or `"wall"` for a name the time every machine already keeps answers to. `wall` itself is built in and cannot be declared. Every other instance names the domain it reads with [`framework.clock`](#framework-optional).

The launcher's declarations and those of every [fragment](#fragments-splitting-a-launcher-across-files) the selection pulls in are merged: identical declarations agree, two different declarations of one name are refused naming both documents, and an unselected fragment contributes nothing. A [copy](#copies) binds the domains the stack declares, naming them as the stack does.

Every producer binding, pairing and observation joins two instances that read one clock, so a launcher wiring an instance on one domain to an instance on another is refused before anything starts. See [System clock](/advanced_guides/system_clock/#clock-domains).

The launcher's `framework` also takes `restart`, the policy of every instance whose entry and node declare none; a fragment writes a policy on its instance entries or through an adjustment's `set_framework`, never at its root.

## Restart policy

A restart policy controls what the daemon does when a `running` instance exits on its own or stops answering health checks:

| Policy | On clean exit (code 0) | On crash / non-zero exit / health kill |
|---|---|---|
| `"never"` | Moves to `finished` | Moves to `failed` (unhealthy instances are never killed) |
| `"on_failure"` *(default)* | Moves to `finished` | Restarts (also kills unresponsive instances after 60 s; see [Health monitoring](/guides/node_stack/#instance-health-and-lifecycle)) |
| `"always"` | Restarts | Restarts (also kills unresponsive instances after 60 s) |

To cap consecutive restart attempts (including failed restarts), pass an object: `{ policy: "on_failure", max_restarts: 5 }`. Exceeding `max_restarts` leaves the instance `failed`. (`max_restarts` is invalid with `"never"`.)

**Precedence (most specific wins; each level replaces the whole value without merging):**

1. **Instance**: `framework.restart` on the launcher instance entry, `set_framework.restart` in an adjustment, or `--restart` / `--max-restarts` on `peppy node run` / `peppy node add --run`.
2. **Node**: `framework.restart` in `peppy.json5`.
3. **Launcher root**: `framework.restart` at the launcher root (fragments cannot set a root restart policy).
4. **Default**: `"on_failure"`.

A node declares its own policy in `peppy.json5`:

<Code code={wristCameraNode} lang="json5" title="peppy.json5" />

In the launcher below, the rear camera inherits the root's `always`, the front camera overrides it on its instance entry, and the wrist camera uses its own manifest's `on_failure`:

For a single node on the CLI:

```bash
peppy node run wrist_camera:v1 -i wrist_cam_inst --restart on_failure --max-restarts 5
```

**How restarts behave:**

- **Only after first `running`**: A failed initial start still fails `peppy stack launch` or `peppy node run`.
- **Same identity & wiring**: Each restart launches a new process under the same `instance_id` with the same arguments, environment, clock, core node, slots, pairings, and observations. Consumers receive from it again automatically. Because shutdown hooks do not run on a crash, write `setup` to reset hardware to a safe state before enabling it.
- **Exponential backoff**: Wait starts at **1 second**, doubling on each consecutive exit or failed start up to **60 seconds**. Running cleanly for **2 minutes or more** resets the backoff to 1 second and attempt count to 1. (For health kills, uptime counts only up to the last answered health check, so repeatedly hanging nodes still hit `max_restarts`.)
- **Logs and inspection**: Each process gets its own run log (`<instance_id>_<timestamp>.log`); restarted logs note the attempt number and previous log path. `peppy stack list` shows `restarting` and `RESTARTS` count; `peppy node info` shows attempt count, last exit, and next start time; `peppy stack resolve` prints each instance's effective policy and origin.
- **Interaction with other commands**: Explicit stop/replace commands (`peppy node stop`, `node remove`, `node add`, `stack reset`, `stack remove`, `stack launch`, daemon shutdown) cancel any pending restart. While a restart is actively starting up (up to 10 min ready timeout), stack commands on that daemon return `busy` naming the restarting instance and how to stop it. `peppy node remove` pauses pending restarts while stopping instances; if an instance is mid-start, re-run `peppy node remove <name>:<tag> --stop-instances` once it finishes. `peppy stack join` refuses to modify a running instance's restart policy or add members to a `restarting` instance's slot.

Example crash and restart in `~/.peppy/stack_log.log`:

```text
[2026-10-07T14:02:11.204+00:00] Instance 'wrist_cam_inst' of node 'wrist_camera:v1' failed: signal 11 (SIGSEGV), core dumped
[2026-10-07T14:02:11.209+00:00] Instance 'wrist_cam_inst' of node 'wrist_camera:v1' restarting in 1 s (attempt 1)
[2026-10-07T14:02:13.487+00:00] Instance 'wrist_cam_inst' of node 'wrist_camera:v1' restarted (attempt 1)
```

### Starting a failed instance again

An instance in a terminal `failed` or `finished` state stays listed until you clear or relaunch it. How you restart it depends on how it was originally started:

1. **Started via `peppy node run` or `peppy node add --run`**:
   Clear the old instance with `peppy node stop <instance-id>`, then run `peppy node run <name>:<tag>` with the original flags and links. (If another running peer had paired into this instance via its own `--link`, find the pair in `~/.peppy/logs/run/*.log` using `grep -l '⇌ [^ ]*/<instance-id>:' ~/.peppy/logs/run/*.log` and re-establish it with `--link LINK_ID@PEER_INSTANCE[/PEER_LINK]`.)
   ```sh
   peppy node stop arm_1
   peppy node run --instance-id arm_1 robot_arm:v1 --link controller@ctrl_1
   ```
2. **Started as part of a joined copy** (listed under a `Copy` line in `peppy stack list` that is *not* repeated verbatim under `Launch copies`):
   Note its `Copy` line first, then remove and re-join the copy on the coordinator (or with `--core-node <coordinator>`):
   ```sh
   peppy stack remove bravo
   peppy stack join openarm:bravo@jetson-2 --with model=openarm_v1,robot_commander=ker_commander
   ```
   *(If removal is refused, such as the last copy of a `one_or_more` axis, relaunch the stack instead.)*
3. **Started by `peppy stack launch`** (a base stack instance, or a copy whose full `Copy` line matches an entry under `Launch copies`):
   Re-run `peppy stack launch` on the coordinator with the original launcher, `--place`, `--with`, and `--join` arguments. Because `launch` replaces the entire stack, note any extra joined copies first and re-join them afterward.

If a restart was refused because its [clock domain](/advanced_guides/system_clock/#lifetime-replacement-and-removal) publisher ended, the stack log names the cause: relaunch the stack (for launcher/join instances) or restart the clock publisher with `--publish-clock` before re-running the reader with `--clock` (for `peppy node run`).

## Reusing built nodes across launches

Every node build goes through the [build artifact cache](/advanced_guides/containers/#build-caching). If staged sources match an earlier build byte for byte (same Peppy version, OS, architecture, and artifact kind), the launch reuses the cached artifact in seconds:

```
Reusing cached build of waldo:v1 (fingerprint 3f9a1c2e5d7b8a4f) at ~/.peppy/built_nodes/waldo_v1/3f9a1c2e5d7b8a4f.linux-amd64.sif
```

Pass `--rebuild` to `peppy stack launch` or `peppy stack build` to force a fresh build on all machines (for example, after a floating Docker base image tag updates).

### Building without starting

`peppy stack build` accepts the same flags as `peppy stack launch` and runs everything through the build phase (replacing the stack, adding and building all nodes on their target machines plus [joinable nodes](#building-the-nodes-a-join-brings) on the coordinator) without starting any instances.

This is ideal for baking machine disk images so robots boot ready to launch immediately:

```sh
peppy stack build openarm_simulation --with mujoco
# Save the disk image and boot each machine from it, then run:
peppy stack launch openarm_simulation --with mujoco
```

:::caution
On Linux, the default core node name is derived from `/var/lib/dbus/machine-id` (or `/etc/machine-id`). Machines cloned from the same disk image will collide unless each gets a unique [`core_node_name`](/advanced_guides/daemon_config/#core_node_name-the-daemons-core-node-name).
:::

After `peppy stack build`, nodes sit at `Ready` with `0` instances. Because no launcher is active, `peppy stack join` requires `peppy stack launch` first. Pass `peppy stack build --publish` to also push built container images to an OCI registry ([Publish the nodes of a stack](/advanced_guides/publishing/#publish-the-nodes-of-a-stack)).

### Building the nodes a join brings

When a launcher includes an MCP endpoint with a [`robot_membership` daemon target](/advanced_guides/mcp/#daemon-targets), clients can dynamically add robots after launch. To keep those joins fast, `peppy stack launch` pre-builds every **joinable node** on the coordinator up front:

- **What gets pre-built**: Every node across all feature combinations allowed by the `robot_membership` scope(s) (built-in MCP servers need no build). Nodes already deployed on the coordinator are built only once; nodes placed elsewhere by the launch are also built on the coordinator so local joins have them ready.
- **How joins use them**: Later joins on the coordinator (`stack.join` or `peppy stack join`) reuse those pinned sources and cached artifacts in seconds, even after `peppy repo refresh`. Joins placed on a remote machine or using un-scoped `--with` options still build on demand.
- **Failure handling**: An unresolvable joinable node or invalid trial composition refuses the launch before touching the running stack; a build failure fails and clears the launch.
- **Opting out**: Pass `--no-prebuild` to `peppy stack launch` or `peppy stack build` to build only the nodes currently launched; joins will resolve against current repositories and build on demand (useful when iterating on a robot node without relaunching the stack). `--rebuild` forces joinable nodes to rebuild too.

## Launch timeouts

Each launch phase (`add`, `build`, `run`) has a per-node **idle timeout** that resets whenever the node produces progress (download bytes, build output, disk writes, CPU usage, startup output, or the ready signal):

| Flag | Phase | Default |
| --- | --- | --- |
| `--node-add-idle-timeout-secs` | Fetching source and generating bindings | 600 s |
| `--node-build-idle-timeout-secs` | Running `build_cmd` or building container image (disk writes and CPU usage count as output) | 180 s |
| `--node-run-idle-timeout-secs` | Starting an instance until setup returns and it is `running` | 600 s |

Additional timeout details:

- **Overall budget**: Add `--max-timeout-secs` to cap the total duration of the launch or join.
- **Client watchdog**: The CLI waits up to `max(idle budgets) + 60 s` without daemon output before exiting with code `1` (which triggers daemon-side cancellation). For MCP `robot_membership` `join` tools, set `progress_timeout_ms` to at least `660000` (660 s) so daemon timeouts surface first.
- **Cargo progress**: Builds automatically set `CARGO_TERM_PROGRESS_WHEN=always` and `CARGO_TERM_PROGRESS_WIDTH=80` (unless overridden) so slow crate downloads keep resetting the idle clock.
- **Setup timeout**: Within the run phase, each node's [`setup_timeout_secs`](/guides/node_stack/#how-an-instance-starts) (max 540 s) still applies independently.
- **Cleanup on timeout**: An interrupted `add` never publishes the node (in-flight codegen finishes on its worker thread and deletes the temp dir); an interrupted `build` kills the build process; an interrupted `run` tears down the half-started instance (gracefully if it already signalled ready, force-killed if not). A timed-out `launch` clears the stack; a timed-out `join` rolls back its copy and leaves the existing stack running.

## How a stack command ends

`peppy stack launch`, `build`, `join`, and `remove` each run as a goal on the daemon. If refused (exit code `3`) or failed (exit code `4`), the CLI prints the **failure kind**, reason, and (on failure) the launch log path:

```text
Error: Launch refused (busy): a stack launch, build, join, removal or reset, or a coordinator's change to this daemon's slice, is in progress on this daemon; run this again once it ends
Error: Launch failed (attempt_failed): failed to build node arm:v1: build_cmd `cargo build --release` failed with status exit status: 101. Log file: /home/ubuntu/.peppy/logs/launch/launch_20261023_101500_123Z.log
```

| Kind | Meaning |
| --- | --- |
| `rejected` | Invalid launcher, CLI argument, or reference to a missing item. |
| `busy` | Another stack operation, node command, restart, reset, or launch reservation holds a target machine. Retry once it finishes. |
| `precondition_failed` | Current stack state disallows the operation (such as a name collision or no active launcher). |
| `resource_unavailable` | A target machine is offline or unreachable. |
| `timeout` | An idle or max timeout expired. |
| `attempt_failed` | A build, start, or execution step failed. |

See [Exit statuses of the other commands](/advanced_guides/calling_instances/#exit-statuses-of-the-other-commands) for all exit codes. If the CLI falls behind by more than 65,536 unread output lines, it cancels the goal and exits with code `1`.

### Stopping a stack command with Ctrl+C

| Event | What happens | Exit code |
| --- | --- | --- |
| **1st Ctrl+C** | Sends a cancel to the daemon (forwarded to remote peers). The daemon stops at the current step and cleans up: a cancelled `launch`/`build` clears the stack, a cancelled `join` rolls back its copy, and a cancelled `remove` stops remaining stops while keeping unstopped instances. The CLI waits for cleanup (bounded only by `--max-timeout-secs`). | `5` (cancelled), `0` (already completed), or `4` (already failed) |
| **2nd Ctrl+C** | Stops waiting once the cancel reaches the daemon (cleanup continues in the background). | `130` |
| **3rd Ctrl+C** | Exits immediately. | `130` |
| **CLI killed / terminal closed** | Daemon detects the missing caller and cancels the goal after 1 minute (long enough to survive a router restart). Launch log ends with `cancelled: its sender is gone`. | - |
| **`peppy stack reset`** | Cancels the in-flight operation and clears the stack. | `5` |

## Running one launcher across several machines

A launcher can span machines. It declares named placeholders under `core_nodes`,
each instance says which one it runs on via `core_node`, and
`peppy stack launch --place <core-node-link>@<core-node>` binds those
placeholders to real hardware at launch time. Producer links, pairings, and
observations all work across the boundary, and consumers still start after their
producers. See [Federation](/advanced_guides/federation/).

Every placeholder the launcher declares must be bound with `--place`; a launch
that leaves one unwired is refused. The escape hatch is
`peppy stack launch --local`, which ignores the launcher's placements and runs
every instance on the daemon you launched from. `--local` and `--place` are
mutually exclusive, and under `--local` no `--join` and no `--with` word names
a machine. A [copy](#copies) runs where it is named, and each part of it where
the word that selects it says.

## Swapping parts at launch time

A launcher file can describe a family of stacks whose members differ in which implementation fills a slot: a real robot or a simulator, a browser panel or a headset, with or without a recorder. The launcher declares **component axes**, `deployments` says which option of each it starts, and the launch command swaps one with `--with`. A launcher without `components` is a plain flat stack, and that stays the ordinary way to write a one-off.

The whole feature fits in one file. Here is a viewer stack with two swappable cameras:

<Code code={viewerLauncher} lang="json5" title="viewer.json5" />

```sh
peppy stack launch ./viewer.json5              # runs the camera the file deploys (uvc)
peppy stack launch ./viewer.json5 --with=zed   # runs the ZED camera instead
```

Components declare what may run; `deployments` says what runs. An axis entry has four fields:

| Field | Meaning |
|---|---|
| `name` | The axis's name, unique in the launcher. Used in `--with axis=option`, in `deployments`, and in adjustment guards. |
| `options` | The alternatives that fill this axis, at least one. Each option is a fragment: a body using the same `deployments` grammar the launcher's own `deployments` use, written inline, or a path string naming its own [file](#fragments-splitting-a-launcher-across-files), or the object `{ fragments: ["fragments/relays.json5", "fragments/mujoco.json5"], ... }`, which is how an option names more than one file and how, in a launcher, it carries the [adjustments](#adjustments) that run when the option is selected. |
| `cardinality` | How many selections of the axis a stack allows. `one` (the default): exactly one option runs. `zero_or_one`: at most one. `zero_or_more`: any number, each a named [copy](#copies). `one_or_more`: the same copies, with at least one started by every launch and `stack remove` refusing the last one. |
| `provides` | Instance IDs every option defines, so a link written against one is valid whichever option is selected. On an axis that runs as copies the IDs are checked as written, before a copy's name prefixes them. |

A `deployments` entry deploys a node, `{ source, instances }`, or a component's option, `{ <component>: "<option>" }`:

- On a `one` axis the entry names the option that runs, ids as written, and `--with` swaps it for another option of that axis. A `one` axis the file does not deploy must be named with `--with`.
- A `zero_or_one` axis is never deployed by the file, since nothing on the command line could switch it off. `--with` turns it on. A feature that is on by default and switchable is a `one` axis with a `none` option (its body can be empty), deployed by the file and swapped off with `--with none`.
- On an axis that runs as copies the entry lists the ones that run, each under `instances` with a name, or lists none and says how every copy of the option is set up; see [copies](#copies). `--with` cannot name one, since a copy needs a name; `--join OPTION:NAME` starts one with the launch.

Each `--with` entry is either `option` (looked up across every axis in reach) or `axis=option`. A bare word matching options on more than one axis is refused, naming the axes, so `axis=option` says which you mean. An axis takes one option; repeating it, or naming it once bare and once as `axis=option`, selects it once. On `stack launch` and `stack build`, `NAME.option` or `NAME.axis=option` selects the own axis of a copy the file deploys, over the file's `with`.

A launch of a launcher with components echoes the full resolution before anything runs, marking the axes a `deployments` entry filled:

```
components: simulation=waldo (from file)  robot_control=(off)  scene_commander=(off)
copy alpha: robot=openarm_sim  model=openarm_v2 (from file)  robot_commander=web_commander (from file)  recorder=(off)  camera_rig=none (from file)  brain=(off)
```

Passing `--with` to a launcher that declares no `components` is refused.

## Adjustments

A family of stacks often needs more than swapped deployments: selecting the recorder binds it into whichever commander runs, and selecting the KER leader releases the backbone's joint sockets. An **adjustment** names one instance and one change to it, and every change names its operation. A fragment writes only the instances it deploys, so the connections between fragments are the launcher's, written under the option that names the fragment:

```json5
components: [
  { name: "simulation", cardinality: "zero_or_one", provides: ["simulation_inst"],
    options: { mujoco: "simulation/fragments/mujoco.json5", isaac_sim: "simulation/fragments/isaac_sim.json5",
               waldo: "simulation/fragments/waldo.json5" } },
  { name: "recorder", cardinality: "zero_or_one", provides: ["recorder_inst"],
    options: {
      lerobot_recorder: {
        // An inline body, beside the launcher's writes for it.
        deployments: [{ source: { name: "lerobot_recorder", tag: "v1" },
                        instances: [{ instance_id: "recorder_inst" }] }],
        adjustments: [
          // Runs when this option is selected; the guard adds a condition
          // of its own, see below.
          { target: "recorder_inst", when: { simulation: "isaac_sim" },
            set_arguments: { robot_type: "openarm_v2_isaac" } },
        ],
      },
    } },
  { name: "robot_commander", provides: ["commander_inst"],
    options: {
      ker_commander: {
        fragments: ["openarm/fragments/ker_commander.json5"],
        adjustments: [
          {
            target: "backbone_inst",              // an instance the launcher's deployments define
            set_arguments: { upstream_mode: "joints" },
            set_links: { collision_ctrl: { vacant: "the KER never produces governor_control" } },
            unset_links: ["leader_left_arm"],
          },
        ],
      },
    } },
],
```

The launcher's own top-level `adjustments` list takes the same entries, guarded on the launcher's axes, which is how one launcher specializes what every option wrote.

| Operation | Effect |
|---|---|
| `set_arguments` | Replaces the target's value for each named argument key, creating it when absent. Nested objects replace wholesale. |
| `set_framework` | Replaces the target's value for each named [framework knob](#framework-optional), `clock` or `restart`; a knob the adjustment omits keeps its value. How the launcher, under the option that selects a simulated robot, binds the commander and recorder that robot shares with its physical twin to the [clock domain](#clock-domains) this selection runs on. |
| `set_links` | Replaces the target's whole entry for each named slot, creating it when absent. The value uses the ordinary [links](#links-optional) grammar, including vacancies. |
| `add_links` | Appends targets to each named slot's array binding, creating the binding when the slot has no entry. Refused when the slot holds a scalar or a vacancy: replacing is `set_links`'s job. Appending is what lets independent options each contribute bindings to one multi-cardinality slot, and what lets a [copy](#copies) that joins add its own instances to a running instance's set. |
| `unset_links` | Drops each named slot's entry entirely, returning the slot to absent. |
| `set_daemon_scopes` | Replaces the [scope](#daemon_scopes-optional) of each named daemon target, creating it when absent. No operation removes a scope. Refused in the composition of a copy, because a scope belongs to the stack: write it at the top level, under an option of an axis that does not run as copies, or in the instance's own `daemon_scopes`. |
| `set_env_from_launch` | Replaces the target's [`env_from_launch`](#env_from_launch-optional) with the list or the `any_of`, so a launcher names exactly the keys of the models that its instances can use. An empty list is an operation: the target then takes no variable from the launch, for example an instance of a shared fragment whose model calls no service. |

A fragment's adjustments run first (in file order), then option adjustments (in `components` axis order), and finally top-level launcher adjustments. Later writes win on the same field.

**How adjustments target instances in [copies](#copies):**

An adjustment resolves its `target` inside each matching copy when any of the following holds:

1. It lives under an option of a copy axis (`zero_or_more` / `one_or_more`).
2. It lives at the top level or under a single-fill option (`one` / `zero_or_one`) and has a `when` guard naming a copy axis.
3. Its `target` is defined *only* by options on copy axes (runs in every copy of those axes).

If an unguarded adjustment targets an instance ID defined by *both* a copy axis and another single-fill axis (not its own option), composition refuses it as ambiguous: either move it under that single-fill option or guard it on the copy axis.

**Target rules and guards:**

- `target` accepts either a single instance ID or a non-empty list of unique instance IDs (applied in order to each):
  ```json5
  { target: ["framework_controls_inst", "applier_inst"],
    set_daemon_scopes: { stack: { max_copies: 4, options: [ /* ... */ ] } } }
  ```
- If the current selection does not deploy a target, the adjustment is **skipped** (not an error). However, targeting an instance ID that *no* reachable option defines fails at load time as a dead reference.
- An option's adjustments automatically run only when that option is selected. Add `when` only for extra cross-axis conditions: top-level guards name launcher axes; option guards name other launcher axes plus [the option's own axes](#an-options-own-axes). Each axis takes one option or a non-empty list (OR within a list, AND across axes):
  ```json5
  when: { simulation: ["mujoco", "isaac_sim"] }
  ```
  An adjustment reaching copies from the top level or a single-fill option may guard on at most one copy axis (never on a copy's own axes) and target only that copy's or stack instances.

**Rule of thumb:** If an operator should choose a variation on the CLI, make it an option on an axis. If a change is just a consequence of another choice, write it as an adjustment under that option.

## Constraints

Adjustments tweak valid stacks; **constraints** forbid invalid combinations (for example, launching a physical-only stereo camera against a simulator). Constraints only reject invalid selections before anything starts; they never auto-select options.

```json5
constraints: [
  // With the ZED camera selected, the robot must be the real one.
  { when: { camera: "zed" }, requires: [{ robot: "real" }],
    reason: "the ZED films the physical rig" },

  // The whole combination is refused, no guard needed.
  { forbids: [{ robot: "mujoco", camera: "zed" }],
    reason: "the stereo camera pairs with the real rig only" },
]
```

| Field | Meaning |
|---|---|
| `when` | Optional guard (`axis: option` or `axis: [opt1, opt2]`, AND across axes, OR within a list). Omit to apply to all selections. |
| `requires` | List of alternatives (OR across entries; AND within each map). At least one alternative must match. |
| `forbids` | List of forbidden combinations (OR across entries; AND within each map). Matching any entry rejects the selection. |
| `reason` | Required explanation quoted verbatim when rejected. |

Key rules:

- Every constraint must include at least one of `requires` or `forbids`, cannot repeat an axis already fixed by `when`, and cannot duplicate maps.
- An unselected (`zero_or_one`) axis never matches a `when` or `requires` entry. Use `forbids` to block an optional axis from pairing with another option; prefer `requires` on required axes so future options fail closed.
- The first violated constraint in declaration order wins and prints the full resolved selection, rule, and `reason`.
- Launcher constraints use launcher axes; fragment constraints use the fragment's own axes and launcher axes. `peppy repo index --check` rejects dead constraints, unreachable options, and invalid default/file-deployed stacks.

## Fragments: splitting a launcher across files

Extract an option body into a separate **fragment** file (`peppy_schema: "launcher_fragment/v1"`) once multiple launchers share it. Inline options stay self-contained when reuse is not needed.

<Code code={zedCameraFragment} lang="json5" title="fragments/zed_camera.json5" />

Reference a fragment by relative path or combine multiple fragments in order with `fragments: [...]`:

```json5
options: {
  mujoco: { fragments: ["fragments/relays.json5", "fragments/mujoco.json5"] },
  isaac_sim: { fragments: ["fragments/relays.json5", "fragments/isaac_sim.json5"],
               adjustments: [
                 { target: "viewer_inst", set_arguments: { renderer: "path_traced" } },
               ] },
}
```

Fragment rules:

- **Path boundaries**: Paths resolve relative to the declaring document and must stay within the repository root (nearest ancestor with `peppy_repository.json5`, or the launcher's directory for standalone files). Absolute paths and escaping symlinks are rejected.
- **Ownership**: A fragment's `adjustments` can only modify instances deployed by that fragment itself; cross-fragment wiring belongs in the launcher's option `adjustments`. A fragment's `framework` block may only declare `clocks` (never root `restart`). Fragments may declare `core_nodes` (merged into the launcher's placeholders when selected).
- **Not launchable standalone**: Fragments are never indexed as launchers by `peppy repo index`, cannot collide with launcher names, and are validated across every legal axis combination by `peppy repo index --check`.

## An option's own axes

An option fragment can declare its own nested `components` (cardinality `one` or `zero_or_one` only; nesting stops at two levels). For example, an OpenArm robot fragment can own its `model`, `robot_commander`, `recorder`, `camera_rig`, and `brain` axes:

- **`role: "robot_commander"`** (at most one per option, never on a copy axis): marks which own axis supplies the robot's local manual controller (such as a leader arm or browser panel) that drives the robot outside [leases and the halt](/advanced_guides/fleet/). Reported in the fleet listing (`none` means no commander).

On a single-robot (`one`) axis, `--with ker_commander` or `--with robot_commander=ker_commander` reaches directly into the fragment's axes. On a multi-robot copy axis, prefix with the copy name (`--with alpha.ker_commander`).

## Copies

An axis with `cardinality: "zero_or_more"` or `"one_or_more"` runs as **copies**: named deployments of an option (such as multiple robots sharing one simulation or fleet stack).

- Every instance defined in the copy's fragment is automatically prefixed with `<copy_name>_` (for example, `backbone_inst` inside copy `alpha` becomes `alpha_backbone_inst`). Links between the copy's own instances follow the prefix; links to shared stack instances (like `simulation_inst`) keep their unprefixed IDs.
- The unprefixed fragment ID is also the public member name on a [per-robot MCP surface](/advanced_guides/mcp/#per-robot-surfaces) (so renaming it in a fragment changes the name MCP clients pass).
- **`zero_or_more`**: launches with 0 or more copies; you can add copies at launch (`--join`) or live (`peppy stack join`) and remove any copy (`peppy stack remove`).
- **`one_or_more`**: requires at least 1 copy at launch (listed in `deployments` or passed via `--join`) and refuses removing the last copy.

### Declaring copies in a launcher

```json5
components: [
  { name: "simulation", provides: ["simulation_inst"],
    options: { mujoco: "...", isaac_sim: "...", waldo: "..." } },
  { name: "robot", cardinality: "zero_or_more",
    options: { openarm_sim: "...", so101_sim: "..." } },
],
deployments: [
  { simulation: "waldo" },
  { robot: "openarm_sim", with: { robot_commander: "web_commander" }, instances: [
      { instance_id: "alpha", arguments: { commander_inst: { http_port: 8765 } } },
      { instance_id: "bravo", with: { model: "openarm_v1" }, arguments: { commander_inst: { http_port: 8766 } } },
  ] },
],
```

Each copy entry accepts `instance_id` (name), `with` (own-axis selections), `arguments` (keyed by unprefixed fragment ID, then parameter name), and `adjustments` (same verbs as launcher adjustments, excluding `set_daemon_scopes`). The parent option entry can also declare shared `with`, `arguments`, and `adjustments` inherited by every copy (listed or joined), and may omit `instances` to configure defaults for future joins without starting any copy at launch. Each option can appear in at most one `deployments` entry.

Precedence for a copy's configuration (weakest to strongest):
1. Option fragment defaults
2. Option entry `with` / `arguments` / `adjustments` in `deployments`
3. Per-copy `with` / `arguments` / `adjustments` (or CLI `--with` / `--set-arguments` for joins)

### Launching, joining, and removing copies

```sh
# Launch default copies from the file
peppy stack launch openarm_simulation

# Override a listed copy's own axis at launch
peppy stack launch openarm_simulation --with mujoco,alpha.ker_commander

# Add copies at launch time (comma-separated or repeated --join)
peppy stack launch physical \
  --join openarm:alpha@jetson-1 \
  --join openarm:bravo@jetson-2 \
  --with xr_commander,bravo.model=openarm_v1,bravo.robot_commander=none

# Add and remove copies dynamically on a running stack
peppy stack join openarm_sim:charlie --with web_commander \
  --set-arguments backbone_inst.max_stream_ee_velocity_m_s=0.2 \
  --set-arguments commander_inst.http_port=8766
peppy stack remove charlie
```

- `--join OPTION:NAME[@CORE_NODE]` at launch composes identically to `peppy stack join` after launch, so any copy you can pass at launch can also be joined live.
- `--set-arguments INSTANCE.ARG=JSON5` overrides arguments on `peppy stack join` (quote strings; numbers must be finite).
- Run `join` and `remove` on the coordinator (or pass `--core-node <coordinator>`). Both serialize with other stack operations and reserve only the machines they touch.

### Placing a copy and its parts across machines

A copy runs on the coordinator by default, or on the machine named after `@`:

- **Base copy**: `OPTION:NAME@CORE_NODE` (on `stack join` or `--join`), or `--place NAME@CORE_NODE` (for a copy listed in the launcher file).
- **Individual parts** (an own axis of the copy, such as an AI brain on a GPU host): attach `@CORE_NODE` to its `--with` word (`--with ai_brain_vla@cn-gpu-box` on `stack join`, or `--with delta.ai_brain_vla@cn-gpu-box` on `stack launch`). Use `@self` for the coordinator.

```sh
# OpenArm on jetson-1, AI brain on a GPU machine
peppy stack join openarm_sim:delta@jetson-1 --with ai_brain_vla@cn-gpu-box
```

Launcher files never hardcode machines for copies (`core_node` and `core_nodes` are forbidden in copy entries and copy fragments). Invalid placements are rejected before anything starts (for example: placing an empty `none` option, conflicting machines on one axis, putting `@machine` on a stack-level `--with` axis instead of `--place`, or placing remote machines under `--local`).

### Wiring copies into running stack instances

A stack-level instance (such as a fleet monitor or per-robot MCP server) can dynamically accept new copies by declaring a `one_or_more` or `zero_or_more` producer or observer slot, and having the copy option append its instances via `add_links`:

```json5
// In the monitor's peppy.json5
depends_on: {
  nodes: [{ name: "openarm_backbone", tag: "v1", link_id: "robots", cardinality: "zero_or_more" }],
}

// In the launcher under the robot option
options: {
  openarm: {
    fragments: ["openarm/fragments/openarm.json5"],
    adjustments: [
      { target: "monitor_inst", add_links: { robots: ["backbone_inst"] } },
    ],
  },
}
```

```sh
peppy stack launch monitored          # monitor_inst sees []
peppy stack join openarm:alpha        # [alpha_backbone_inst]
peppy stack join openarm:bravo        # [alpha_backbone_inst, bravo_backbone_inst]
peppy stack remove alpha              # [bravo_backbone_inst]
```

Rules for how joined copies interact with existing stack instances:

- **What a join may change on a running stack instance**: Only (1) appending its own instances to a `one_or_more` / `zero_or_more` producer or observer slot, or (2) pairing into a `zero_or_one` pairing slot declared vacant (releasing the vacancy with `unset_links`; `stack remove` restores the vacancy). Any other modification to a running stack instance (such as changing an argument or restart policy) is refused.
- **No daemon scopes in copies**: Copy entries and copy adjustments cannot declare or modify `daemon_scopes`.
- **Snapshot and pins**: A launch snapshots its launcher/fragment files and resolved node pins. Later joins compose against that snapshot, reusing existing nodes on machines where they already run. (Relaunch to pick up edits to launcher files; a restarted coordinator requires a fresh launch before accepting joins.)

### How `stack remove` and `stack list` work with copies

- **`peppy stack remove NAME`** stops the copy's instances one by one in reverse start order across all its machines (printing each stop line), removes its members from dynamic sets, and restores any vacated pairing slots it took.
  - **Refused** if removing the copy would empty a `one_or_more` slot, remove the last copy of a `one_or_more` axis, or break another copy's link to it.
  - **Offline or reset machines**: If a machine was already reset, nothing stops there; if a machine is offline, removal skips it and warns which instances remain until `peppy stack reset` clears that machine upon return. If a stop fails, the copy stays listed so you can retry `peppy stack remove`.
  - **Failed join**: Stops everything it started, removes added nodes, and leaves the rest of the stack running.
- **`peppy stack list`** prints one recipe line per active copy (paste the part after `:` straight into `--with` on `peppy stack join`), its instances, and its `Set members:`. It also lists `Launch copies` (all copies started by the original launch, unchanged by later joins/removals) and `copy_change` while a join or removal is in progress. Pass `--json` for structured `copies`, `launch_copies`, `copy_change`, and `set_members`.

## Auditing a composed launch

`peppy stack resolve` flattens any composed launcher without a running daemon, writing the resulting plain `launcher/v1` file to **stdout** and a diagnostic report to **stderr**:

```sh
peppy stack resolve physical --join so101:alpha --with xr_commander,alpha.robot_commander=none,alpha.lerobot_recorder
```

```
components: robot_control=(off)  teleop=xr_commander
copy alpha: robot=so101  robot_commander=none  recorder=lerobot_recorder  camera_rig=(off)
adjustments applied:
  alpha_backbone_inst.arguments.upstream_mode: "joints" -> "pose"  (so101/fragments/so101.json5)
  alpha_backbone_inst.links.leader_pose: {"vacant":"upstream_mode joints: arm commands arrive on the joint slot"} -> "headset_inst/right_arm"  (so101/fragments/so101.json5)
  headset_inst.links.recorder: + alpha_recorder_inst  (physical.json5, option `robot.so101`, copy `alpha`)
  alpha_recorder_inst.arguments.robot_type: (absent) -> "so101"  (physical.json5, option `robot.so101`)
adjustments skipped:
  alpha_backbone_inst: guard robot_commander=so101_leader is not met  (so101/fragments/so101.json5)
  headset_inst: guard camera_rig=cameras teleop=xr_commander robot_commander=none is not met  (physical.json5, option `robot.so101`, copy `alpha`)
headset_inst: clock `wall`, restart on_failure (default)
alpha_backbone_inst: clock `wall`, restart on_failure (default)
alpha_recorder_inst: clock `wall`, restart on_failure (default)
link rules hold: slot keys, vacancies, pairing coverage, observation sources and clock agreement checked over 5 node manifest(s)
```

What the report checks (offline, using `~/.peppy/cache/`):

1. **Selections and adjustments**: Every selected axis, copy, applied adjustment (old value -> new value and source file), and skipped adjustment (with unmet guard).
2. **Clocks and restart policies**: Effective clock domain and restart policy (with origin) per instance.
3. **Daemon scopes**: Validates exposure and cached node [`daemon_scopes`](#daemon_scopes-optional) (noting any uncached node manifests skipped).
4. **Launch variables**: Lists every required [`env_from_launch`](#env_from_launch-optional) variable of a list, and every `any_of` with its sets (``launch variables: the launch needs one set of `A` and `B`, or of `C`, from the shell that launches: ...``), and flags any instance using launch variables placed off the coordinator.
5. **Link rules**: Reads cached node manifests to validate slot keys, vacancies, pairing coverage, observation sources, and clock agreement (skipping with a notice if a manifest is missing from the cache; run `peppy repo refresh` to populate it). Contract-implementation matching stays launch-only.

Because stdout is a valid flat `launcher/v1` file, you can redirect it, edit it by hand, and launch it directly (except launchers containing a `robot_membership` scope, which require dynamic copy axes and cannot run flat unless you remove that instance). Copy parts placed with `@machine` flatten onto their copy's `core_nodes` link in the flat file.

### Many selections of one launcher

To validate many combinations in a single fast pass (loading the launcher, fragments, and caches once), pass a JSONL file (or `-` for stdin) to `--selections`:

```sh
peppy stack resolve physical --selections selections.jsonl
```

```json
{}
{"with": ["xr_commander"]}
{"with": ["xr_commander", "alpha.robot_commander=none"], "join": ["so101:alpha"]}
```

- Each input line is a JSON object with optional `with` and `join` string arrays (`{}` tests the default selection).
- Stdout emits one JSON line per selection in input order: either `{"launcher": ..., "report": [...]}` on success (non-finite numbers become `null`), or `{"error": "..."}` on failure.
- Exit code is `0` as long as the launcher and input file themselves are valid; per-selection failures appear as `"error"` records in stdout. Logs go to stderr.
